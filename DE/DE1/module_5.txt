Lecture 55: Is Data Warehouse Still Relevant in the Age of Big Data?
The Question on Everyone's Mind
With the rise of data lakes, lakehouses, cloud storage, and big data technologies like Hadoop and Spark, many organizations question whether traditional data warehouses still have a place in modern data architecture. The answer is a resounding YES, but with important context.

Why Data Warehouses Remain Critical
Business Intelligence & Reporting: Data warehouses are optimized for fast, consistent query performance on structured data---exactly what BI tools need.

Data Quality & Governance: Enterprise-grade data governance, quality checks, and lineage tracking are mature in DW platforms.

Proven Track Record: Decades of refinement have made data warehouses extremely reliable for mission-critical analytics.

SQL Expertise: Most business analysts know SQL. Data warehouses leverage this existing skill set.

Regulatory Compliance: Features like audit trails, data retention policies, and security are built-in.

Performance at Scale: Modern cloud data warehouses (Snowflake, BigQuery, Redshift) handle petabytes with sub-second query times.

The Modern Reality: Hybrid Architectures
Most successful enterprises don't choose between data warehouses and data lakes---they use both:

Data Lake: Store raw, unstructured data for exploratory analysis, ML, and data science

Data Warehouse: Store curated, business-ready data for operational reporting and dashboards

Lakehouse: Combine both approaches with modern table formats (Delta Lake, Iceberg)

Real-World Evidence
According to Gartner's 2024 Magic Quadrant for Cloud Database Management Systems, data warehouse adoption continues to grow 20% year-over-year. Companies like:

Netflix: Uses both data lakes (S3) and data warehouses (Snowflake) for different use cases

Airbnb: Maintains a massive data warehouse for business reporting while using Spark for ML

Spotify: Runs Google BigQuery for analytics alongside data lakes for audio processing

Uber: Uses multiple data warehouses across different regions for regulatory compliance

Key Insight
The question isn't "Should we use a data warehouse?" but rather "How do we integrate a data warehouse into our modern data architecture?"

Lecture 56: Why Do We Need a Data Warehouse?
The Business Problem
Imagine you're a retail company with:

An e-commerce website (PostgreSQL database)

Physical stores with point-of-sale systems (Oracle)

A mobile app (MongoDB)

Marketing campaigns (Salesforce)

Customer service tickets (Zendesk)

Supply chain management (SAP)

Your CEO asks: "What were our total sales last quarter, broken down by region, product category, and customer segment?"

Without a data warehouse, you would need to:

Query 6 different systems with different technologies

Manually combine data in spreadsheets

Deal with inconsistent data formats and naming conventions

Risk getting different numbers depending on when you run each query

Spend days or weeks on what should be a simple analysis

The Data Warehouse Solution
A data warehouse solves this by:

Centralization: Bringing all data into one place

Integration: Combining data from different sources into a unified format

Historical Storage: Keeping data over time for trend analysis

Optimization: Structuring data specifically for analytical queries

Consistency: Ensuring everyone gets the same numbers from the same source

Real-World Example: E-Commerce Analytics
-- Without Data Warehouse: Complex joins across systems
-- Impossible to write this query!

-- With Data Warehouse: Simple, fast query
SELECT
d.year,
d.quarter,
p.category,
c.region,
SUM(f.sales_amount) as total_sales
FROM fact_sales f
JOIN dim_date d ON f.date_key = d.date_key
JOIN dim_product p ON f.product_key = p.product_key
JOIN dim_customer c ON f.customer_key = c.customer_key
WHERE d.year = 2024 AND d.quarter = 1
GROUP BY d.year, d.quarter, p.category, c.region
ORDER BY total_sales DESC;

Lecture 57: What is a Data Warehouse? Complete Definition
The Classic Definition
Bill Inmon (Father of Data Warehousing) defined it as:

"A data warehouse is a subject-oriented, integrated, time-variant, and non-volatile collection of data in support of management's decision-making process."

Let's break this definition down into practical terms:

Components of the Definition
Subject-Oriented: Organized around key business subjects (customers, products, sales) rather than applications.

Integrated: Data from multiple sources is combined and standardized into a unified format.

Time-Variant: Stores historical data---not just current state---enabling trend analysis.

Non-Volatile: Data is stable; once written, it doesn't change (append-only, immutable).

Modern Perspective
Today, we can add to this definition:

Cloud-Native: Most modern DWs are cloud-based (Snowflake, BigQuery, Redshift)

Scalable: Can grow from gigabytes to petabytes seamlessly

Performance-Optimized: Columnar storage, MPP architecture, query optimization

Separation of Storage & Compute: Scale resources independently

Schema Flexibility: Support for semi-structured data (JSON, Parquet)

Architectural Components
A complete data warehouse solution includes:

1. Data Sources
Operational databases, SaaS applications, APIs, files, streams
2. ETL/ELT Layer
Extract, Transform, Load processes (tools: Airflow, dbt, Fivetran)
3. Staging Area
Temporary storage for data validation and transformation
4. Data Warehouse Database
Core storage with fact tables, dimension tables, and data marts
5. Metadata Repository
Data catalog, lineage, schemas, business glossary
6. BI & Analytics Layer
Tableau, Power BI, Looker, Python notebooks
Data Warehouse Architecture

Types of Data Warehouses
Enterprise Data Warehouse (EDW): Central repository for entire organization (e.g., Teradata, Oracle Exadata)

Operational Data Store (ODS): Near-real-time data for operational reporting

Data Mart: Subset of DW focused on specific business unit (Sales, Finance, HR)

Cloud Data Warehouse: Fully managed, scalable cloud service (Snowflake, BigQuery, Redshift)

Lecture 58: The Four Characteristics
1. Subject-Oriented
Data warehouses organize data around business subjects (customers, products, orders) rather than around applications or transactions.

Traditional Database Approach:

-- Application-centric: Tables per application
order_processing_db.orders
inventory_system_db.products
crm_system_db.customers
-- Each system has its own structure

Data Warehouse Approach:

-- Subject-centric: Organized by business concept
dim_customer -- ALL customer data
dim_product -- ALL product data
fact_sales -- ALL sales transactions
-- Integrated view across all systems

Example: Customer subject includes data from CRM, orders, support tickets, marketing campaigns---all in one place.

2. Integrated
Data from multiple sources is transformed into a consistent format with standardized naming, data types, and business rules.

Integration Challenges & Solutions:

Challenge Source Data Integrated DW

Gender codes M/F, Male/Female, 1/0 Standardized: M/F

Date formats MM/DD/YYYY, DD-MM-YY ISO: YYYY-MM-DD

Currency $100, 100 USD, €85 Normalized to USD

Product IDs SKU-123, PROD_123, P123 Unique surrogate key
3. Time-Variant
Data warehouses maintain historical data over long periods (5-10 years typical) to support trend analysis.

Key Concepts:

Time Dimension: Every fact table has a date/time reference

Slowly Changing Dimensions (SCD): Track how dimension attributes change over time

Historical Snapshots: Store data as it was at different points in time

Effective Dating: Records have start_date and end_date to track validity periods

Example: SCD Type 2 - Tracking Product Price Changes

product_key | product_id | product_name | price | effective_date | end_date
------------|------------|--------------|-------|----------------|----------
1 | PROD-100 | Widget | 9.99 | 2023-01-01 | 2023-06-30
2 | PROD-100 | Widget | 12.99 | 2023-07-01 | 9999-12-31

-- This allows us to answer: "What was the price on May 15, 2023?"

4. Non-Volatile
Once data is loaded into the data warehouse, it is not updated or deleted---only inserted. This ensures historical accuracy and auditability.

OLTP Database (Volatile):

UPDATE products SET price = 12.99 WHERE product_id = 'PROD-100';
-- Old price is lost forever!

Data Warehouse (Non-Volatile):

-- Close old record
UPDATE dim_product SET end_date = '2023-06-30'
WHERE product_key = 1;

-- Insert new record
INSERT INTO dim_product VALUES
(2, 'PROD-100', 'Widget', 12.99, '2023-07-01', '9999-12-31');

-- Both prices are preserved!

Benefits of Non-Volatility
Audit trail for compliance and regulatory reporting

Ability to recreate any historical report exactly as it was

Root cause analysis: "What was different then vs now?"

Predictive modeling requires stable historical data

Real-World Example: Financial Reporting
A CFO needs to reproduce the exact revenue report from Q1 2022 for an audit. Because the data warehouse is non-volatile, the data hasn't changed, and the report can be regenerated accurately.

While both data warehouses and databases store data, they serve fundamentally different purposes and are optimized for different workloads.

Example Scenario: E-Commerce Company
Operational Database (OLTP):

-- When customer clicks 'Buy Now'
BEGIN TRANSACTION;

INSERT INTO orders (customer_id, total) VALUES (12345, 99.99);
INSERT INTO order_items (order_id, product_id, qty) VALUES (789, 'PROD-100', 2);
UPDATE inventory SET quantity = quantity - 2 WHERE product_id = 'PROD-100';
UPDATE customers SET last_order_date = NOW() WHERE customer_id = 12345;

COMMIT;
-- Must complete in < 100ms!

Data Warehouse (OLAP):

-- Executive dashboard: "What are our top products this quarter?"
SELECT
p.product_name,
p.category,
SUM(f.quantity) as units_sold,
SUM(f.sales_amount) as revenue,
AVG(f.profit_margin) as avg_margin
FROM fact_sales f
JOIN dim_product p ON f.product_key = p.product_key
JOIN dim_date d ON f.date_key = d.date_key
WHERE d.year = 2024 AND d.quarter = 1
GROUP BY p.product_name, p.category
ORDER BY revenue DESC
LIMIT 10;
-- Scans millions of rows, takes 2-3 seconds

Why You Need Both
Separation of Concerns: Don't slow down operations with heavy analytics

Optimized Performance: Each system optimized for its specific workload

Data Protection: Analysts can't accidentally corrupt operational data

Scalability: Scale each system independently based on needs

Historical Analysis: DW keeps history; OLTP keeps current state

Common Anti-Pattern: Using OLTP for Analytics
⚠️ WARNING: Running complex analytical queries on production databases can:

Slow down customer-facing applications

Lock tables and cause timeouts

Consume resources needed for transactions

Lead to incorrect results due to changing data

Result in downtime during peak hours

Lecture 60: Data Warehouse vs Data Lake vs Lakehouse
The evolution of data storage has given us three major paradigms. Understanding when to use each is critical for modern data architecture.

Evolution & Comparison
{width="6.5in" height="4.178571741032371in"}

Data Warehouse
Definition: Centralized repository of integrated data from multiple sources, optimized for analysis.

Key Characteristics:

Schema: Schema-on-write (define before loading)

Data Type: Structured, curated data

Format: Proprietary or columnar (Parquet in cloud DW)

Cost: Higher per TB (compute + storage bundled)

Performance: Optimized for SQL queries

Use Cases: BI reporting, dashboards, KPI tracking

Tools: Snowflake, BigQuery, Redshift, Synapse

Data Lake
Definition: Vast pool of raw data stored in native format until needed, typically on object storage (S3, ADLS, GCS).

Key Characteristics:

Schema: Schema-on-read (define when querying)

Data Type: Structured, semi-structured, unstructured

Format: Any format (CSV, JSON, Parquet, images, videos)

Cost: Very low per TB (object storage prices)

Performance: Slower queries, requires processing engines

Use Cases: ML training, data science, exploratory analysis

Tools: S3 + Spark, Azure Data Lake + Databricks

Lakehouse
Definition: Hybrid architecture combining the flexibility of data lakes with the structure and performance of data warehouses.

Key Characteristics:

Schema: Both schema-on-write AND schema-on-read

Data Type: All types, with ACID guarantees

Format: Open table formats (Delta Lake, Iceberg, Hudi)

Cost: Low storage + pay-per-query compute

Performance: Near data warehouse performance

Use Cases: Unified analytics + ML, streaming + batch

Tools: Databricks, Dremio, Starburst

When to Use Each
Use Case Best Choice Reason

Standard BI reporting Data Warehouse Optimized for SQL, fast dashboards

Machine learning on raw data Data Lake Flexible schema, any data type

Real-time analytics + ML Lakehouse Unified platform, ACID on lake
Real-World Example: Netflix Architecture
Netflix uses a combination of all three:

Data Warehouse (Redshift/Teradata): User engagement metrics, subscription reporting

Data Lake (S3): Raw viewing logs, A/B test data, content metadata

Lakehouse (Iceberg on S3): Unified analytics for personalization algorithms

The "Data Swamp" Problem
⚠️ Data Lake Warning: Without proper governance, data lakes become "data swamps"---repositories of unusable data with no metadata, quality controls, or documentation.

Lakehouse architectures solve this by adding:

ACID transactions for data integrity

Schema enforcement and evolution

Time travel and versioning

Fine-grained security and access control

Unified metadata catalog

Cost Comparison Example
For 100 TB of data with moderate query workload:

Data Lake (S3): ~$2,300/month (storage only)

Data Warehouse (Snowflake): ~$15,000/month (storage + compute)

Lakehouse (Databricks): ~$6,000/month (storage + serverless compute)

Lecture 61: OLTP vs OLAP - Fundamental Differences
Understanding the distinction between OLTP and OLAP is foundational to data engineering. These represent two fundamentally different approaches to working with data.

Visual Comparison
{width="6.0in" height="4.0in"}

OLTP: Online Transaction Processing
Definition: Systems designed to manage transaction-oriented applications with emphasis on data integrity and high concurrency.

Characteristics:

Primary Goal: Capture and store data from business transactions

Data Operations: INSERT, UPDATE, DELETE (write-heavy)

Query Complexity: Simple queries on small datasets

Response Time: Milliseconds (< 100ms typical)

Concurrency: Thousands of simultaneous users

Data Volume: Current, operational data (GB to low TB)

Database Design: Highly normalized (3NF) to reduce redundancy

Indexing: B-tree indexes on primary/foreign keys

Backup Frequency: Continuous (point-in-time recovery needed)

OLAP: Online Analytical Processing
Definition: Systems designed for complex queries and analysis of large datasets to support business intelligence and decision-making.

Characteristics:

Primary Goal: Analyze data for business insights

Data Operations: SELECT (read-heavy, minimal writes)

Query Complexity: Complex aggregations, joins across large tables

Response Time: Seconds to minutes acceptable

Concurrency: Dozens to hundreds of users

Data Volume: Historical data (TB to PB)

Database Design: Denormalized (Star/Snowflake schema)

Indexing: Bitmap indexes, columnar storage, partitioning

Backup Frequency: Daily or weekly (point-in-time less critical)

Technical Architecture Differences
Component OLTP OLAP

Storage Row-based Columnar

Processing Single-node or simple replication MPP (Massively Parallel Processing)

Optimization Transaction throughput Query throughput

Caching Hot data in memory Aggregate pre-computation

Partitioning Range/hash by key Time-based (daily/monthly)

Compression Minimal Aggressive (10-20x reduction)
Query Pattern Examples
OLTP Query - Customer Order:

-- Fetch single customer's current cart
SELECT
c.cart_id,
c.product_id,
p.product_name,
c.quantity,
p.price * c.quantity AS subtotal
FROM cart_items c
JOIN products p ON c.product_id = p.product_id
WHERE c.customer_id = 12345 AND c.status = 'active';

-- Returns in < 10ms
-- Accesses ~10 rows total

OLAP Query - Sales Analysis:

-- Analyze sales trends by region and product category
SELECT
d.year,
d.month,
c.region,
p.category,
COUNT(DISTINCT f.order_id) AS total_orders,
SUM(f.quantity) AS units_sold,
SUM(f.sales_amount) AS revenue,
SUM(f.sales_amount) / COUNT(DISTINCT f.order_id) AS avg_order_value
FROM fact_sales f
JOIN dim_date d ON f.date_key = d.date_key
JOIN dim_customer c ON f.customer_key = c.customer_key
JOIN dim_product p ON f.product_key = p.product_key
WHERE d.year BETWEEN 2022 AND 2024
GROUP BY d.year, d.month, c.region, p.category
ORDER BY d.year DESC, revenue DESC;

-- Returns in 2-5 seconds
-- Scans 50M+ rows, returns 10K aggregated rows

Why Separation Matters
Resource Isolation: Analytics don't impact operational performance

Optimized Performance: Each system tuned for its workload

Security: Analysts can't modify production data

Data Transformation: OLAP can denormalize without affecting OLTP

Backup Strategy: Different RTO/RPO requirements

Scaling Strategy: Scale each independently

Detailed Example: Airline Reservation System
Let's examine how an airline uses both OLTP and OLAP systems:

OLTP: Booking a Flight

-- User books seat 15A on flight UA123
BEGIN TRANSACTION;

-- Check seat availability
SELECT seat_status FROM seats
WHERE flight_id = 'UA123' AND seat_number = '15A' FOR UPDATE;

-- Reserve the seat
UPDATE seats SET seat_status = 'RESERVED', passenger_id = 789
WHERE flight_id = 'UA123' AND seat_number = '15A';

-- Create reservation
INSERT INTO reservations (passenger_id, flight_id, seat_number, price)
VALUES (789, 'UA123', '15A', 450.00);

-- Process payment
INSERT INTO payments (reservation_id, amount, status)
VALUES (LAST_INSERT_ID(), 450.00, 'COMPLETED');

COMMIT;

-- Must complete in < 1 second to avoid double-booking

OLAP: Route Profitability Analysis

-- Analyze route profitability by season
SELECT
r.origin_city,
r.destination_city,
d.season,
COUNT(DISTINCT f.booking_id) AS total_bookings,
AVG(f.ticket_price) AS avg_ticket_price,
SUM(f.ticket_price) AS total_revenue,
AVG(f.load_factor) AS avg_load_factor,
SUM(f.fuel_cost + f.crew_cost + f.maintenance_cost) AS total_costs,
SUM(f.ticket_price) - SUM(f.fuel_cost + f.crew_cost + f.maintenance_cost) AS profit
FROM fact_flights f
JOIN dim_route r ON f.route_key = r.route_key
JOIN dim_date d ON f.date_key = d.date_key
WHERE d.year = 2024
GROUP BY r.origin_city, r.destination_city, d.season
HAVING COUNT(DISTINCT f.booking_id) > 100
ORDER BY profit DESC;

-- Scans millions of flight records
-- Used for strategic decisions: which routes to expand/cancel

Both are essential and complementary, not competing

Lecture 64: Data Warehouse Design Principles
Successful data warehouse design follows proven principles that ensure scalability, performance, and maintainability.

1. Kimball's Dimensional Modeling
Ralph Kimball's dimensional modeling approach uses star schemas with fact and dimension tables.

Core Concepts:

Fact Tables: Contain measurable, quantitative data (sales, clicks, transactions)

Dimension Tables: Contain descriptive attributes (who, what, when, where, why)

Star Schema: Fact table at center, surrounded by dimension tables

Conformed Dimensions: Shared dimensions across data marts for consistency

Star Schema Example
{width="5.4680664916885386e-6in" height="4.374453193350831e-6in"}

2. Inmon's Corporate Information Factory
Bill Inmon's approach emphasizes building an enterprise-wide, integrated data warehouse first.

Top-Down Approach: Build enterprise DW first, then create data marts

3NF Normalized: Store data in third normal form in the DW

Single Source of Truth: All data marts derive from the central DW

Enterprise Focus: Think holistically across the organization

3. Core Design Principles
1. Business-Driven DesignStart with business questions, not technical architecture

2. Grain DefinitionClearly define the level of detail for each fact table

3. Slowly Changing DimensionsChoose appropriate SCD type (Type 1, 2, or 3)

4. Surrogate KeysUse auto-generated keys instead of natural business keys

5. Conformed DimensionsEnsure consistency across the enterprise

6. Aggregation StrategyPre-compute common aggregates for performance

7. Partitioning StrategyPartition large tables by date for manageability

8. Index StrategyCreate indexes based on query patterns

4. Grain Definition Example
-- Bad: Mixed grain
-- This table has BOTH daily and monthly data - inconsistent!
CREATE TABLE fact_sales_bad (
date DATE,
product_id INT,
daily_sales DECIMAL,
monthly_sales DECIMAL -- DON'T DO THIS!
);

-- Good: Single grain
-- One row per transaction
CREATE TABLE fact_sales (
transaction_id INT,
date_key INT,
product_key INT,
customer_key INT,
quantity INT,
unit_price DECIMAL,
sales_amount DECIMAL
);

-- Aggregate in queries or materialized views
CREATE MATERIALIZED VIEW daily_sales AS
SELECT date_key, product_key, SUM(sales_amount)
FROM fact_sales
GROUP BY date_key, product_key;

5. Slowly Changing Dimension Types
Choose the appropriate SCD type based on business requirements:

Type Description Use Case History

Type 1 Overwrite old value Non-critical attributes (phone, address) No

Type 2 Add new row with dates Track all changes (price, status) Yes

Type 3 Add new column Track one previous value Limited
6. Naming Conventions
Consistent naming makes the warehouse intuitive:

Fact tables: fact_<subject> (fact_sales, fact_orders)

Dimension tables: dim_<subject> (dim_customer, dim_product)

Keys: <subject>_key (customer_key, product_key)

Dates: <subject>_date (order_date, ship_date)

Amounts: <subject>_amount (sales_amount, discount_amount)

Lecture 65: Common Pitfalls in DW Design
Learning from common mistakes can save months of rework and millions in costs.

Pitfall 1: No Clear Business Requirements
❌ Problem: Building a data warehouse without understanding what questions it needs to answer.

Result: Expensive warehouse that no one uses because it doesn't answer business questions.

✓ Solution: Start with business questions. Conduct stakeholder interviews. Create a requirements document.

Pitfall 2: Wrong Grain Definition
❌ Problem: Mixing different levels of detail in the same fact table.

-- BAD: Mixing transaction and summary data
transaction_id | product_id | transaction_amt | monthly_total
123 | P1 | 100 | 50000 -- Inconsistent!
124 | P2 | 200 | 75000

✓ Solution: One grain per fact table. Use separate tables or aggregates for different grain levels.

Pitfall 3: Not Using Surrogate Keys
❌ Problem: Using natural business keys (customer_id, product_code) as primary keys.

Difficult to track history (SCD Type 2 becomes complex)

Can't handle source system key changes

Performance issues with string/composite keys

Difficult to integrate data from multiple sources

✓ Solution: Use auto-incrementing integer surrogate keys. Keep natural keys as attributes.

Pitfall 4: Over-Normalization
❌ Problem: Applying OLTP normalization rules to OLAP warehouses (snowflake schema everywhere).

Result: Complex queries with 10+ joins, slow performance, confused analysts.

✓ Solution: Use star schemas. Denormalize dimensions. Prioritize query simplicity over storage savings.

Pitfall 5: Ignoring Data Quality
❌ Problem: "Garbage in, garbage out." Loading dirty data without validation.

Duplicate records

Missing required fields

Invalid dates (9999-12-31, 1900-01-01)

Inconsistent formats

Orphaned foreign keys

✓ Solution: Implement data quality checks in ETL. Create error tables. Monitor data quality metrics.

Pitfall 6: No Documentation
❌ Problem: No metadata, data dictionary, or lineage tracking.

Result: Analysts don't know what data means. "Where does revenue come from? What's the difference between gross_sales and net_sales?"

✓ Solution: Maintain data dictionary. Document business logic. Use tools like Alation, Collibra, or dbt docs.

Pitfall 7: Monolithic Architecture
❌ Problem: One giant warehouse for everything with no separation.

Result: Changes to one department's data break reports for everyone. Long deployment cycles.

✓ Solution: Use data marts by subject area. Implement data mesh principles for large organizations.

Pitfall 8: Neglecting Performance
❌ Problem: No indexing, partitioning, or aggregation strategy.

Dashboards take minutes to load

Queries time out

Month-end reports take days to run

Users complain and stop using the warehouse

✓ Solution: Partition large tables. Create appropriate indexes. Build aggregate tables. Use materialized views.

Pitfall 9: No Testing Strategy
❌ Problem: Deploying ETL changes without testing.

Result: Incorrect business metrics, broken dashboards, loss of trust.

✓ Solution: Implement data testing (Great Expectations, dbt tests). Validate row counts, sums, and business rules.

Pitfall 10: Technology Before Strategy
❌ Problem: Choosing Snowflake/BigQuery/Redshift before understanding requirements.

Result: Expensive tool that doesn't fit the use case.

✓ Solution: Define requirements first. Then evaluate technologies. Consider TCO, not just license costs.

Best Practices Checklist
 Clear business requirements documented

 Star schema with proper grain definition

 Surrogate keys for all dimensions

 Data quality checks in ETL

 Comprehensive documentation and metadata

 Performance optimization (indexes, partitions, aggregates)

 Automated testing framework

 Incremental loads for large tables

 Monitoring and alerting

 Disaster recovery plan
