# 3.1 Perform Data Loading and Unloading

## A. File Formats

### Core concept
A **file format object** is a named, schema-level database object that tells Snowflake how to parse a data file — delimiter, compression, header handling, null representation, date/time parsing, etc. You can either declare format options **inline** in a `COPY INTO`/stage/table statement, or create a **named file format** object and reference it. Named formats are optional but recommended for reuse and consistency.

### Supported types
| Type | Load | Unload | Notes |
|---|---|---|---|
| CSV (delimited) | ✅ | ✅ | Despite the name, any single-byte character can be the field delimiter, not just a comma |
| JSON | ✅ | ✅ | Semi-structured; unload always produces **NDJSON** (newline-delimited JSON), never a comma-separated array |
| AVRO | ✅ | ❌ (cannot unload) | Semi-structured, binary |
| ORC | ✅ | ❌ (cannot unload) | Semi-structured, columnar |
| PARQUET | ✅ | ✅ | Columnar; supports `USE_LOGICAL_TYPE` and a **vectorized scanner** (`USE_VECTORIZED_SCANNER`) for faster loads |
| XML | ✅ | ❌ (cannot unload) | Each top-level element (matching start/end tag) becomes one row |

**Semi-structured loading rule:** JSON/Avro/ORC/Parquet — each top-level, complete object becomes one row. Data can be loaded directly into a `VARIANT` column without predefining a schema.

### Precedence order (critical exam point)
When file format or copy options are set in more than one place, Snowflake resolves them using this precedence (highest wins), and settings are **not cumulative** — the higher-precedence location's value completely overrides a lower one for the *same* option:
1. `COPY INTO <table>` statement (highest)
2. Stage definition
3. Table definition (lowest)

⚠️ **Copy options** (like `ON_ERROR`, `PURGE`) behave differently — those set in different places are treated as **cumulative**, unlike file format options which override.

⚠️ **Do not** specify copy options on `CREATE STAGE`, `ALTER STAGE`, `CREATE TABLE`, or `ALTER TABLE` — Snowflake recommends specifying them only on `COPY INTO <table>`.

### Gotchas / Edge Cases
- **You cannot `ALTER` the `TYPE` property** of an existing file format. To change the type, you must recreate it.
- **`CREATE OR REPLACE FILE FORMAT` breaks external table linkage.** An external table references a file format by a hidden internal ID, not by name. `CREATE OR REPLACE` actually drops and recreates the object with a new hidden ID — so any external table using the old file format silently loses its association. Fix: recreate the affected external table(s) with `CREATE OR REPLACE EXTERNAL TABLE` (you can get the DDL via `GET_DDL`).
- **Conflicting option values in one statement cause an error** (e.g., specifying `FIELD_DELIMITER` twice with different values in the same statement).
- `FORMAT_NAME` and inline `TYPE = ...` are **mutually exclusive** — using both in the same `COPY` command can cause unexpected behavior.
- `USE_VECTORIZED_SCANNER = TRUE` for Parquet forces `BINARY_AS_TEXT = FALSE` and always uses `USE_LOGICAL_TYPE = TRUE` — it changes other settings implicitly.

### Exam traps
- "Which file format cannot be used to unload data?" → AVRO, ORC, XML (memorize these three — the "load only" set).
- A question implying you changed a file format's `TYPE` via `ALTER FILE FORMAT` → **not possible**, must recreate.
- A scenario where an external table "stopped working" after a `CREATE OR REPLACE FILE FORMAT` → the hidden-ID breakage is the answer.
- Confusing **copy options are cumulative** vs **file format options override** — expect a question flipping this.

## B. Stages

### The big picture
A **stage** is a pointer to a storage location (internal to Snowflake or external in a cloud provider) used as a staging area during load/unload. Two families:

### Internal stages (Snowflake-managed storage)
| Type | Reference | Key facts |
|---|---|---|
| **User stage** | `@~` | Auto-created per user; not alterable/droppable; **cannot** set file format options at the stage level — must specify in `COPY INTO`; bad choice if multiple users need the files, or if the user lacks `INSERT` on the target table |
| **Table stage** | `@%table_name` | Auto-created per table, same name as table; good when only one table needs the data but multiple users need access; **not supported for Apache Iceberg™ tables**; cannot be altered/dropped independently of the table |
| **Named stage** | `@stage_name` | Explicitly created object; most flexible — supports file formats, directory tables, granting access to other roles without exposing credentials |

### External stages
Reference cloud storage: **Amazon S3**, **Google Cloud Storage**, or **Microsoft Azure Blob/ADLS Gen2**. Require either:
- A **storage integration** (recommended — no credentials embedded in the stage), or
- Direct `CREDENTIALS = (...)` (legacy, less secure — credentials live in the stage object).

External stages provide **read/write access** to files but are otherwise "virtual" — Snowflake does not physically move/store the files until a `COPY INTO <table>` is run.

### Temporary stage behavior — a key asymmetry
- **Dropping a temporary EXTERNAL stage**: only the stage object is removed; the actual data files remain untouched in cloud storage.
- **Dropping a temporary INTERNAL stage**: all files in it are **purged from Snowflake immediately**, regardless of load status, and **cannot be recovered**. (This exists to prevent temp internal stages from silently accruing storage charges.)
  - ⚠️ Best practice: keep external copies of any data staged in a temporary internal stage.

### `CREATE OR REPLACE STAGE` — hidden side effects (very testable)
Recreating a stage:
1. **Drops the existing directory table** for that stage (if any exists). If you recreate the stage *with* a directory table, it starts **empty**.
2. **Breaks the association with any external table** that references the stage (same hidden-ID mechanism as file formats) — you must recreate those external tables too.

### Directory tables
A **directory table** is not a standalone object — it's an implicit metadata layer on a stage, conceptually similar to an external table (stores file-level metadata: size, last-modified timestamp, file URL, etc.). It has **no grantable privileges of its own** — access is inherited from privileges on the parent stage (READ/WRITE/USAGE).

- Enable at creation: `CREATE STAGE ... DIRECTORY = (ENABLE = TRUE)`, or later via `ALTER STAGE ... SET DIRECTORY = (ENABLE = TRUE)`.
- **Refresh mechanisms**:
  - **Manual**: `ALTER STAGE <name> REFRESH` (optionally scoped to a subpath — recommended for large stages to reduce the list operation cost).
  - **Automatic**: driven by cloud event-notification services (S3 SQS/SNS, Azure Event Grid, GCS Pub/Sub) — only supported for **external** stages fully across all clouds.
  - **Internal stage auto-refresh**: Only available in **preview**, and only for Snowflake accounts hosted on **AWS**. Azure/GCP-hosted accounts cannot auto-refresh directory tables on internal stages — manual refresh only.
- `REFRESH_ON_CREATE` (default TRUE) automatically does one refresh right after stage creation. Recommendation: set to `FALSE` if the storage location already has close to a million files, then refresh incrementally by subpath.
- **Billing**: automatic refresh overhead is billed as **Snowpipe charges** (visible in `PIPE_USAGE_HISTORY`) because the underlying mechanism is the same event-notification/Snowpipe infrastructure. Manual refresh incurs a small **cloud services** charge and does **not** show up in `PIPE_USAGE_HISTORY`.
- Query the file list using `SELECT * FROM DIRECTORY(@stage_name)`.
- Only `OBJECT_DELETE`/`OBJECT_FINALIZE` (GCS) or `BlobCreated`/`BlobDeleted` (Azure) events trigger refreshes — renaming a file/folder does **not** trigger a refresh.
- Replication caveat: directory tables **cannot be disabled** once a stage has been part of a replication/failover group; a refresh will **fail** if any tracked file exceeds 5 GB.

### Encryption — client-side vs. server-side (a classic exam trap area)
**General principle:** all data at rest in Snowflake is always encrypted; TLS protects data in transit. The stage-level `ENCRYPTION` setting controls the encryption applied to the *staged files themselves*.

**Internal stages** — set via `ENCRYPTION = (TYPE = 'SNOWFLAKE_SSE' | 'SNOWFLAKE_FULL')`, decided **at creation time and cannot be changed afterward**:
| Type | Behavior |
|---|---|
| `SNOWFLAKE_FULL` (default) | **Client-side AND server-side** encryption. Files are encrypted by the client during `PUT`, using a 128-bit key by default (configurable to 256-bit via `CLIENT_ENCRYPTION_KEY_SIZE`), then also AES-256 server-side encrypted. Because it's client-side encrypted, files are **unreadable via pre-signed/file/scoped URLs and external tools** — this breaks unstructured-data access use cases. |
| `SNOWFLAKE_SSE` | **Server-side only.** Encryption happens when the file lands in the stage; no client-side layer. Required if you want to use pre-signed URLs / scoped URLs to read staged files directly (e.g., for unstructured data access) or from external tools. Does **not** support Tri-Secret Secure. |

⚠️ **Exam trap:** "Which encryption type supports Tri-Secret Secure for internal stages?" → **`SNOWFLAKE_FULL`**, not `SNOWFLAKE_SSE`.
⚠️ **Exam trap:** "Which type enables client-side encryption for a directory table / internal stage?" → **`SNOWFLAKE_FULL`**.

**External stages** — the `ENCRYPTION` clause varies by cloud:
| Cloud | Options |
|---|---|
| AWS (S3) | `AWS_CSE` (client-side, requires `MASTER_KEY`), `AWS_SSE_S3` (server-side, no extra config), `AWS_SSE_KMS` (server-side, optional `KMS_KEY_ID`), `NONE` |
| GCS | `GCS_SSE_KMS` (optional `KMS_KEY_ID`) |
| Azure | `AZURE_CSE` (client-side, requires `MASTER_KEY`), `NONE` |

⚠️ Snowflake's official recommendation is to use **client-side encryption for data in external stages** (since Snowflake doesn't control that storage until the data is loaded); for internal stages, Snowflake automatically encrypts data client-side by default.

### Exam traps for stages
- Confusing which internal stage type is auto-created vs. must be explicitly created (only **named** stages require `CREATE STAGE`).
- Table stage cannot be used for Iceberg tables — a scenario question about Iceberg + table stage is designed to trip you up.
- "I recreated my file format / stage and now my external table query fails" → hidden-ID association break.
- Directory table auto-refresh on an **internal stage on Azure/GCP** → **not supported**, must be manual.
- Assuming `SNOWFLAKE_SSE` is "more secure" because "server" sounds authoritative — it's actually the *simpler* single-layer option; `SNOWFLAKE_FULL` is the default and has both layers but blocks pre-signed URL access.

## C. COPY INTO Command

### Two directions
- `COPY INTO <table>` — load data from a stage into a table.
- `COPY INTO <location>` — unload data from a table/query into a stage.

### Key copy options (loading)
| Option | Purpose | Gotcha |
|---|---|---|
| `ON_ERROR` | Error-handling strategy (see table below) | Default is `ABORT_STATEMENT` for bulk `COPY`; Snowpipe's **default is `SKIP_FILE`** — a very common trap |
| `VALIDATION_MODE` | `RETURN_n_ROWS`, `RETURN_ERRORS`, `RETURN_ALL_ERRORS` — tests the files without loading | **Cannot** be combined with `MATCH_BY_COLUMN_NAME` or with statements that transform data via a query |
| `SIZE_LIMIT` | Max bytes to load in one statement — applies across the whole file set, not per file; the file that crosses the threshold is still fully loaded before stopping | — |
| `PURGE` | Deletes files from the stage automatically after a successful load | Files that fail to load with errors are **not** purged even if `PURGE = TRUE` |
| `FORCE` | Reloads files even if they were already loaded and unchanged | Can duplicate data — use with care |
| `MATCH_BY_COLUMN_NAME` | `CASE_SENSITIVE` / `CASE_INSENSITIVE` / `NONE` — maps semi-structured/staged columns to target table columns by name instead of position | **Cannot be combined with a `SELECT` transformation** in the same `COPY` statement (BCR-enforced); not supported for XML; cannot combine with `VALIDATION_MODE` |
| `INCLUDE_METADATA` | Maps `METADATA$FILENAME`, `METADATA$FILE_ROW_NUMBER`, `METADATA$FILE_CONTENT_KEY`, `METADATA$START_SCAN_TIME` to target columns | Must be used **together with** `MATCH_BY_COLUMN_NAME` |
| `TRUNCATECOLUMNS` / `ENFORCE_LENGTH` | Opposite behaviors for handling over-length strings | Only specify one — they're functional opposites, and combining is redundant/confusing |
| `RETURN_FAILED_ONLY` | Return only rows/files that failed | Handy for automated error-monitoring pipelines |

### `ON_ERROR` values (memorize exactly)
| Value | Behavior |
|---|---|
| `CONTINUE` | Skip only the erroring **rows**; load everything else in every file |
| `SKIP_FILE` | Skip the **entire file** if any error is found in it (default for Snowpipe) |
| `SKIP_FILE_<num>` | Skip the file only if the error-row count reaches/exceeds `<num>` |
| `'SKIP_FILE_<num>%'` | Skip the file if the **percentage** of error rows reaches/exceeds `<num>%` |
| `ABORT_STATEMENT` | Stop the entire load on the first error (default for bulk `COPY INTO <table>`) |

⚠️ `SKIP_FILE` buffers the **whole file** in memory regardless of where the error is — it's slower than `CONTINUE` or `ABORT_STATEMENT`. For files with no logical row boundary meaning (e.g., machine-generated at intervals), prefer `CONTINUE`.

### File selection
- `FILES = (...)` — explicit list of file names.
- `PATTERN = '<regex>'` — regex match against file paths.
- ⚠️ **Don't combine `FILES` and `PATTERN`** — if both given, only `FILES` is honored.
- For Snowpipe specifically, Snowflake recommends using **cloud-native event filtering** (S3 object key filtering, Event Grid subscription filters) over `PATTERN`, to reduce cost/latency/noise.

### Data transformation during load
- Supported: column reordering, column omission, casts (`TO_NUMBER`, `TO_TIMESTAMP`, etc.), via a `SELECT` inside the `FROM` clause of `COPY INTO`.
- **Not supported in a transforming COPY**: `WHERE` clause filtering, `DISTINCT`, use on clustered tables reliably, combining with `MATCH_BY_COLUMN_NAME`.
- The number/order of columns in the file does **not** need to match the table.
- Omitted target columns are auto-populated (e.g., with defaults/NULL) — you don't need to explicitly `NULL` them in the SELECT.

### Load metadata & deduplication (crucial exam area)
- Snowflake **prevents reloading a file with the same name**, even if its content changed (different eTag/checksum) — unless you use `FORCE = TRUE` or the file name changes.
- **Load history retention differs by mechanism** (see the Snowpipe section below for the full comparison): bulk `COPY` load metadata lives in the **target table** for **64 days**; Snowpipe load metadata lives in the **pipe object** for **14 days**.
- `TRUNCATE TABLE` does **not** clear Snowpipe's file-loading metadata — so re-adding a previously-loaded file name after a truncate still won't reload it unless you recreate the pipe.

### Validating & troubleshooting loads
- `VALIDATION_MODE` — pre-check before loading (doesn't support transforming COPY statements).
- `VALIDATE()` table function — post-check: pass a `query_id` (or `_last`) to see **all** errors from a past `COPY INTO <table>` execution, not just the first. Returns **no results** if the original `COPY` used `ON_ERROR = ABORT_STATEMENT` (the default) since it stops on the very first error and won't have accumulated more.
- `COPY_HISTORY` — query load activity/status (`LOADED`, `PARTIALLY_LOADED`, `LOAD_FAILED`) including `FIRST_ERROR_MESSAGE` (only the *first* error is shown even if multiple exist).

### PUT / GET essentials (client-side staging commands)
- `PUT` uploads local files **only to internal stages** (not external — for external stages, use the cloud provider's own upload tools, or Snowpark's `FileOperation.put`, which *does* support external stages).
- Options: `PARALLEL` (1–99 threads, default varies by driver), `AUTO_COMPRESS` (TRUE by default — gzips uncompressed files), `SOURCE_COMPRESSION`, `OVERWRITE`.
- ⚠️ A "successful" `PUT`/`GET` query status in Query History means Snowflake **authorized** the transfer, not that the file transfer itself definitely completed — actual success/failure of the client-side transfer is reported separately in the command output.
- To overwrite a staged file without `OVERWRITE=TRUE`, you must change the file content (so the checksum differs) — otherwise Snowflake treats it as already staged.
- Recommended file size for parallel load efficiency: **100–250 MB compressed** per file.

### Exam traps
- Assuming `ON_ERROR` default is the same for bulk load and Snowpipe — **it is not** (`ABORT_STATEMENT` vs `SKIP_FILE`).
- Thinking `MATCH_BY_COLUMN_NAME` can be freely combined with a transforming `SELECT` — it **cannot**.
- Thinking `VALIDATE()` will return errors after an `ABORT_STATEMENT` load — it **won't**, because the load stopped before accumulating a full error set.
- Believing `PURGE` deletes files even when they failed to load — it does **not**.
- Believing `SIZE_LIMIT` applies per-file — it applies to the **aggregate** of the file set.

# 3.2 Perform Automated Data Ingestion

## A. Snowpipe (continuous, file-based, serverless micro-batch loading)

### Core concept
Snowpipe wraps a single `COPY INTO <table>` statement inside a **pipe** object and executes it automatically in small batches ("micro-batches") as new files appear in a stage — typically loading within **minutes**, not on a fixed schedule.

### Compute model
- **Serverless** — Snowflake provides and auto-scales the compute; you never assign or size a warehouse for Snowpipe.
- ⚠️ **A resource monitor cannot cap Snowpipe spend**, because resource monitors attach to virtual warehouses you own, and Snowpipe uses Snowflake-managed compute. This is a frequently tested fact.
- Billed per-second based on actual usage; historically included a small per-file overhead fee, folded (per recent Snowflake changes) into a straightforward per-GB-ingested credit charge. Either way, the practical rule survives: **avoid a flood of tiny files** — target ~100–250 MB compressed.

### Two file-detection mechanisms
1. **Auto-ingest** (`AUTO_INGEST = TRUE`) — cloud event-notification driven:
   - AWS: SQS (via S3 event notifications, optionally through SNS)
   - Azure: Event Grid
   - GCP: Pub/Sub
2. **REST API** — your own client calls a public REST endpoint naming the pipe and a list of files; requires **key-pair authentication with a JWT** (signed via RSA public/private key pair).

### Load metadata comparison (bulk COPY vs. Snowpipe) — a top exam fact
| | Bulk `COPY INTO` | Snowpipe |
|---|---|---|
| Metadata location | Target **table** | The **pipe** object |
| Retention | **64 days** | **14 days** |
| Default `ON_ERROR` | `ABORT_STATEMENT` | `SKIP_FILE` |
| Compute | Your warehouse | Snowflake serverless |
| Dedup rule | Same filename ignored even if modified (different eTag) | Same rule |

### Gotchas
- **Recreating a pipe** (`CREATE OR REPLACE PIPE`) **drops its file-loading history**. If you then run `ALTER PIPE ... REFRESH`, previously-loaded files (still present in storage) can be **reloaded — duplicating data**.
- `ALTER PIPE ... REFRESH` only scans files **staged within the last 7 days**. For older backlogs, run a manual `COPY INTO <table>` first, *then* enable Snowpipe for new arrivals going forward (this avoids double-loading the historic files, since they never trigger an event notification).
- **Pausing a pipe**: incoming event notifications are retained for only **14 days** while paused. Beyond that, the pipe is "stale." Resuming a stale pipe silently may skip old notifications (Snowflake processes them best-effort, no guarantee) — you must call `SYSTEM$PIPE_FORCE_RESUME` with `STALENESS_CHECK_OVERRIDE` to explicitly acknowledge this.
- Modifying the **URL** of a stage referenced by an active auto-ingest pipe can **break the pipe silently** (the cloud messaging trigger stops functioning) — you must recreate the pipe after such a change.
- Snowpipe ignores a re-staged file with the same name even if its **content changed** — you must `CREATE OR REPLACE PIPE` to force a reload of modified files.
- Never run bulk `COPY` and Snowpipe against the same files/target table concurrently — their load histories are tracked **separately**, so duplicate loads are possible.
- Transformations in a pipe's `COPY` statement support only simple `SELECT`s (column reorder/omit/cast) — **no `WHERE` filtering**.
- Pipe definitions are **not dynamic** — if you rename/drop the underlying stage or table, the pipe does not auto-update.

### Exam traps
- "Can I attach a resource monitor to control Snowpipe costs?" → **No.**
- "My Snowpipe recreated pipe reloaded old data — why?" → history reset + `ALTER PIPE REFRESH`.
- "What's the default `ON_ERROR` for Snowpipe vs. `COPY INTO`?" → `SKIP_FILE` vs `ABORT_STATEMENT`.
- "How long is Snowpipe's load metadata retained?" → **14 days** (vs 64 days for bulk load, in the table).

## B. Snowpipe Streaming (row-based, low-latency ingestion)

### Core concept
An entirely different ingestion path: applications push **rows directly** into a target table via an SDK (Java/Python/Node.js — sharing a Rust-based client core) or the REST API, **without staging files at all**. Data becomes queryable typically within seconds.

### Key properties
- **Exactly-once delivery** via **offset tokens**: your client application tracks the last committed offset and can safely resume/replay from there without duplicating data.
- **Ordered ingestion within a channel** — a channel commonly maps to one source partition (e.g., one Kafka topic-partition), enabling deterministic replay.
- Supports schema evolution (auto-adds new columns), pre-clustering at ingest, and writing into Apache Iceberg™ tables.
- Billing: throughput-based, credits per uncompressed GB ingested (**not** per-file — there are no files).
- Complements, does **not replace**, classic Snowpipe: use Snowpipe Streaming for continuous row-level/event-style data (IoT, CDC, clickstream); use classic Snowpipe/COPY for file-oriented sources.
- Under the hood, streaming ingestion can define a custom **pipe** (`COPY INTO ... FROM (SELECT ... FROM TABLE(DATA_SOURCE(TYPE => 'STREAMING')))`) if you need in-flight transformations or clustering — otherwise Snowflake auto-creates a default pipe per target table.

### Comparison table (a favorite scenario-question setup)
| | Snowpipe (classic) | Snowpipe Streaming |
|---|---|---|
| Ingest unit | Files | Individual rows |
| Latency | Minutes | Seconds (as low as ~5s) |
| Needs staging? | Yes (external/internal stage) | No |
| Dedup mechanism | Filename-based metadata | Offset tokens (exactly-once) |
| Typical source | Batch file drops | Kafka, application event streams, CDC |
| Billing basis | Compute + per-file overhead (historically) | Credits per GB ingested |

### Exam traps
- Confusing Snowpipe Streaming with "faster Snowpipe" — it's architecturally distinct (no files, no stage, no `COPY` required for basic use).
- Assuming Snowpipe Streaming *replaces* Snowpipe — the docs explicitly frame it as **complementary**.
- Forgetting that exactly-once semantics depend on the **client** tracking/replaying offsets correctly — Snowflake tracks committed offsets, but correct behavior on recovery is a shared responsibility.

## C. Streams (Change Data Capture)

### Core concept
A **stream** tracks DML changes (inserts/updates/deletes) to a source object between two transactional points in time, called the stream's **offset**. A stream stores **no actual data** — only metadata/offset pointers into the source object's change history (its "change tracking" versioning).

### Three types
| Type | Tracks | Supported on | Key trait |
|---|---|---|---|
| **Standard** (delta) | Inserts, updates, deletes (incl. truncates) | Tables, dynamic tables (as a *standard* stream only), views, directory tables | Full CDC |
| **Append-only** | Inserts **only** | Tables, views, directory tables — **not** dynamic tables | Ignores deletes/updates entirely — very performant for pure-append ELT; you can truncate the source right after consuming without extra overhead next read |
| **Insert-only** | Inserts **only** | **External tables** and externally-managed Iceberg tables | The *only* stream type valid on external tables |

⚠️ **Exam trap:** Don't confuse *append-only* (standard/table-based, inserts only) with *insert-only* (external-table-specific). They sound nearly identical but apply to different object types.

### Metadata columns added to every stream query result
- `METADATA$ACTION` — `INSERT` or `DELETE`
- `METADATA$ISUPDATE` — `TRUE` if the row change is part of an update (recorded internally as a paired DELETE + INSERT)
- `METADATA$ROW_ID` — a stable, immutable row identifier used to track a specific row across multiple changes

### Offset / staleness mechanics
- The stream's offset **advances only when consumed inside a DML transaction** (e.g., used as the source of an `INSERT`, `MERGE`, or `CREATE TABLE AS SELECT`) — a plain `SELECT` does **not** advance the offset.
- A stream becomes **stale** when its offset falls outside the source table's/view's **data retention period**. Once stale, unconsumed change history is permanently lost, and the stream must be **dropped and recreated** — there's no "un-stale" operation.
- If a table's retention is under 14 days and its stream hasn't been consumed, Snowflake **temporarily extends** the retention period (up to 14 days) purely to keep the stream from going stale — this costs extra storage.
- Recreating the underlying table (`CREATE OR REPLACE TABLE`) drops its history and therefore makes any stream on it **stale immediately**.
- Streams have **no Fail-safe and no Time Travel of their own** — if you drop a stream, its metadata is unrecoverable.
- `SYSTEM$STREAM_HAS_DATA('stream_name')` — cheaply checks whether a stream currently has unconsumed change data, without materializing/consuming it. Commonly used as a `WHEN` condition for triggered tasks.

### Other important limitations
- You **cannot** change `APPEND_ONLY`/`INSERT_ONLY`/the source object of an existing stream — you must drop and recreate.
- `COPY GRANTS` is **not supported** for streams; tagging is also unsupported.
- Best practice: **one stream per consumer.** Don't share a single stream across multiple downstream consumers/tables — since the *first* consumer to use it in a DML statement advances the offset for everyone, other consumers silently lose data.
- Streams on **views** require the underlying tables to be native Snowflake tables; supported query shapes are limited to projections, filters, `UNION ALL`, and inner/cross joins — no arbitrary SQL.
- For a data **share** consumer to create a stream on a shared table/secure view, the **provider** must have enabled `CHANGE_TRACKING = TRUE` on it first.
- Streams **on dynamic tables**: only the **standard** type is supported (not append-only). The underlying dynamic table must use **incremental** refresh — a dynamic table using **full** refresh has no incremental change history, so no stream is possible on it. After a dynamic table *reinitializes* (e.g., due to `CREATE OR REPLACE` upstream, a masking policy change, etc.), the next stream read can return an unusually large batch of changes, and previously-seen updates may appear as DELETE+INSERT pairs.

### Exam traps
- "Which stream type is valid on an external table?" → **insert-only** (not append-only).
- "A stream's offset didn't move after I ran a `SELECT * FROM my_stream`." → correct — offset only advances on **DML consumption**.
- "Can I use `APPEND_ONLY` streams on dynamic tables?" → **No.**
- "Multiple pipelines read the same stream — did we do that right?" → **No**, best practice is one stream per consumer.

## D. Tasks

### Core concept
A **task** executes a single SQL statement (or a call to a stored procedure) on a **schedule** or **trigger**. Tasks can be chained into a **task graph** (DAG) to build multi-step pipelines.

### Compute models
| Model | How it works |
|---|---|
| **User-managed** | You specify `WAREHOUSE = <name>` — you control size/scaling, and you're billed normal warehouse compute |
| **Serverless** | Omit `WAREHOUSE`; optionally set `USER_TASK_MANAGED_INITIAL_WAREHOUSE_SIZE` for the first few runs. Snowflake auto-right-sizes based on run history after that. Max size ≈ **XXLARGE**. If you need bigger, you must use a user-managed warehouse instead. |

⚠️ Serverless compute for tasks is historically billed at a premium multiplier (~1.5x) vs. equivalent user-managed warehouse compute — so very short/cheap tasks may favor serverless (avoiding idle-warehouse waste), while long-running heavy tasks may favor a right-sized dedicated warehouse.

### Scheduled vs. triggered tasks
- **Scheduled**: `SCHEDULE = 'N MINUTE'` (minimum: 1 minute) or `SCHEDULE = 'USING CRON <expr> <timezone>'`.
- **Triggered**: no `SCHEDULE`; instead a `WHEN` clause, most commonly `WHEN SYSTEM$STREAM_HAS_DATA('my_stream')`. `SYSTEM$STREAM_HAS_DATA` is the **only** function supported for evaluation in a task's `WHEN` expression.
  - Triggered tasks run **at most every 30 seconds by default** (configurable down to 10 seconds via `USER_TASK_MINIMUM_TRIGGER_INTERVAL_IN_SECONDS`).
  - Serverless triggered tasks **require** a `TARGET_COMPLETION_INTERVAL` (cannot combine with `WAREHOUSE`).
  - If a health check finds the stream hasn't triggered a run in **12 hours**, Snowflake schedules a check to head off stream staleness.

### Task graphs (DAGs)
- One **root task** (only the root needs a `SCHEDULE`) + child tasks defined via `AFTER <parent_task>`.
- **All tasks in one DAG must share the same owner** — a single role must hold `OWNERSHIP` on every task in the graph.
- Hard limits: **max 1,000 tasks per graph**; **max 100 parent tasks and 100 child tasks** per individual task.
- New tasks (and DAGs) start **suspended** by default — you must `ALTER TASK ... RESUME` to activate.
- Snowflake guarantees **only one instance of a DAG runs at a time** by default; if a run is still going when the next scheduled trigger fires, that trigger is **skipped**. `ALLOW_OVERLAPPING_EXECUTION` can permit concurrency if your pipeline logic tolerates it.
- An optional **finalizer task** can run cleanup logic after all other tasks in the graph complete (success or failure).
- `SUSPEND_TASK_AFTER_NUM_FAILURES` — auto-suspends a standalone task, or a whole DAG's root, after N consecutive failures/timeouts.

### Exam traps
- "Which function can I use inside a task's `WHEN` clause?" → **only `SYSTEM$STREAM_HAS_DATA`**.
- "Can different roles own different tasks in the same DAG?" → **No**, one owner for the whole DAG.
- "My child task didn't run even though its parent finished." → check for a `WHEN` condition failing, or the parent itself not completing successfully — descendants of a skipped/failed task (with a `WHEN` predicate not met) also don't run.
- "Is there a maximum on tasks per DAG?" → **1,000**; and 100 parents/children per single task.

## E. Dynamic Tables

### Core concept
A **dynamic table** materializes the result of a query and is **automatically, incrementally kept up to date** by Snowflake according to a declared freshness target — no manual stream/task orchestration required. You just write the `SELECT`; Snowflake manages *when* and *how* to refresh it.

```sql
CREATE OR REPLACE DYNAMIC TABLE dt_orders
  TARGET_LAG = '10 minutes'
  WAREHOUSE = transform_wh
  REFRESH_MODE = INCREMENTAL
AS
  SELECT ... FROM raw_orders WHERE order_status != 'returned';
```

### Target lag
- The maximum acceptable staleness vs. the base tables. It's a **target Snowflake tries to meet**, not a hard guarantee — actual lag can exceed it under heavy load, large data volume, complex queries, or pipeline depth.
- Special value: `TARGET_LAG = DOWNSTREAM` — the table has **no independent schedule**; it refreshes **only** when a downstream dynamic table that reads from it needs fresh data. Snowflake uses the *shortest* lag among all downstream consumers to decide timing.
  - ⚠️ If a `DOWNSTREAM`-lag table has **no** downstream consumers, it **never refreshes automatically**, and Snowflake gives **no warning**.
- Within a multi-table pipeline, Snowflake coordinates refresh timing so downstream tables always see a **consistent snapshot** of their upstream inputs (snapshot isolation across the DAG).

### Refresh modes
| Mode | Behavior |
|---|---|
| `INCREMENTAL` | Processes only the changed rows since last refresh — efficient, but requires an "incrementalizable" query (no unsupported constructs like `EXCEPT`, certain window functions, etc.) |
| `FULL` | Recomputes the entire result every refresh — needed when the query can't be incrementalized, or when almost all rows change between refreshes anyway |
| `AUTO` (default if omitted) | Snowflake decides INCREMENTAL vs FULL **once, at creation time** — the choice does **not** change dynamically afterward |
| `ADAPTIVE` | Behaves like INCREMENTAL but auto-reinitializes (a full recompute) when it detects large upstream changes; can use a separate `INITIALIZATION_WAREHOUSE` sized just for these occasional reinitializations |
| `CUSTOM_INCREMENTAL` | Advanced: you define your own incremental `MERGE`/`INSERT` refresh logic |

⚠️ **Gotcha:** The `CREATE` statement itself does **not** report which mode was actually resolved for `AUTO` — you must run `SHOW DYNAMIC TABLES` and check the `refresh_mode` / `refresh_mode_reason` columns. Snowflake recommends setting `REFRESH_MODE` **explicitly** in production so behavior doesn't silently shift between Snowflake releases.

### Pipeline / dependency rules
- Dynamic tables can chain into DAGs; Snowflake infers dependencies automatically from the queries.
- **A table using `INCREMENTAL` refresh mode cannot sit downstream of a table using `FULL` refresh mode** — full refresh replaces the entire result each time, which is incompatible with incremental change-merging logic downstream. (`ADAPTIVE` has the same restriction, unless the upstream has a system-derived unique key or a frozen region.)
- `INITIALIZE = ON_CREATE` (default) — populates data synchronously at creation (blocking). `INITIALIZE = ON_SCHEDULE` — creation returns immediately, and the table populates within the target-lag window; useful for adding a new leaf table to a live pipeline without blocking deployment.
- Manual refresh: `ALTER DYNAMIC TABLE ... REFRESH`. Refresh timeouts are governed by `STATEMENT_TIMEOUT_IN_SECONDS`.

### Notable hard limitations
- Can't use dynamic SQL / session variables inside the definition.
- Can't use sequences (`.NEXTVAL`) or `SAMPLE`/`TABLESAMPLE`.
- Requires the minimum target lag of **60 seconds** — can't get fresher than that, nor use stored procedures / external functions in the definition (some workarounds exist with UDTFs in lateral joins).
- Dynamic table refresh operations are **not** captured in `ACCESS_HISTORY`.
- Changing the SQL definition requires a full recreate (`CREATE OR REPLACE` / `CREATE OR ALTER`), which **reinitializes** the table and any downstream incremental dynamic tables (but not downstream full-refresh tables).

### Dynamic Tables vs. Streams+Tasks vs. Materialized Views (comparison — common scenario question)
| | Materialized View | Dynamic Table | Streams + Tasks |
|---|---|---|---|
| Query complexity | Single table only | Full SQL — joins, aggregations, window functions | Full SQL, but you write the merge logic yourself |
| Freshness control | Always fresh (auto), query-rewrite eligible | Declarative `TARGET_LAG` | Manual scheduling via task cadence |
| Orchestration | None needed | None needed (declarative) | You build/maintain the pipeline logic |
| Best for | Simple single-table rollups | Multi-step declarative transformation pipelines | Fine-grained custom incremental control |

### Exam traps
- "My dynamic table with `TARGET_LAG = DOWNSTREAM` never refreshes — why?" → it likely has **no downstream consumer**, and Snowflake won't warn you.
- "Can an incremental dynamic table read from a full-refresh dynamic table?" → **No** (pipeline compatibility constraint).
- "Which mode is chosen automatically and can it change later?" → `AUTO`, decided **once** at creation, not re-evaluated automatically after that.
- Confusing dynamic tables with materialized views — remember MVs are **single-table only**.

# 3.3 Snowflake Connectors and Integrations

## A. Drivers
Client libraries that let applications in a given language talk to Snowflake directly:

| Driver | Language/Interface |
|---|---|
| JDBC | Java (and any JDBC-compatible tool) |
| ODBC | C-based/ODBC-compatible client apps (e.g., BI tools) |
| Python Connector | Native Python, implements the Python DB API — no ODBC/JDBC dependency |
| Node.js Driver | Native asynchronous JS/Node.js interface |
| Go Driver | Go applications — ⚠️ has **limited operations**; notably **`PUT`/`GET` are not supported** in the Go driver |
| .NET Driver | Microsoft .NET applications |
| PHP Driver (PDO) | PHP applications |

⚠️ Client version support policy explicitly **excludes third-party partner connectors** (e.g., Informatica, Tableau) — those follow the partner's own support lifecycle, not Snowflake's.

## B. Connectors
Purpose-built integrations for specific ecosystems/tools (broader than "drivers," often bi-directional or ETL-oriented):

| Connector | Purpose |
|---|---|
| **Snowflake Connector for Kafka** | Reads from one or more Apache Kafka topics and loads into Snowflake tables; runs inside a Kafka Connect cluster; under the hood it can leverage Snowpipe or **Snowpipe Streaming** (Snowflake explicitly supports **replication/failover for Snowpipe Streaming with the Kafka connector**, but **not** for classic Snowpipe with the Kafka connector) |
| **Snowflake Connector for Spark** | Bi-directional data movement between a Spark cluster and Snowflake; supports predicate/query pushdown by translating Spark logical plan operations into SQL run in Snowflake; version-specific to your Spark version |
| **SnowSQL** | Command-line client (CLI) |
| **Snowpark** | Library for writing Python/Java/Scala code (including DataFrame-style operations, UDFs, stored procedures) that runs inside Snowflake's compute |

## C. Storage Integration
### Core concept
A **storage integration** is a first-class Snowflake object storing a Snowflake-generated cloud identity (an IAM role/user for AWS, a service principal for Azure, a service account for GCS) that external stages can use to access cloud storage **without embedding credentials** in the stage object.

### Key facts
- One storage integration can back **multiple** external stages — its `STORAGE_ALLOWED_LOCATIONS`/`STORAGE_BLOCKED_LOCATIONS` govern which buckets/paths/containers stages using it may reference.
- **AWS specifics**: `STORAGE_AWS_ROLE_ARN` (the IAM role you created and trust to Snowflake) is required; Snowflake auto-generates (or lets you supply) a `STORAGE_AWS_EXTERNAL_ID` used in the IAM trust policy's `sts:ExternalId` condition, closing the "confused deputy" security gap. After creation, `DESCRIBE INTEGRATION` reveals the auto-generated `STORAGE_AWS_IAM_USER_ARN` and `STORAGE_AWS_EXTERNAL_ID` — you then edit the AWS IAM role's trust policy to reference these values.
- ⚠️ **Snowflake provisions a single IAM user per Snowflake account**, shared across **all** S3 storage integrations in that account — this is a subtle but testable detail.
- Optional `STORAGE_AWS_OBJECT_ACL = 'bucket-owner-full-control'` — needed when unloading into a bucket owned by a *different* AWS account than the one whose IAM role is doing the writing.
- `STORAGE_BLOCKED_LOCATIONS` **takes precedence** over `STORAGE_ALLOWED_LOCATIONS` (deny wins on overlap).
- Only `ACCOUNTADMIN` or a role with the **global `CREATE INTEGRATION` privilege** can create a storage integration.
- Temporary AWS credentials generated for access are **cached by Snowflake up to 60 minutes** — meaning if you revoke access from the AWS side, Snowflake might still be able to list/access files until that cache naturally expires.

### Exam traps
- "Do I need separate IAM users for each of my stages?" → **No** — one IAM user is shared account-wide by all S3 storage integrations.
- "Which takes precedence if a location matches both allowed and blocked lists?" → **blocked**.
- "Do I embed my access keys in the `CREATE STAGE` statement when using a storage integration?" → **No** — that's the whole point; you reference the integration name instead.

## D. API Integration
### Core concept
An **API integration** object stores the connection details Snowflake needs to reach an external HTTPS API — used for two very different purposes on the exam:
1. **External functions** — calling out to an HTTPS proxy service (e.g., an Amazon API Gateway instance) so Snowflake SQL can invoke logic hosted outside Snowflake.
2. **Git integration** — connecting Snowflake to a remote Git repository's HTTPS API (`API_PROVIDER = git_https_api`).

### Key parameters
- `API_ALLOWED_PREFIXES` — restricts calls to specific HTTPS URL prefixes (an allowlist).
- `API_BLOCKED_PREFIXES` — explicit denylist; **takes precedence** over the allowed list on overlap (same pattern as storage integrations).
- `ENABLED` — disabling the integration disables any dependent external function or Git repository immediately.
- Only `ACCOUNTADMIN` (or a role with the appropriate global privilege) can create one.

## E. Git Integration
### Core concept
Lets Snowflake clone and stay synced with a remote Git repository (GitHub, GitLab, BitBucket, Azure DevOps, or a custom HTTPS Git server) via a special stage type: a **Git repository (repository stage)**.

### Setup building blocks
1. (Optional but common) A **`SECRET`** object storing credentials — Snowflake recommends a **personal access token** as the password value for private repos.
2. An **`API INTEGRATION`** with `API_PROVIDER = git_https_api`, scoped via `API_ALLOWED_PREFIXES` to the relevant Git host/org, and (if needed) `ALLOWED_AUTHENTICATION_SECRETS` naming the secret(s) it may use.
3. A **`GIT REPOSITORY`** object: `CREATE GIT REPOSITORY <name> ORIGIN = '<https_url>' API_INTEGRATION = <integration> [GIT_CREDENTIALS = <secret>]`.

### Key facts and gotchas
- The **origin URL must be HTTPS** — Snowflake does not support SSH-based Git URLs.
- A repository stage behaves like other stages (`LIST @repo_stage`, etc.) and exposes a special path structure: `@repo_name/branches/<branch>/...`, `@repo_name/tags/<tag>/...`, `@repo_name/commits/<commit>/...`.
- **Interaction is read-only** from Snowflake's side for SQL access: you can fetch/browse/pull the latest commits into Snowflake, but you **cannot** write/push changes back to the remote repo purely via SQL/repository-stage mechanics. (Note: **Snowsight Workspaces** is a separate, richer feature that *does* support commit/push directly from the UI, distinct from the base read-only repository-stage/API-integration mechanism.)
- Access to the Git repository is supported **only over the public internet** — no private connectivity/private network support for this feature.
- You can execute SQL scripts directly from a synced repo file using `EXECUTE IMMEDIATE FROM @repo_name/branches/main/sql/setup.sql` — a common DevOps/CI pattern for deploying Snowflake object definitions from version control.
- A repository must contain **at least one branch** — an empty repository cannot be synced.
- Sharing repository stages via **data sharing or Native Apps is not supported**; you also can't create repository stages inside a Native App on the consumer's side.
- Refreshing the local clone after new commits on the remote requires an explicit **fetch** action (manual sync — not automatically pushed to Snowflake).
- Compute cost note: Git operations run using your custom warehouse compute (billed like ordinary query compute), not a separate serverless charge.

### Exam traps
- "Can I push code changes from Snowflake back to GitHub using `EXECUTE IMMEDIATE FROM`?" → **No** — that command only *executes* files, it doesn't modify the repo; base Git-integration/API-integration access is read-only for repo content.
- "My repository URL uses `git@github.com:...` (SSH) — will `CREATE GIT REPOSITORY` accept it?" → **No**, HTTPS only.
- "Which parameter of `API INTEGRATION` is mandatory when connecting to Git?" → `API_PROVIDER = git_https_api`.
- "Can I share my repository stage with another Snowflake account?" → **No**, not supported via data sharing/Native Apps.

# Practice Scenario Questions

*(Original questions written to mirror common exam phrasing — not reproduced from any exam bank.)*

**Q1.** A data engineer sets `ON_ERROR = 'SKIP_FILE'` on a bulk `COPY INTO` load of 20 files, where one file has a single malformed row. What happens to that file?
> **A:** The *entire* file is skipped, not just the bad row — `SKIP_FILE` buffers and discards the whole file if it contains any error.

**Q2.** A pipe was recreated using `CREATE OR REPLACE PIPE` after a schema change. The team then runs `ALTER PIPE ... REFRESH`. What's the risk?
> **A:** File-loading history was reset by the recreate, so previously-loaded files still sitting in the stage could be reloaded, duplicating data.

**Q3.** True or False: You can attach a resource monitor directly to a Snowpipe object to cap its credit usage.
> **A:** False — Snowpipe uses Snowflake-managed serverless compute; resource monitors attach only to virtual warehouses.

**Q4.** A stream was created on a table with `APPEND_ONLY = TRUE`. Ten rows are inserted, then five are deleted before the stream is consumed. How many rows does the stream show?
> **A:** 10 — an append-only stream ignores deletes/updates entirely and only ever reports inserts.

**Q5.** Your dynamic table `dt_summary` has `TARGET_LAG = DOWNSTREAM` and no other dynamic table reads from it. How often does it refresh?
> **A:** It never refreshes automatically, and Snowflake does not raise any warning about this — a design/monitoring pitfall to watch for.

**Q6.** Which internal stage encryption type must you use if external tools need to read staged files through a pre-signed URL?
> **A:** `SNOWFLAKE_SSE` (server-side only) — `SNOWFLAKE_FULL`'s client-side layer makes files unreadable by external tools via such URLs.

**Q7.** A company wants Snowflake to write unloaded files into an S3 bucket owned by a *different* AWS account than the one whose IAM role Snowflake assumes. What storage integration parameter is needed?
> **A:** `STORAGE_AWS_OBJECT_ACL = 'bucket-owner-full-control'`.

**Q8.** Can you push local edits made inside a Snowflake worksheet back to a connected GitHub repository using the base Git repository / API integration mechanism (not Workspaces)?
> **A:** No — that mechanism is read-only; only Snowsight Workspaces supports committing and pushing changes back to the remote.
