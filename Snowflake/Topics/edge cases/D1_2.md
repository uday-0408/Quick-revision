
## 1.4 Configuring Virtual Warehouses

### Why this is the highest-yield section on the exam
Virtual warehouse questions dominate SnowPro Core scenario questions because warehouse configuration is where **cost, performance, and concurrency trade-offs** all meet — and Snowflake loves to test whether you'd make the *economically and technically correct* choice for a described business situation, not just whether you know the vocabulary.

### What a warehouse actually is

A warehouse is an MPP compute cluster providing CPU, memory, and local SSD ("temp") storage needed to execute SQL: SELECTs, DML (INSERT/UPDATE/DELETE/MERGE), and data loading/unloading (`COPY INTO`). A warehouse **must be running** to do any of this — while running, it consumes credits, billed **per-second with a 60-second minimum** each time it starts/resumes.

### Warehouse Types

#### 1. Standard Warehouses — Generation 1 vs. Generation 2

Both Gen1 and Gen2 are still "Standard" type warehouses (`WAREHOUSE_TYPE = 'STANDARD'`) — Gen2 is **not** a separate warehouse type, it's a hardware/engine generation setting (`GENERATION = '2'` or `RESOURCE_CONSTRAINT = STANDARD_GEN_2`).

| | Gen1 | Gen2 |
|---|---|---|
| What it is | Original standard warehouse hardware/engine | Newer hardware (e.g. AWS Graviton3) + query-engine optimizations for DML (DELETE/UPDATE/MERGE) and table scans |
| Performance | Baseline | Faster for most queries — Snowflake's own benchmarks and third-party tests report roughly **1.3x–2x+ speedups**, especially on scan-heavy and DML-heavy workloads |
| Credit rate | Baseline (1x) | Higher — roughly **~1.35x on AWS, ~1.25x on Azure** per-second rate |
| Sizes supported | All sizes including X5LARGE/X6LARGE | **X5LARGE and X6LARGE are NOT supported on Gen2** |
| Default when creating a new standard warehouse | — | **Gen2 is now the default** in regions where it's available (this changed via a 2026 Behavior Change Bundle); if Gen2 isn't available in your region, it silently falls back to Gen1 |
| Set via | omit the clause, or `GENERATION = '1'` | `GENERATION = '2'` or `RESOURCE_CONSTRAINT = 'STANDARD_GEN_2'` |
| Manageable in Snowsight? | Yes | **No — SQL only** (`CREATE WAREHOUSE` / `ALTER WAREHOUSE`); the GENERATION/RESOURCE_CONSTRAINT clauses are not yet exposed in the Snowsight UI |

**Critical gotcha — switching generations on a running warehouse:** If you `ALTER WAREHOUSE ... SET GENERATION = '2'` on a warehouse that's currently running queries, **existing in-flight queries keep running on Gen1 compute** while **new queries route to Gen2** compute. During this transition window **you are billed for both sets of compute resources simultaneously**, and the warehouse will **not auto-suspend** during this period even if it otherwise would. To avoid double-billing, either suspend the warehouse first before converting, or accept the temporary overlap cost.

#### 2. Snowpark-Optimized Warehouses

`WAREHOUSE_TYPE = 'SNOWPARK-OPTIMIZED'`. Purpose-built for **memory-intensive, often single-node** workloads: ML model training via stored procedures, complex/stateful UDFs and UDTFs, large in-memory data transformations.

- Provide **16x the memory per node** and **~10x the local cache** compared to a standard warehouse of the same size, by default (`MEMORY_16X` resource constraint).
- Configurable resource constraints: `MEMORY_1X`, `MEMORY_1X_X86`, `MEMORY_16X`, `MEMORY_16X_X86`, `MEMORY_64X`, `MEMORY_64X_X86` (the 64X / 1 TB-memory tier is currently AWS-only and in preview).
- **Cannot be created at X-Small or Small size** — the minimum supported size for a Snowpark-optimized warehouse is **Medium**.
- Cost roughly **~1.5x** the credit rate of an equivalent standard warehouse.
- **Cannot combine with Gen2**: Snowpark-optimized warehouses are not currently available as Gen2 warehouses — the GENERATION clause does not apply to them at all.
- For multi-node UDF/UDTF workloads (Large size or bigger), Snowflake automatically parallelizes and redistributes rows across nodes — it's not purely single-node-only at larger sizes.
- To maximize resources for a single heavy Snowpark operation, set `MAX_CONCURRENCY_LEVEL = 1` so one operation gets the entire node's CPU/memory instead of sharing it with concurrent queries.

**Exam signal:** "Team is getting out-of-memory errors / disk spillage training an ML model via a stored procedure" → **Snowpark-optimized warehouse**, not a bigger standard warehouse. Standard warehouses scale by adding *parallel* nodes; they don't give any single node more memory the way Snowpark-optimized does.

#### 3. Default Warehouse for Notebooks *(feature note)*

Per the current exam guide, this sub-feature is **not yet tested** until it reaches General Availability — know that it exists conceptually (a warehouse that Notebooks can default to without you specifying one each time) but don't expect deep configuration questions on it yet.

### Warehouse Sizing

Sizes run **X-Small → Small → Medium → Large → X-Large → 2X-Large → 3X-Large → 4X-Large → 5X-Large → 6X-Large**. Each step up **roughly doubles** compute resources and, correspondingly, credits consumed per hour (e.g., X-Small = 1 credit/hr, Small = 2, Medium = 4 ... 6X-Large = 512, following the doubling pattern per full continuous hour).

- **Resizing** = "scaling up/down" — changes compute *per cluster*. Can be done **any time, even while running.**
- Resizing does **not** directly solve concurrency/queuing problems by itself in the way people assume — Snowflake's own guidance is that **warehouse resizing is not intended for handling concurrency**; use multiple warehouses or multi-cluster warehouses for concurrency instead.
- **Larger ≠ always faster for data loading.** Load performance depends more on the **number and size of files** being loaded than on warehouse size. Loading a small number of large files, or a huge number of tiny files, won't necessarily go faster on a bigger warehouse — a classic exam distractor.

### Multi-Cluster Warehouses (Scaling **Out**) — Enterprise Edition+

A multi-cluster warehouse is a warehouse configured with `MAX_CLUSTER_COUNT > 1`. It has two modes:

- **Maximized mode**: `MIN_CLUSTER_COUNT = MAX_CLUSTER_COUNT` — all clusters run all the time, no dynamic scaling; use only when you need guaranteed, constant high concurrency capacity.
- **Auto-scale mode**: `MIN_CLUSTER_COUNT < MAX_CLUSTER_COUNT` — Snowflake starts/stops clusters automatically based on load. **This is the recommended default mode.**

#### Scaling Policies (only relevant in Auto-scale mode)

| Policy | Behavior | Best for |
|---|---|---|
| **Standard** (default) | Starts a new cluster quickly — after roughly **20 seconds** of sustained query queuing — prioritizing performance/minimal wait over cost. Shuts down clusters after a couple of minutes of low utilization. | Interactive/BI workloads, dashboards, anything latency-sensitive. |
| **Economy** | Waits much longer — roughly **6 minutes** — and only starts a new cluster if it estimates the additional cluster will stay busy for that sustained period; tolerates short queuing to save credits. | Batch/ETL, predictable workloads where saving credits matters more than instant response. |
| ~~Legacy~~ | **Removed.** Any warehouse still configured with the old "Legacy" policy is automatically treated as **Standard** now. | — trivia/legacy-knowledge trap. |

**Gotcha — "Interactive" warehouses:** a warehouse type built for responsiveness only supports the **Standard** scaling policy (not Economy) and scales more proactively/aggressively than a normal standard-scaling-policy warehouse, because it's designed to pre-empt queuing before it happens.

**Gotcha — auto-suspend on multi-cluster warehouses:** Auto-suspend applies to the *entire* warehouse, not individual clusters. For a multi-cluster warehouse, auto-suspend only fires when the warehouse is down to its **minimum cluster count** (usually 1, but can be configured higher for HA) **and** there's no activity for the configured idle period.

### Scaling Up vs. Scaling Out — the classic exam dichotomy

| | Scale **Up** (resize) | Scale **Out** (multi-cluster) |
|---|---|---|
| What it changes | Compute per cluster (size) | Number of clusters |
| Solves | Slow, complex individual queries | High concurrency / many simultaneous users or queries causing queuing |
| Edition requirement | Any edition | **Enterprise Edition or higher** |
| Analogy | Give one team member a bigger desk | Hire more team members for parallel throughput |

### Best Practices

**Sizing (up/down):**
- Start small (e.g., X-Small/Small/Medium) for ad-hoc/testing; scale to Large+ for production analytical workloads with complex joins/aggregations over big data.
- Data loading: size the warehouse to the **number and size of the files**, not the total table size. Bulk-loading hundreds/thousands of files concurrently benefits from a bigger warehouse; a handful of files usually doesn't.
- Per-second billing + auto-suspend means you can afford to start larger and tune down, since you're not locked into a fixed size for a billing period.

**Scaling (in/out) — multi-cluster best practices:**
- Prefer Auto-scale mode over Maximized unless you specifically need guaranteed constant capacity.
- Start conservatively: e.g., `MIN=1, MAX=2 or 3`, then observe and adjust.
- Keep `MIN_CLUSTER_COUNT` at the default of 1 unless high availability (protecting against a cluster failure) is a specific requirement, in which case raise it.
- Set `MAX_CLUSTER_COUNT` as high as the workload might need, bounded by cost tolerance for that warehouse's size.

**Auto-Suspend:**
- Setting it aggressively low (e.g., 60 seconds) minimizes idle-credit waste but can cause more frequent cold-starts (each resume still costs the 60-second minimum billing).
- Setting it high (or disabling) suits warehouses with near-constant, bursty traffic where suspending/resuming repeatedly would itself waste credits and add latency.
- There is **no universal "correct" number** — the exam tests understanding of the trade-off (idle waste vs. resume overhead/latency), not a magic value.

**Workload-based warehouse assignment (a very common scenario-question pattern):**

| Workload | Recommended pattern |
|---|---|
| **Ad-hoc / exploratory queries** | Small-to-medium, single-cluster, short auto-suspend (e.g., 1–5 min) — usage is bursty and unpredictable. |
| **Data loading (ETL/ELT)** | Size to file count/size, not data volume; often a dedicated warehouse separate from BI so load jobs don't compete with or delay reporting queries. |
| **BI / reporting (many concurrent dashboard users)** | Multi-cluster, Auto-scale, **Standard** scaling policy (fast response), sized to typical query complexity. |
| **Different teams sharing an account** | Separate warehouses **per team/workload** so credit usage is attributable and so one team's heavy queries can't starve another's — this is the standard "workload isolation" answer pattern. |
| **High concurrency** | Multi-cluster warehouse (Enterprise+), Auto-scale mode. |
| **Complex, resource-intensive individual queries** | Scale **up** (bigger single warehouse), not out. |

### Edge Cases & Gotchas — Warehouses (consolidated)

| Situation | What actually happens |
|---|---|
| Resizing a running warehouse | Allowed at any time; in-flight queries generally continue on their original compute, new queries pick up the new size — mirrors the Gen1→Gen2 transition behavior. |
| Warehouse credit billing minimum | **60-second minimum** per start/resume, then **per-second** billing after that — stopping a warehouse before the first 60 seconds elapse doesn't save anything, since the minimum has already been charged. |
| Multi-cluster warehouses on Standard Edition | **Not available** — hard Enterprise+ requirement; Standard Edition accounts are always single-cluster. |
| Query Acceleration Service (QAS) + scaling policy changes | Changing the scaling policy (Standard ↔ Economy) does **not** enable or disable QAS — they're independent settings. |
| QAS defaults on new Gen2/multi-cluster warehouses | As of recent behavior-change bundles, QAS is **enabled by default** on newly created multi-cluster warehouses (default max scale factor of 2), but still **disabled by default** on single-cluster warehouses. |
| Converting warehouse type mid-flight (Standard ↔ Snowpark-optimized, or Gen1 ↔ Gen2) | Existing queries finish on the resource type they started with; only new queries use the new configuration — same overlap-billing caveat as the Gen1→Gen2 case applies whenever you change `RESOURCE_CONSTRAINT` on a running warehouse. |

### Common Misconceptions

- **"A bigger warehouse always makes queries faster."** Only true for scan/compute-heavy queries with room to parallelize; small or already-fast queries see no benefit, and data loading in particular is governed by file count/size, not warehouse size.
- **"Multi-cluster warehouses are about making individual queries faster."** No — they solve **concurrency** (many simultaneous queries/users), not single-query speed. Confusing "scale up" with "scale out" is the single most common exam trap in this whole domain.
- **"Snowpark-optimized warehouses are just bigger standard warehouses."** No — they provide disproportionately more **memory per node**, not simply more nodes; the value is memory density for single/few-node memory-bound workloads, not raw parallel throughput.
- **"Gen2 is strictly better so there's no reason to use Gen1."** Gen2 costs more per second; for light/simple queries where Gen1 already finishes fast, the performance gain may not offset the higher rate — cost/performance testing is Snowflake's own official recommendation before switching a whole fleet to Gen2.

### Quick Revision — 1.4

1. Warehouse types: **Standard** (Gen1/Gen2) and **Snowpark-Optimized**; Gen2 is a generation setting on Standard warehouses, not a separate type.
2. Gen2 = newer hardware, faster for most workloads, ~1.25–1.35x higher credit rate, no X5/X6-Large support, SQL-only to configure, now the **default** where available.
3. Snowpark-optimized = 16x memory/node, ~10x cache, Medium minimum size, ~1.5x cost, no Gen2 combo, ideal for ML training / heavy UDFs / memory-bound single-node work.
4. **Scale up** (resize) = faster individual queries. **Scale out** (multi-cluster, Enterprise+) = more concurrency.
5. Scaling policies: **Standard** (fast, ~20 sec trigger, costlier) vs **Economy** (patient, ~6 min trigger, cheaper); Legacy policy removed → became Standard.
6. Multi-cluster modes: **Maximized** (all clusters always on) vs **Auto-scale** (recommended default).
7. Billing: 60-second minimum per resume, then per-second.
8. Workload isolation via separate warehouses per team/purpose is the standard best-practice answer.
9. Switching warehouse config on a running warehouse can cause temporary double-billing while old queries finish on old compute.
