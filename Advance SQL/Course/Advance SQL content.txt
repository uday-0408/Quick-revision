Module Summary
1. Introduction to SQL Performance Tuning
1.1 Why Performance Tuning Matters
SQL Performance Tuning optimizes queries and data structures for faster execution and efficient resource use. While the goal is universal, each platform has unique architectures requiring different approaches:

Platform	Architecture	Key Tuning Focus
Oracle	Traditional RDBMS with B-tree indexes	Indexes, statistics, hints
Snowflake	Cloud-native, micro-partitions, no indexes	Clustering, warehouse sizing, caching
Databricks	Distributed Spark, Delta Lake	Partitioning, Z-ordering, file optimization
1.2 Universal Performance Principles
Regardless of platform, these principles apply:

Reduce Data Scanned - Filter early, select only needed columns
Optimize Joins - Join order, join types, data locality
Leverage Caching - Reuse computed results when possible
Understand Execution Plans - Know what the engine is doing
Keep Statistics Current - Help the optimizer make good decisions
2. Oracle Performance Tuning
2.1 The Cost-Based Optimizer (CBO)
Oracle's Cost-Based Optimizer evaluates multiple execution paths and selects the one with lowest estimated cost based on statistics.

How CBO Works
SQL Statement → Parse → Transform → Generate Plans → Estimate Costs → Select Best Plan → Execute
Viewing Execution Plans
-- Method 1: EXPLAIN PLAN
EXPLAIN PLAN FOR
SELECT e.employee_name, d.department_name, e.salary
FROM employees e
JOIN departments d ON e.department_id = d.department_id
WHERE e.salary > 50000
  AND d.location_id = 1700;

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);

-- Method 2: AUTOTRACE (SQL*Plus)
SET AUTOTRACE ON EXPLAIN STATISTICS
SELECT * FROM employees WHERE department_id = 10;

-- Method 3: Real-time SQL Monitoring (Enterprise Edition)
SELECT DBMS_SQLTUNE.REPORT_SQL_MONITOR(
    sql_id => 'abc123xyz',

) FROM dual;

2.2 Oracle Index Types
B-Tree Index (Default)
-- Standard B-Tree index
CREATE INDEX emp_lastname_idx ON employees(last_name);

-- Composite index (column order matters!)
CREATE INDEX emp_dept_job_idx ON employees(department_id, job_id);

-- Query uses index (filters on leading column)
SELECT * FROM employees WHERE department_id = 10;  -- ✓ Uses index

-- Query CANNOT use index efficiently (missing leading column)
SELECT * FROM employees WHERE job_id = 'CLERK';    -- ✗ Full scan or skip scan
Unique Index
-- Enforce uniqueness
CREATE UNIQUE INDEX emp_email_uk ON employees(email);

-- Automatic with primary key
ALTER TABLE employees ADD CONSTRAINT emp_pk PRIMARY KEY (employee_id);
Function-Based Index
-- Problem: Function prevents index usage
SELECT * FROM employees WHERE UPPER(last_name) = 'SMITH';  -- Full scan!

-- Solution: Function-based index
CREATE INDEX emp_upper_name_idx ON employees(UPPER(last_name));

-- Now uses index
SELECT * FROM employees WHERE UPPER(last_name) = 'SMITH';  -- Index range scan

-- Other examples
CREATE INDEX emp_year_idx ON employees(EXTRACT(YEAR FROM hire_date));
CREATE INDEX emp_salary_calc_idx ON employees(salary * 12 + NVL(commission_pct, 0));
Bitmap Index (Data Warehouse Only)
-- Ideal for low-cardinality columns in DW environments
CREATE BITMAP INDEX emp_gender_bidx ON employees(gender);
CREATE BITMAP INDEX emp_status_bidx ON employees(status);

-- Excellent for combining multiple conditions
SELECT COUNT(*) FROM employees
WHERE gender = 'F' 
  AND status = 'ACTIVE' 
  AND region = 'WEST';
-- Oracle performs efficient bitmap AND operations
⚠️ Warning: Never use bitmap indexes in OLTP systems - they cause severe locking issues during DML operations.

Reverse Key Index
-- Problem: Sequential values cause "hot block" contention
CREATE INDEX order_id_idx ON orders(order_id);  -- All inserts hit rightmost leaf

-- Solution: Reverse key distributes inserts
CREATE INDEX order_id_ridx ON orders(order_id) REVERSE;

-- Limitation: Cannot use for range scans
SELECT * FROM orders WHERE order_id BETWEEN 1000 AND 2000;  -- Full scan!
2.3 Oracle Query Anti-Patterns
Anti-Pattern 1: Functions on Indexed Columns
-- ❌ BAD: Prevents index usage
SELECT * FROM orders WHERE TRUNC(order_date) = DATE '2024-01-15';

-- ✓ GOOD: Rewrite as range
SELECT * FROM orders 
WHERE order_date >= DATE '2024-01-15' 
  AND order_date < DATE '2024-01-16';
Anti-Pattern 2: Implicit Type Conversion
-- ❌ BAD: phone_number is VARCHAR2, comparing with number
SELECT * FROM employees WHERE phone_number = 5551234;
-- Oracle converts: TO_NUMBER(phone_number) for EVERY row!

-- ✓ GOOD: Match data types
SELECT * FROM employees WHERE phone_number = '5551234';
Anti-Pattern 3: Leading Wildcards
-- ❌ BAD: Cannot use B-tree index
SELECT * FROM employees WHERE last_name LIKE '%SMITH%';

-- ✓ GOOD: Trailing wildcard uses index
SELECT * FROM employees WHERE last_name LIKE 'SMITH%';

-- ✓ ALTERNATIVE: Oracle Text for full-text search
CREATE INDEX emp_name_ctx ON employees(last_name) INDEXTYPE IS CTXSYS.CONTEXT;
SELECT * FROM employees WHERE CONTAINS(last_name, '%SMITH%') > 0;

3. Snowflake Performance Tuning
3.1 Snowflake Architecture Overview
Snowflake uses a unique architecture that differs fundamentally from traditional databases:

┌─────────────────────────────────────────────────────────────┐
│                    Cloud Services Layer                      │
│         (Query Optimization, Metadata, Security)             │
├─────────────────────────────────────────────────────────────┤
│                    Virtual Warehouses                        │
│              (Compute - Scalable Independently)              │
├─────────────────────────────────────────────────────────────┤
│                    Storage Layer                             │
│         (Micro-partitions, Compressed, Immutable)            │
└─────────────────────────────────────────────────────────────┘
Key Concepts:

No Traditional Indexes - Snowflake automatically manages data organization
Micro-partitions - Data stored in 50-500MB compressed chunks
Automatic Clustering - Data naturally organized by insert order
Pruning - Optimizer skips irrelevant micro-partitions
3.2 Understanding Snowflake Query Profile
-- Run a query
SELECT c.c_name, SUM(o.o_totalprice) total_orders
FROM customer c
JOIN orders o ON c.c_custkey = o.o_custkey
WHERE o.o_orderdate BETWEEN '2024-01-01' AND '2024-03-31'
GROUP BY c.c_name
ORDER BY total_orders DESC
LIMIT 100;

-- View query profile in Snowflake UI:
-- 1. Go to Query History
-- 2. Click on the query
-- 3. Select "Query Profile" tab

-- Or get query ID programmatically
SELECT LAST_QUERY_ID();

-- View execution details
SELECT *
FROM TABLE(INFORMATION_SCHEMA.QUERY_HISTORY_BY_USER())
WHERE QUERY_ID = '<query_id>'
ORDER BY START_TIME DESC;
Key Query Profile Metrics
Metric	Description	What to Look For
Partitions Scanned	Number of micro-partitions read	Lower is better - indicates good pruning
Partitions Total	Total partitions in table	Compare with scanned
Bytes Scanned	Data volume processed	Minimize with filtering/clustering
Spillage to Local/Remote	Data overflow from memory	Indicates warehouse too small
Queue Time	Time waiting for resources	Consider larger warehouse
3.3 Clustering Keys
Snowflake's alternative to indexes - organizes data within micro-partitions for better pruning.

When to Use Clustering Keys
-- Check current clustering info
SELECT TABLE_NAME, CLUSTERING_KEY, 
       TOTAL_CONSTANT_PARTITION_COUNT,
       AVERAGE_OVERLAPS,
       AVERAGE_DEPTH
FROM INFORMATION_SCHEMA.TABLES
WHERE TABLE_NAME = 'ORDERS';

-- View clustering depth (lower is better, 1-2 is ideal)
SELECT SYSTEM$CLUSTERING_DEPTH('orders');

-- Check clustering information for specific columns
SELECT SYSTEM$CLUSTERING_INFORMATION('orders', '(o_orderdate)');
Creating Clustering Keys
-- Add clustering key to existing table
ALTER TABLE orders CLUSTER BY (o_orderdate);

-- Create table with clustering key
CREATE TABLE sales (
    sale_id NUMBER,
    sale_date DATE,
    region VARCHAR(50),
    product_id NUMBER,
    amount DECIMAL(18,2)
) CLUSTER BY (sale_date, region);

-- Multiple columns for common query patterns
ALTER TABLE orders CLUSTER BY (o_orderdate, o_orderstatus);

-- Expression-based clustering
ALTER TABLE events CLUSTER BY (TO_DATE(event_timestamp));
Clustering Best Practices
-- ✓ GOOD: Cluster on frequently filtered columns
ALTER TABLE orders CLUSTER BY (order_date);  -- Date ranges common

-- ✓ GOOD: Cluster on join columns for large-large joins
ALTER TABLE lineitem CLUSTER BY (l_orderkey);

-- ❌ BAD: High cardinality columns alone
ALTER TABLE orders CLUSTER BY (order_id);  -- Too unique

-- ✓ BETTER: Combine with lower cardinality
ALTER TABLE orders CLUSTER BY (order_date, customer_id);

-- Check if clustering is helping
SELECT SYSTEM$CLUSTERING_INFORMATION('orders', '(order_date)');
-- Look for: average_depth close to 1, low overlap
3.4 Snowflake Query Optimization Techniques
Technique 1: Partition Pruning
-- ❌ BAD: No pruning possible (function on column)
SELECT * FROM orders 
WHERE DATE_TRUNC('month', o_orderdate) = '2024-01-01';

-- ✓ GOOD: Enables partition pruning
SELECT * FROM orders
WHERE o_orderdate >= '2024-01-01' 
  AND o_orderdate < '2024-02-01';

-- Check pruning effectiveness in Query Profile
-- Look for: "Partitions scanned" vs "Partitions total"
Technique 2: Warehouse Sizing
-- Create warehouses for different workloads
CREATE WAREHOUSE analytics_wh
    WAREHOUSE_SIZE = 'LARGE'
    AUTO_SUSPEND = 300
    AUTO_RESUME = TRUE
    MIN_CLUSTER_COUNT = 1
    MAX_CLUSTER_COUNT = 4
    SCALING_POLICY = 'STANDARD';

-- Resize based on query needs
ALTER WAREHOUSE analytics_wh SET WAREHOUSE_SIZE = 'XLARGE';

-- For complex queries with spillage, scale up
-- For many concurrent queries, scale out (multi-cluster)
Technique 3: Caching Strategies
-- Snowflake has 3 cache layers:
-- 1. Query Result Cache (24 hours, automatic)
-- 2. Local Disk Cache (warehouse SSD)
-- 3. Remote Disk Cache (S3/Azure/GCS)

-- Force fresh execution (bypass result cache)
ALTER SESSION SET USE_CACHED_RESULT = FALSE;
SELECT * FROM large_table WHERE date_col = CURRENT_DATE();
ALTER SESSION SET USE_CACHED_RESULT = TRUE;

-- Leverage result cache for repeated queries
-- Same query + same user + same role = instant results
SELECT COUNT(*) FROM orders WHERE year = 2024;  -- First run: 5 seconds
SELECT COUNT(*) FROM orders WHERE year = 2024;  -- Second run: instant

-- Check if result came from cache
SELECT QUERY_ID, QUERY_TEXT, BYTES_SCANNED, 
       PERCENTAGE_SCANNED_FROM_CACHE
FROM TABLE(INFORMATION_SCHEMA.QUERY_HISTORY())
ORDER BY START_TIME DESC
LIMIT 10;
Technique 4: Materialized Views
-- Create materialized view for expensive aggregations
CREATE MATERIALIZED VIEW mv_daily_sales AS
SELECT 
    sale_date,
    region,
    COUNT(*) as num_sales,
    SUM(amount) as total_amount,
    AVG(amount) as avg_amount
FROM sales
GROUP BY sale_date, region;

-- Snowflake automatically maintains and uses MV
SELECT * FROM mv_daily_sales WHERE region = 'WEST';

-- Check materialized view status
SHOW MATERIALIZED VIEWS;

-- Force refresh if needed
ALTER MATERIALIZED VIEW mv_daily_sales REFRESH;
Technique 5: Search Optimization Service
-- Enable for point lookups on large tables (Enterprise Edition)
ALTER TABLE customers ADD SEARCH OPTIMIZATION;

-- Check search optimization status
SHOW TABLES LIKE 'customers';
SELECT SYSTEM$ESTIMATE_SEARCH_OPTIMIZATION_COSTS('customers');

-- Optimizes these query patterns:
SELECT * FROM customers WHERE customer_id = 12345;       -- Equality
SELECT * FROM customers WHERE email = 'john@email.com';  -- Equality on string
SELECT * FROM customers WHERE tags LIKE '%premium%';     -- Substring
SELECT * FROM customers WHERE ARRAY_CONTAINS(interests, 'sports');  -- Semi-structured
3.5 Snowflake-Specific Anti-Patterns
Anti-Pattern 1: SELECT *
-- ❌ BAD: Scans all columns
SELECT * FROM wide_table WHERE date_col = '2024-01-01';

-- ✓ GOOD: Select only needed columns
SELECT id, name, amount FROM wide_table WHERE date_col = '2024-01-01';
-- Snowflake is columnar - fewer columns = less data scanned
Anti-Pattern 2: ORDER BY Without LIMIT
-- ❌ BAD: Sorts entire result set
SELECT * FROM orders WHERE year = 2024 ORDER BY order_date DESC;

-- ✓ GOOD: Limit results when possible
SELECT * FROM orders WHERE year = 2024 ORDER BY order_date DESC LIMIT 1000;
Anti-Pattern 3: Exploding Joins
-- ❌ BAD: Cartesian-like explosion
SELECT a.*, b.*
FROM table_a a
JOIN table_b b ON a.category = b.category  -- Low cardinality join key
WHERE a.status = 'active';

-- ✓ GOOD: Add more selective conditions
SELECT a.*, b.*
FROM table_a a
JOIN table_b b ON a.category = b.category 
              AND a.date_col = b.date_col  -- Additional join condition
WHERE a.status = 'active';
Anti-Pattern 4: UDFs in WHERE Clauses
-- ❌ BAD: UDF prevents pruning
SELECT * FROM orders WHERE my_udf(order_date) = 'Q1-2024';

-- ✓ GOOD: Use native functions
SELECT * FROM orders WHERE QUARTER(order_date) = 1 AND YEAR(order_date) = 2024;

-- ✓ BETTER: Range predicate for best pruning
SELECT * FROM orders 
WHERE order_date >= '2024-01-01' AND order_date < '2024-04-01';
4. Databricks Performance Tuning
4.1 Databricks/Spark Architecture
Databricks runs on Apache Spark, a distributed computing engine:

┌────────────────────────────────────────────────────────────────┐
│                        Driver Node                              │
│            (Coordinates, Query Planning, Optimization)          │
├────────────────────────────────────────────────────────────────┤
│     Worker 1      │      Worker 2      │      Worker N         │
│   ┌──────────┐   │   ┌──────────┐     │   ┌──────────┐       │
│   │ Executor │   │   │ Executor │     │   │ Executor │       │
│   │ (Tasks)  │   │   │ (Tasks)  │     │   │ (Tasks)  │       │
│   └──────────┘   │   └──────────┘     │   └──────────┘       │
├────────────────────────────────────────────────────────────────┤
│                    Delta Lake Storage                           │
│        (Parquet files + Transaction Log + Metadata)             │
└────────────────────────────────────────────────────────────────┘
Key Concepts:

Delta Lake - ACID transactions on data lake
Partitioning - Physical data organization by column values
Z-Ordering - Multi-dimensional clustering within partitions
Data Skipping - Statistics-based file pruning
4.2 Understanding Spark Execution Plans
Viewing Query Plans
-- Method 1: EXPLAIN command
EXPLAIN SELECT * FROM orders WHERE order_date = '2024-01-15';

-- Method 2: Extended explain with statistics
EXPLAIN EXTENDED 
SELECT c.name, SUM(o.amount)
FROM customers c
JOIN orders o ON c.id = o.customer_id
GROUP BY c.name;

-- Method 3: Cost-based explain
EXPLAIN COST
SELECT * FROM orders WHERE region = 'WEST';

-- Method 4: Formatted explain (easier to read)
EXPLAIN FORMATTED
SELECT * FROM large_table WHERE date_col = '2024-01-15';
Sample Spark Execution Plan
== Physical Plan ==
*(2) HashAggregate(keys=[name#10], functions=[sum(amount#25)])
+- Exchange hashpartitioning(name#10, 200)
   +- *(1) HashAggregate(keys=[name#10], functions=[partial_sum(amount#25)])
      +- *(1) Project [name#10, amount#25]
         +- *(1) BroadcastHashJoin [id#5], [customer_id#20], Inner, BuildLeft
            :- BroadcastExchange HashedRelationBroadcastMode(List(input[0, int, false]))
            :  +- *(1) Filter isnotnull(id#5)
            :     +- *(1) Scan parquet customers [id#5, name#10]
            +- *(1) Filter isnotnull(customer_id#20)
               +- *(1) Scan parquet orders [customer_id#20, amount#25]

-- Key indicators:
-- Exchange = Shuffle (expensive!)
-- BroadcastHashJoin = Small table broadcast (efficient)
-- Scan parquet with pushdown = Good filtering
Using Spark UI

# Navigate to: SQL tab → Query details → DAG Visualization

# Programmatically get query metrics
spark.sql("SELECT * FROM orders WHERE date = '2024-01-15'")

4.3 Delta Lake Optimization
Partitioning
-- Create partitioned table
CREATE TABLE sales (
    sale_id BIGINT,
    sale_date DATE,
    customer_id BIGINT,
    product_id BIGINT,
    region STRING,
    amount DECIMAL(18,2)
) 
USING DELTA
PARTITIONED BY (sale_date);

-- Query leverages partition pruning
SELECT * FROM sales WHERE sale_date = '2024-01-15';
-- Only reads partition: sale_date=2024-01-15/

-- Check partitions
SHOW PARTITIONS sales;

-- Partitioning guidelines:
-- ✓ GOOD: Date columns (daily/monthly granularity)
-- ✓ GOOD: Columns with < 10,000 distinct values
-- ❌ BAD: High-cardinality columns (creates too many small files)
Z-Ordering (Multi-Dimensional Clustering)
-- Z-Order for columns frequently used together in filters
OPTIMIZE sales ZORDER BY (customer_id, product_id);

-- How it works:
-- - Colocates related data in same files
-- - Enables data skipping via file-level statistics
-- - Best for columns with high cardinality

-- Example: Before Z-ORDER
-- customer_id=100 scattered across 1000 files

-- After Z-ORDER on customer_id
-- customer_id=100 concentrated in ~10 files

-- Combine with partitioning
CREATE TABLE events (
    event_id BIGINT,
    event_date DATE,
    user_id BIGINT,
    event_type STRING,
    properties MAP<STRING, STRING>
)
USING DELTA
PARTITIONED BY (event_date);

-- Then Z-ORDER within partitions
OPTIMIZE events WHERE event_date >= '2024-01-01' ZORDER BY (user_id);
OPTIMIZE and VACUUM
-- Compact small files (improves read performance)
OPTIMIZE orders;

-- Optimize specific partition
OPTIMIZE orders WHERE order_date >= '2024-01-01';

-- Remove old files (saves storage)
VACUUM orders RETAIN 168 HOURS;  -- Keep 7 days of history

-- Check table details
DESCRIBE DETAIL orders;
-- Shows: numFiles, sizeInBytes, numPartitions

-- View file statistics
DESCRIBE HISTORY orders;
Auto Optimize (Databricks)
-- Enable auto-optimization for a table
ALTER TABLE orders SET TBLPROPERTIES (
    'delta.autoOptimize.optimizeWrite' = 'true',
    'delta.autoOptimize.autoCompact' = 'true'
);

-- Or set at session level
SET spark.databricks.delta.optimizeWrite.enabled = true;
SET spark.databricks.delta.autoCompact.enabled = true;
4.4 Databricks Query Optimization Techniques
Technique 1: Broadcast Joins
-- Small table automatically broadcast (< 10MB default)
SELECT /*+ BROADCAST(d) */ 
    e.name, d.dept_name
FROM employees e
JOIN departments d ON e.dept_id = d.dept_id;

-- Increase broadcast threshold for larger dimension tables
SET spark.sql.autoBroadcastJoinThreshold = 100m;  -- 100MB

-- Force broadcast hint
SELECT /*+ BROADCAST(small_table) */ *
FROM large_table l
JOIN small_table s ON l.key = s.key;

-- Check join strategy in explain plan
EXPLAIN SELECT * FROM large JOIN small ON large.id = small.id;
-- Look for: BroadcastHashJoin (good) vs SortMergeJoin (more expensive)
Technique 2: Predicate Pushdown
-- ✓ GOOD: Filter pushes to data source
SELECT * FROM parquet.`/path/to/data` WHERE date = '2024-01-15';

-- Verify pushdown in plan
EXPLAIN SELECT * FROM orders WHERE order_date = '2024-01-15';
-- Look for: PushedFilters: [EqualTo(order_date, 2024-01-15)]

-- Delta Lake file skipping
SELECT * FROM delta_table WHERE id = 12345;
-- Delta uses min/max statistics to skip files where id NOT BETWEEN min AND max
Technique 3: Column Pruning
-- ❌ BAD: Reads all columns
SELECT * FROM wide_table WHERE date = '2024-01-15';

-- ✓ GOOD: Reads only needed columns
SELECT id, name, amount FROM wide_table WHERE date = '2024-01-15';

-- Parquet/Delta are columnar - fewer columns = faster queries
Technique 4: Caching
-- Cache frequently accessed table
CACHE TABLE customers;

-- Cache with specific storage level
CACHE TABLE orders OPTIONS ('storageLevel' 'MEMORY_AND_DISK');

-- Cache query result
CACHE SELECT * FROM orders WHERE year = 2024;

-- Check what's cached
SELECT * FROM cached_tables;

-- Clear cache
UNCACHE TABLE customers;
CLEAR CACHE;
Technique 5: Adaptive Query Execution (AQE)
-- Enable AQE (default in Databricks Runtime 7.3+)
SET spark.sql.adaptive.enabled = true;

-- AQE features:
SET spark.sql.adaptive.coalescePartitions.enabled = true;  -- Combine small partitions
SET spark.sql.adaptive.skewJoin.enabled = true;            -- Handle skewed joins
SET spark.sql.adaptive.localShuffleReader.enabled = true;  -- Optimize shuffles

-- AQE automatically:
-- 1. Converts sort-merge joins to broadcast joins at runtime
-- 2. Coalesces small shuffle partitions
-- 3. Handles skewed partition joins
Technique 6: Bloom Filters (Delta Lake)
-- Create bloom filter index for point lookups
CREATE BLOOMFILTER INDEX ON TABLE orders FOR COLUMNS (order_id);

-- Works well for:
-- - Columns with high cardinality
-- - Equality predicates (=, IN)
-- - NOT for range queries

-- Check bloom filter usage
SET spark.databricks.io.skipping.bloomFilter.enabled = true;
4.5 Databricks-Specific Anti-Patterns
Anti-Pattern 1: Too Many Small Files
-- Problem: Thousands of small files (< 128MB each)
-- Symptoms: Slow reads, high metadata overhead

-- Check file count
DESCRIBE DETAIL my_table;

-- Solution: OPTIMIZE
OPTIMIZE my_table;

-- Prevention: Use auto-optimize
ALTER TABLE my_table SET TBLPROPERTIES (
    'delta.autoOptimize.optimizeWrite' = 'true'
);
Anti-Pattern 2: Over-Partitioning
-- ❌ BAD: Too granular partitioning
CREATE TABLE events
PARTITIONED BY (year, month, day, hour, user_id);  -- Creates millions of partitions!

-- ✓ GOOD: Reasonable partitioning
CREATE TABLE events
PARTITIONED BY (event_date);  -- Daily partitions

-- Then use Z-ORDER for additional columns
OPTIMIZE events ZORDER BY (user_id);
Anti-Pattern 3: Cartesian Products
-- ❌ BAD: Accidental cross join
SELECT * FROM table_a, table_b;  -- Cartesian product!

SELECT * FROM table_a 
JOIN table_b ON table_a.category = table_b.category;  
-- If category has low cardinality, still quasi-cartesian

-- ✓ GOOD: Ensure join keys are selective
SELECT * FROM table_a a
JOIN table_b b ON a.id = b.foreign_id;
Anti-Pattern 4: Collect() on Large Datasets
# ❌ BAD: Brings all data to driver (OOM risk)
all_data = spark.sql("SELECT * FROM huge_table").collect()

# ✓ GOOD: Limit data brought to driver
sample = spark.sql("SELECT * FROM huge_table LIMIT 1000").collect()

# ✓ GOOD: Process in distributed manner
spark.sql("""
    SELECT region, SUM(amount) 
    FROM huge_table 
    GROUP BY region
""").write.parquet("/output/path")
Anti-Pattern 5: UDFs Instead of Built-in Functions
# ❌ BAD: Python UDF (slow, no optimization)
from pyspark.sql.functions import udf
@udf
def my_upper(s):
    return s.upper() if s else None

df.withColumn("upper_name", my_upper("name"))

# ✓ GOOD: Built-in function (optimized)
from pyspark.sql.functions import upper
df.withColumn("upper_name", upper("name"))

# If UDF needed, use Pandas UDF for better performance
from pyspark.sql.functions import pandas_udf
@pandas_udf("string")
def pandas_upper(s: pd.Series) -> pd.Series:
    return s.str.upper()
5. Cross-Platform Comparison
5.1 Feature Comparison Matrix
Feature	Oracle	Snowflake	Databricks
Traditional Indexes	✓ B-Tree, Bitmap, etc.	✗ Not supported	✗ Not supported
Clustering	Index-Organized Tables	Clustering Keys	Z-Ordering
Partitioning	Range, List, Hash	Micro-partitions (auto)	Delta partitions
Statistics	DBMS_STATS (manual/auto)	Automatic	ANALYZE TABLE
Execution Plans	EXPLAIN PLAN	Query Profile	EXPLAIN
Caching	Buffer cache	Result cache + warehouse	Spark cache
Materialized Views	✓	✓ (auto-refresh)	✗ (use Delta tables)
Query Hints	✓ Extensive	Limited	✓ Join hints
5.2 Equivalent Operations
Index-like Optimization
-- ORACLE: Create index
CREATE INDEX emp_dept_idx ON employees(department_id);

2.3 Password Policies and Profiles
Profiles control password policies and resource limits.

Creating Security Profiles
-- Production Security Profile (strict)
CREATE PROFILE prod_security_profile LIMIT
    -- Password Parameters
    PASSWORD_LIFE_TIME 90                -- Password expires in 90 days
    PASSWORD_REUSE_TIME 365              -- Can't reuse password for 1 year
    PASSWORD_REUSE_MAX 12                -- Must use 12 different passwords before reusing
    PASSWORD_VERIFY_FUNCTION ora12c_verify_function  -- Password complexity check
    PASSWORD_LOCK_TIME 1                 -- Lock account for 1 day after failures
    PASSWORD_GRACE_TIME 7                -- 7 days grace period after expiry
    FAILED_LOGIN_ATTEMPTS 5              -- Lock after 5 failed attempts
    
    -- Resource Parameters
    SESSIONS_PER_USER 3                  -- Max 3 concurrent sessions
    CPU_PER_SESSION UNLIMITED            -- No CPU limit per session
    CPU_PER_CALL 60000                   -- Max 60 seconds CPU per call
    CONNECT_TIME 480                     -- Max 8 hours connection time
    IDLE_TIME 30                         -- Disconnect after 30 min idle
    LOGICAL_READS_PER_SESSION UNLIMITED;

-- Development Profile (relaxed for convenience)
CREATE PROFILE dev_profile LIMIT
    PASSWORD_LIFE_TIME 180
    PASSWORD_REUSE_TIME 30
    PASSWORD_REUSE_MAX 3
    FAILED_LOGIN_ATTEMPTS 10
    PASSWORD_LOCK_TIME UNLIMITED/1440    -- Lock for 1 minute
    SESSIONS_PER_USER 10
    IDLE_TIME 120;

System privileges control what types of actions a user can perform.

Common System Privileges

3.4 WITH GRANT OPTION vs WITH ADMIN OPTION
-- WITH GRANT OPTION (Object Privileges)
-- Allows grantee to grant the same object privilege to others
GRANT SELECT ON hr.employees TO manager WITH GRANT OPTION;
-- Now manager can do:
-- GRANT SELECT ON hr.employees TO subordinate;

-- If you revoke from manager, subordinate also loses access (CASCADE)
REVOKE SELECT ON hr.employees FROM manager;  -- Affects subordinate too!

-- WITH ADMIN OPTION (System Privileges & Roles)
-- Allows grantee to grant the system privilege or role to others
GRANT CREATE TABLE TO developer WITH ADMIN OPTION;

-- Revoking from developer does NOT affect others
REVOKE CREATE TABLE FROM developer;  -- Others keep it!

4.1 Why Use Roles?
Managing individual privileges for each user becomes unmanageable at scale. Roles group privileges together for easier management.

Creating Roles

Role Hierarchies
/*
 * ROLE HIERARCHY FOR A RETAIL COMPANY
 */

-- Base role for all employees
CREATE ROLE employee_base_role;
GRANT CREATE SESSION TO employee_base_role;
GRANT SELECT ON company.announcements TO employee_base_role;

-- Sales role includes employee base
CREATE ROLE sales_role;
GRANT employee_base_role TO sales_role;  -- Inherit base role
GRANT SELECT, INSERT ON sales.customers TO sales_role;
GRANT SELECT, INSERT, UPDATE ON sales.orders TO sales_role;

-- Manager role includes sales role
CREATE ROLE manager_role;
GRANT sales_role TO manager_role;
GRANT SELECT ON hr.employees TO manager_role;
GRANT SELECT ON finance.budgets TO manager_role;

-- Admin role includes everything
CREATE ROLE admin_role IDENTIFIED BY "Adm1n#S3cur3";
GRANT manager_role TO admin_role;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES TO admin_role;
Granting Roles to Users
-- Grant single role
GRANT sales_role TO john_smith;

-- Grant multiple roles
GRANT sales_role, reporting_role TO jane_doe;

-- Grant with admin option (user can grant this role to others)
GRANT manager_role TO department_head WITH ADMIN OPTION;

-- Set default roles (active upon login)
ALTER USER john_smith DEFAULT ROLE sales_role, employee_base_role;

-- No default roles (must enable manually)
ALTER USER secure_user DEFAULT ROLE NONE;
Enabling and Disabling Roles
-- User with password-protected role must enable it

-- Enable all granted roles
SET ROLE ALL;

-- Disable all roles
SET ROLE NONE;

-- Enable specific roles only
SET ROLE sales_role, reporting_role;

CREATE OR REPLACE FUNCTION sales.customer_policy (
    p_schema  IN VARCHAR2,
    p_object  IN VARCHAR2
) RETURN VARCHAR2 AS
    v_role VARCHAR2(50);
BEGIN
    v_role := SYS_CONTEXT('sales_ctx', 'role');
    
    IF v_role = 'SALES_REP' THEN
        RETURN 'assigned_rep_id = SYS_CONTEXT(''sales_ctx'', ''employee_id'')';

    ELSIF v_role = 'VP_SALES' THEN
        RETURN '1=1';  -- See everything
    ELSE
        RETURN '1=0';  -- See nothing
    END IF;
END;

1. Analytical Functions
1.1 Introduction to Window Functions
Window functions perform calculations across a set of rows that are related to the current row, without collapsing the result set like GROUP BY does.

┌─────────────────────────────────────────────────────────────────┐
│              AGGREGATE vs WINDOW FUNCTIONS                       │
├────────────────────────────┬────────────────────────────────────┤
│      GROUP BY (Aggregate)  │        WINDOW FUNCTION             │
├────────────────────────────┼────────────────────────────────────┤
│ Collapses rows             │ Preserves all rows                 │
│ One row per group          │ Adds calculation to each row       │
│ Cannot see individual rows │ Can access surrounding rows        │
│ Simple totals/averages     │ Running totals, rankings, etc.     │
└────────────────────────────┴────────────────────────────────────┘
Basic Syntax
function_name(arguments) OVER (
    [PARTITION BY partition_expression]
    [ORDER BY sort_expression [ASC|DESC]]
    [window_frame_clause]
)

ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

1.6 Window Frame Specifications
Understanding ROWS vs RANGE
┌─────────────────────────────────────────────────────────────────┐
│                    WINDOW FRAMES                                 │
├────────────────────────────┬────────────────────────────────────┤
│           ROWS             │            RANGE                    │
├────────────────────────────┼────────────────────────────────────┤
│ Physical rows              │ Logical value range                │
│ Exact row count            │ All rows with same ORDER BY value  │
│ ROWS BETWEEN 2 PRECEDING   │ RANGE BETWEEN 100 PRECEDING        │
│   AND CURRENT ROW          │   AND CURRENT ROW                  │
│ Good for: moving averages  │ Good for: value-based windows      │
└────────────────────────────┴────────────────────────────────────┘
Frame Boundary Options
Boundary	Description
UNBOUNDED PRECEDING
First row of partition
n PRECEDING
n rows/values before current
CURRENT ROW
Current row
n FOLLOWING
n rows/values after current
UNBOUNDED FOLLOWING
Last row of partition
Moving Averages
/*
 * STOCK ANALYSIS: 3-day and 7-day moving averages
 */
WITH daily_sales AS (
    SELECT 
        sale_date,
        SUM(amount) AS daily_total
    FROM sales_data
    GROUP BY sale_date
)
SELECT 
    sale_date,
    daily_total,
    -- 3-day moving average (current + 2 preceding)
    ROUND(
        AVG(daily_total) OVER (
            ORDER BY sale_date
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        ), 2
    ) AS moving_avg_3day,
    -- 7-day moving average
    ROUND(
        AVG(daily_total) OVER (
            ORDER BY sale_date
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ), 2
    ) AS moving_avg_7day,
    -- Centered 5-day average (2 before, current, 2 after)
    ROUND(
        AVG(daily_total) OVER (
            ORDER BY sale_date
            ROWS BETWEEN 2 PRECEDING AND 2 FOLLOWING
        ), 2
    ) AS centered_avg_5day
FROM daily_sales
ORDER BY sale_date;

        SUM(amount) AS revenue
    FROM sales_data

        ORDER BY month
        ROWS BETWEEN 11 PRECEDING AND CURRENT ROW

        AVG(revenue) OVER (

/*
 * RECURSIVE CTE: Same org chart using WITH clause
 * (Oracle 11g R2+)
 */
WITH org_hierarchy (employee_id, employee_name, job_title, manager_id, lvl, path) AS (
    -- Anchor: Start with root nodes
    SELECT 
        employee_id, 
        employee_name, 
        job_title, 
        manager_id,
        1 AS lvl,
        employee_name AS path
    FROM employees_hier
    WHERE manager_id IS NULL
    
    UNION ALL
    
    -- Recursive: Join children to parents
    SELECT 
        e.employee_id,
        e.employee_name,
        e.job_title,
        e.manager_id,
        h.lvl + 1,
        h.path || ' → ' || e.employee_name
    FROM employees_hier e
    INNER JOIN org_hierarchy h ON e.manager_id = h.employee_id
)
SELECT 
    lvl AS level,
    LPAD(' ', (lvl - 1) * 4) || employee_name AS org_chart,
    job_title,
    path
FROM org_hierarchy
ORDER BY path;

/*
 * ANALYTICS: Calculate statistics and join back
 */
SELECT 
    e.employee_name,
    e.salary,
    e.department,
    dept_stats.avg_salary,
    dept_stats.min_salary,
    dept_stats.max_salary,

3.4 EXISTS vs IN
Performance Comparison
/*
 * EXISTS: Stops at first match (short-circuits)
 * IN: Evaluates all values in subquery
 */

-- Use EXISTS when subquery returns many rows
-- Finds customers who have placed orders
SELECT c.customer_id, c.customer_name
FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o 
    WHERE o.customer_id = c.customer_id
);

-- Use IN when subquery returns few distinct values
-- Finds customers in specific regions
SELECT customer_id, customer_name
FROM customers
WHERE region_id IN (SELECT region_id FROM regions WHERE country = 'USA');
NOT EXISTS vs NOT IN
/*
 * CRITICAL DIFFERENCE: NULL handling!
 * NOT IN fails if subquery contains NULL
 * NOT EXISTS handles NULLs correctly
 */

-- Find customers with no orders
-- SAFE: Use NOT EXISTS
SELECT c.customer_id, c.customer_name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o 
    WHERE o.customer_id = c.customer_id
);

-- DANGEROUS: NOT IN with potential NULLs
-- If orders.customer_id contains any NULL, this returns NO ROWS!
SELECT customer_id, customer_name
FROM customers
WHERE customer_id NOT IN (SELECT customer_id FROM orders);
-- Fix: Add NULL filter
WHERE customer_id NOT IN (SELECT customer_id FROM orders WHERE customer_id IS NOT NULL);

Basic CTE
/*
 * CTE: Named subquery for better readability and reuse
 */
WITH 
    dept_stats AS (
        SELECT 
            department,
            AVG(salary) AS avg_salary,
            SUM(salary) AS total_salary,
            COUNT(*) AS emp_count
        FROM employees_hier
        GROUP BY department
    ),
    company_stats AS (
        SELECT 
            AVG(salary) AS company_avg,
            SUM(salary) AS company_total
        FROM employees_hier
    )
SELECT 
    d.department,
    d.emp_count,
    ROUND(d.avg_salary, 2) AS dept_avg,
    d.total_salary,
    ROUND(d.total_salary / c.company_total * 100, 1) AS pct_of_total,
    CASE 
        WHEN d.avg_salary > c.company_avg THEN 'Above Average'
        ELSE 'Below Average'
    END AS status
FROM dept_stats d
CROSS JOIN company_stats c
ORDER BY d.total_salary DESC;
Multiple CTEs with Dependencies
/*
 * SALES ANALYSIS: Multi-level aggregation
 */
WITH 
    -- Level 1: Daily sales by salesperson
    daily_sales AS (
        SELECT 
            salesperson,
            TRUNC(sale_date) AS sale_date,
            SUM(amount) AS daily_total
        FROM sales_data
        GROUP BY salesperson, TRUNC(sale_date)
    ),
    -- Level 2: Monthly summary (references daily_sales)
    monthly_sales AS (
        SELECT 
            salesperson,
            TRUNC(sale_date, 'MM') AS month,
            SUM(daily_total) AS monthly_total,
            COUNT(DISTINCT sale_date) AS active_days,
            AVG(daily_total) AS avg_daily
        FROM daily_sales
        GROUP BY salesperson, TRUNC(sale_date, 'MM')
    ),
    -- Level 3: Rankings (references monthly_sales)
    ranked_sales AS (
        SELECT 
            salesperson,
            month,
            monthly_total,
            active_days,
            avg_daily,
            RANK() OVER (PARTITION BY month ORDER BY monthly_total DESC) AS monthly_rank
        FROM monthly_sales
    )
SELECT *
FROM ranked_sales
WHERE monthly_rank <= 3
ORDER BY month, monthly_rank;
CTE for Data Transformation
/*
 * DATA CLEANING: Use CTE to stage transformations
 */
WITH 
    cleaned_data AS (
        SELECT 
            UPPER(TRIM(customer_name)) AS customer_name,
            REGEXP_REPLACE(phone, '[^0-9]', '') AS phone_cleaned,
            LOWER(TRIM(email)) AS email,
            COALESCE(status, 'ACTIVE') AS status
        FROM raw_customers
        WHERE customer_name IS NOT NULL
    ),
    deduplicated AS (
        SELECT 
            customer_name,
            phone_cleaned,
            email,
            status,
            ROW_NUMBER() OVER (
                PARTITION BY email 
                ORDER BY customer_name
            ) AS dup_num
        FROM cleaned_data
    )
SELECT customer_name, phone_cleaned, email, status
FROM deduplicated
WHERE dup_num = 1;

4.1 MERGE Statement (UPSERT)
MERGE combines INSERT and UPDATE in a single statement:

/*
 * REAL-WORLD SCENARIO: Sync inventory from supplier feed
 */

-- Source: Daily supplier inventory file
CREATE TABLE supplier_inventory (
    product_code    VARCHAR2(20),
    product_name    VARCHAR2(100),
    quantity        NUMBER,
    unit_price      NUMBER(10,2),
    last_updated    DATE
);

-- Target: Our inventory table
CREATE TABLE warehouse_inventory (
    product_code    VARCHAR2(20) PRIMARY KEY,
    product_name    VARCHAR2(100),
    quantity        NUMBER,
    unit_price      NUMBER(10,2),
    last_updated    DATE,
    created_date    DATE
);

-- MERGE: Insert new products, update existing ones
MERGE INTO warehouse_inventory tgt
USING supplier_inventory src
ON (tgt.product_code = src.product_code)

-- When product exists: Update
WHEN MATCHED THEN
    UPDATE SET
        tgt.product_name = src.product_name,
        tgt.quantity = src.quantity,
        tgt.unit_price = src.unit_price,
        tgt.last_updated = SYSDATE
    -- Optional: Delete if quantity is 0
    DELETE WHERE src.quantity = 0

-- When product is new: Insert
WHEN NOT MATCHED THEN
    INSERT (product_code, product_name, quantity, unit_price, last_updated, created_date)
    VALUES (src.product_code, src.product_name, src.quantity, src.unit_price, SYSDATE, SYSDATE);

-- Check results
SELECT * FROM warehouse_inventory;

ROLLUP - Hierarchical Subtotals

NULL     NULL         14250        1                   1    <- Grand total

CUBE - All Dimension Combinations
/*
 * ANALYSIS: All possible subtotals
 */
SELECT 
    COALESCE(region, 'ALL REGIONS') AS region,
    COALESCE(product, 'ALL PRODUCTS') AS product,
    SUM(amount) AS total_sales,
    COUNT(*) AS num_sales
FROM sales_data
GROUP BY CUBE(region, product)
ORDER BY region, product;

/*
Result includes:
- Each region + each product
- Each region + ALL products (region subtotals)
- ALL regions + each product (product subtotals)
- ALL regions + ALL products (grand total)
*/
GROUPING SETS - Custom Groupings
/*
 * CUSTOM SUBTOTALS: Only specific groupings
 */
SELECT 
    region,
    product,
    salesperson,
    SUM(amount) AS total_sales
FROM sales_data
GROUP BY GROUPING SETS (
    (region, product),           -- Sales by region and product
    (region, salesperson),       -- Sales by region and person
    (region),                    -- Region subtotals only
    ()                           -- Grand total
)
ORDER BY region NULLS LAST, product NULLS LAST, salesperson NULLS LAST;

/*
 * IDENTIFY aggregation levels
 */
SELECT 
    region,
    salesperson,
    SUM(amount) AS total,
    CASE GROUPING_ID(region, salesperson)
        WHEN 0 THEN 'Detail'
        WHEN 1 THEN 'Region Subtotal'
        WHEN 3 THEN 'Grand Total'
    END AS row_type
FROM sales_data
GROUP BY ROLLUP(region, salesperson);

GROUPING_ID returns a bitmap:
- 0 (binary 00): Both columns are regular values
- 1 (binary 01): salesperson is aggregated (NULL)
- 3 (binary 11): Both columns are aggregated (grand total)
*/
5.5 MODEL Clause (Spreadsheet Calculations)
/*
 * ADVANCED: Spreadsheet-like calculations
 * Calculate forecasts based on growth rate
 */
SELECT region, year, sales, forecast
FROM (
    SELECT region, EXTRACT(YEAR FROM sale_date) AS year, SUM(amount) AS sales
    FROM sales_data
    GROUP BY region, EXTRACT(YEAR FROM sale_date)
)
MODEL
    PARTITION BY (region)
    DIMENSION BY (year)
    MEASURES (sales, 0 AS forecast)
    RULES (
        -- Calculate 10% growth forecast for next year
        forecast[2025] = sales[2024] * 1.10,
        forecast[2026] = sales[2025] * 1.10
    )
ORDER BY region, year;

Query 2: Monthly Trend Analysis
/*
 * TREND ANALYSIS: MoM and YoY comparisons
 */
WITH monthly_data AS (
    SELECT 
        TRUNC(txn_date, 'MM') AS month,
        region,
        SUM(amount) AS revenue,
        COUNT(*) AS transactions,
        COUNT(DISTINCT customer_id) AS customers
    FROM sales_transactions
    GROUP BY TRUNC(txn_date, 'MM'), region
)
SELECT 
    month,
    region,
    revenue,
    transactions,
    customers,
    -- Previous month comparison
    LAG(revenue) OVER (PARTITION BY region ORDER BY month) AS prev_month_revenue,
    ROUND(
        (revenue - LAG(revenue) OVER (PARTITION BY region ORDER BY month)) 
        / NULLIF(LAG(revenue) OVER (PARTITION BY region ORDER BY month), 0) * 100, 
        1
    ) AS mom_growth_pct,
    -- Same month last year
    LAG(revenue, 12) OVER (PARTITION BY region ORDER BY month) AS same_month_ly,
    ROUND(
        (revenue - LAG(revenue, 12) OVER (PARTITION BY region ORDER BY month)) 
        / NULLIF(LAG(revenue, 12) OVER (PARTITION BY region ORDER BY month), 0) * 100, 
        1
    ) AS yoy_growth_pct,
    -- 3-month moving average
    ROUND(AVG(revenue) OVER (
        PARTITION BY region ORDER BY month
        ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
    ), 2) AS moving_avg_3m,
    -- Running total YTD
    SUM(revenue) OVER (
        PARTITION BY region, EXTRACT(YEAR FROM month)
        ORDER BY month
    ) AS ytd_revenue
FROM monthly_data
ORDER BY region, month;

Query 4: Hierarchical Territory Report
/*
 * HIERARCHY: Region > Territory > Salesperson
 */
WITH territory_summary AS (
    SELECT 
        region,
        territory,
        salesperson,
        SUM(amount) AS sales
    FROM sales_transactions
    GROUP BY region, territory, salesperson
)
SELECT 
    LPAD(' ', (LEVEL - 1) * 4) || 
    CASE LEVEL
        WHEN 1 THEN 'Region: ' || region
        WHEN 2 THEN 'Territory: ' || territory
        WHEN 3 THEN salesperson
    END AS hierarchy,
    sales
FROM (
    -- Aggregate at different levels
    SELECT region, NULL AS territory, NULL AS salesperson, SUM(sales) AS sales, 1 AS lvl
    FROM territory_summary GROUP BY region
    UNION ALL
    SELECT region, territory, NULL, SUM(sales), 2
    FROM territory_summary GROUP BY region, territory
    UNION ALL
    SELECT region, territory, salesperson, sales, 3
    FROM territory_summary
)
START WITH territory IS NULL AND salesperson IS NULL
CONNECT BY PRIOR region = region 
       AND (PRIOR territory IS NULL AND territory IS NOT NULL
            OR PRIOR territory = territory AND PRIOR salesperson IS NULL)
ORDER SIBLINGS BY sales DESC;
Query 5: Customer Segmentation with Analytics
/*
 * RFM ANALYSIS: Recency, Frequency, Monetary
 */
WITH customer_rfm AS (
    SELECT 
        customer_id,
        customer_name,
        MAX(txn_date) AS last_purchase,
        COUNT(*) AS frequency,
        SUM(amount) AS monetary,
        TRUNC(SYSDATE) - MAX(txn_date) AS recency_days
    FROM sales_transactions
    GROUP BY customer_id, customer_name
),
rfm_scores AS (
    SELECT 
        customer_id,
        customer_name,
        last_purchase,
        recency_days,
        frequency,
        monetary,
        -- Score 1-5 (5 is best)
        NTILE(5) OVER (ORDER BY recency_days DESC) AS r_score,
        NTILE(5) OVER (ORDER BY frequency) AS f_score,
        NTILE(5) OVER (ORDER BY monetary) AS m_score
    FROM customer_rfm
)
SELECT 
    customer_id,
    customer_name,
    recency_days,
    frequency,
    monetary,
    r_score, f_score, m_score,
    r_score || f_score || m_score AS rfm_segment,
    CASE 
        WHEN r_score >= 4 AND f_score >= 4 AND m_score >= 4 THEN 'Champions'
        WHEN r_score >= 4 AND f_score >= 3 THEN 'Loyal Customers'
        WHEN r_score >= 4 AND m_score >= 4 THEN 'Big Spenders'
        WHEN r_score <= 2 AND f_score >= 4 THEN 'At Risk'
        WHEN r_score <= 2 AND f_score <= 2 THEN 'Lost'
        ELSE 'Regular'
    END AS customer_segment
FROM rfm_scores
ORDER BY monetary DESC;

-- Create source (supplier feed)
CREATE TABLE supplier_prices (

    product_name VARCHAR2(100),
    new_price NUMBER(10,2),
    is_available CHAR(1)
);

-- Create target (our catalog)
CREATE TABLE product_catalog (
    product_code VARCHAR2(20) PRIMARY KEY,
    product_name VARCHAR2(100),
    current_price NUMBER(10,2),
    status VARCHAR2(20),
    last_updated DATE
);

-- Insert test data

INSERT INTO supplier_prices VALUES ('P003', 'New Keyboard', 79, 'Y');
INSERT INTO supplier_prices VALUES ('P002', 'Mouse', 29, 'N');  -- Discontinued

-- MERGE solution
MERGE INTO product_catalog tgt
USING supplier_prices src
ON (tgt.product_code = src.product_code)

WHEN MATCHED THEN
    UPDATE SET
        tgt.product_name = src.product_name,
        tgt.current_price = src.new_price,
        tgt.status = CASE src.is_available WHEN 'Y' THEN 'ACTIVE' ELSE 'DISCONTINUED' END,

WHEN NOT MATCHED THEN
    INSERT (product_code, product_name, current_price, status, last_updated)
    VALUES (src.product_code, src.product_name, src.new_price, 
            CASE src.is_available WHEN 'Y' THEN 'ACTIVE' ELSE 'DISCONTINUED' END,
            SYSDATE)
    WHERE src.is_available = 'Y';  -- Only insert available products

8. Module Summary
8.1 Key Concepts Review
Topic	Key Points
Window Functions	Perform calculations across related rows without collapsing results
ROW_NUMBER, RANK, DENSE_RANK	Different ranking behaviors for ties
LAG/LEAD	Access previous/next row values
Window Frames	ROWS vs RANGE, PRECEDING/FOLLOWING/UNBOUNDED
CONNECT BY	Oracle's traditional hierarchical query syntax
Recursive CTE	Modern, portable alternative to CONNECT BY
Correlated Subqueries	Reference outer query, execute per row
CTEs (WITH)	Named subqueries for readability and reuse
MERGE	UPSERT: combined INSERT/UPDATE/DELETE
Multi-table INSERT	Distribute rows to multiple tables
PIVOT/UNPIVOT	Transform rows↔columns
ROLLUP/CUBE	Hierarchical and multi-dimensional subtotals
8.2 Quick Reference
-- Window Function Syntax
function() OVER (
    PARTITION BY col
    ORDER BY col
    ROWS BETWEEN n PRECEDING AND m FOLLOWING
)

-- Hierarchical Query
SELECT ... FROM table
START WITH condition
CONNECT BY PRIOR parent = child
ORDER SIBLINGS BY col;

-- Recursive CTE
WITH cte (cols) AS (
    SELECT ... -- Anchor
    UNION ALL
    SELECT ... FROM cte JOIN table ON ... -- Recursive
)
SELECT * FROM cte;

-- MERGE
MERGE INTO target USING source ON (join_condition)
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...;

-- PIVOT
SELECT * FROM table
PIVOT (agg_function FOR column IN (values));

-- ROLLUP/CUBE
GROUP BY ROLLUP(col1, col2)  -- Hierarchical subtotals
GROUP BY CUBE(col1, col2)    -- All combinations

2. PL/SQL Block Structure
2.1 Anonymous Block Structure
Every PL/SQL program is composed of blocks. The basic block structure:

```sql DECLARE -- Declaration Section (Optional) -- Define variables, constants, cursors, exceptions, types v_variable datatype; BEGIN -- Executable Section (Required) -- Contains procedural and SQL statements statements; EXCEPTION -- Exception Handling Section (Optional) -- Handles runtime errors WHEN exception_name THEN handler_statements; END; / ```

Key Points:

`DECLARE` is optional if no variables needed
`BEGIN...END` is required
`EXCEPTION` section is optional but recommended
Forward slash (`/`) executes the block in SQL*Plus/SQL Developer
2.2 Complete Block Example
```sql SET SERVEROUTPUT ON;

DECLARE -- Variables v_dept_id NUMBER := 10; v_dept_name VARCHAR2(50); v_emp_count NUMBER; v_total_salary NUMBER; v_avg_salary NUMBER;

-- Constants
c_bonus_rate    CONSTANT NUMBER := 0.10;
c_currency      CONSTANT VARCHAR2(3) := 'USD';
BEGIN -- Get department information SELECT department_name INTO v_dept_name FROM departments WHERE department_id = v_dept_id;

-- Get employee statistics
SELECT COUNT(*), SUM(salary), AVG(salary)
INTO v_emp_count, v_total_salary, v_avg_salary
FROM employees 
WHERE department_id = v_dept_id;

-- Display results
DBMS_OUTPUT.PUT_LINE('═══════════════════════════════════════');
DBMS_OUTPUT.PUT_LINE('Department Report: ' || v_dept_name);
DBMS_OUTPUT.PUT_LINE('═══════════════════════════════════════');
DBMS_OUTPUT.PUT_LINE('Employee Count: ' || v_emp_count);
DBMS_OUTPUT.PUT_LINE('Total Salary: ' || c_currency || ' ' || TO_CHAR(v_total_salary, '999,999.99'));
DBMS_OUTPUT.PUT_LINE('Average Salary: ' || c_currency || ' ' || TO_CHAR(v_avg_salary, '999,999.99'));
DBMS_OUTPUT.PUT_LINE('Bonus Pool (10%): ' || c_currency || ' ' || TO_CHAR(v_total_salary * c_bonus_rate, '999,999.99'));
EXCEPTION WHEN NO_DATA_FOUND THEN DBMS_OUTPUT.PUT_LINE('ERROR: Department ID ' || v_dept_id || ' not found'); WHEN OTHERS THEN DBMS_OUTPUT.PUT_LINE('ERROR: ' || SQLERRM); END; / ```

2.3 Nested Blocks and Variable Scope
```sql <<outer_block>> DECLARE v_outer_value NUMBER := 100; v_shared VARCHAR2(50) := 'Outer Value'; BEGIN DBMS_OUTPUT.PUT_LINE('Outer Block - v_outer_value: ' || v_outer_value);

<<inner_block>>
DECLARE
    v_inner_value NUMBER := 200;
    v_shared      VARCHAR2(50) := 'Inner Value';  -- Shadows outer
BEGIN
    DBMS_OUTPUT.PUT_LINE('Inner Block - v_inner_value: ' || v_inner_value);
    DBMS_OUTPUT.PUT_LINE('Inner Block - v_shared (inner): ' || v_shared);
    DBMS_OUTPUT.PUT_LINE('Inner Block - v_shared (outer): ' || outer_block.v_shared);
    
    -- Modify outer variable
    outer_block.v_shared := 'Modified by Inner';
END inner_block;

DBMS_OUTPUT.PUT_LINE('Back in Outer - v_shared: ' || v_shared);
END outer_block; / ```

4. Control Structures
4.1 IF-THEN-ELSIF-ELSE
```sql DECLARE v_salary NUMBER := 75000; v_bonus_pct NUMBER; BEGIN IF v_salary >= 100000 THEN v_bonus_pct := 0.20; ELSIF v_salary >= 75000 THEN v_bonus_pct := 0.15; ELSIF v_salary >= 50000 THEN v_bonus_pct := 0.10; ELSE v_bonus_pct := 0.05; END IF;

4.2 CASE Expression and Statement
```sql -- CASE Expression (returns a value) DECLARE v_grade CHAR(1) := 'B'; v_gpa NUMBER; BEGIN v_gpa := CASE v_grade WHEN 'A' THEN 4.0 WHEN 'B' THEN 3.0 WHEN 'C' THEN 2.0 WHEN 'D' THEN 1.0 ELSE 0.0 END; DBMS_OUTPUT.PUT_LINE('GPA: ' || v_gpa); END; /

-- CASE Statement (controls flow) DECLARE v_status VARCHAR2(20) := 'PENDING'; BEGIN CASE v_status WHEN 'PENDING' THEN DBMS_OUTPUT.PUT_LINE('Processing pending order'); WHEN 'SHIPPED' THEN DBMS_OUTPUT.PUT_LINE('Order is on its way'); WHEN 'DELIVERED' THEN DBMS_OUTPUT.PUT_LINE('Order completed'); ELSE DBMS_OUTPUT.PUT_LINE('Unknown status'); END CASE; END; / ```

WHILE Loop
```sql DECLARE v_counter NUMBER := 1; BEGIN WHILE v_counter <= 5 LOOP DBMS_OUTPUT.PUT_LINE('Count: ' || v_counter); v_counter := v_counter + 1; END LOOP; END; / ```

FOR Loop
```sql BEGIN -- Forward loop FOR i IN 1..5 LOOP DBMS_OUTPUT.PUT_LINE('Forward: ' || i); END LOOP;

END; / ```

CONTINUE Statement

Nested Loops with Labels

5. Cursors
5.1 Implicit Cursors
```sql BEGIN UPDATE employees SET salary = salary * 1.05 WHERE department_id = 60;

IF SQL%FOUND THEN
    DBMS_OUTPUT.PUT_LINE('Updated: ' || SQL%ROWCOUNT || ' rows');
ELSE
    DBMS_OUTPUT.PUT_LINE('No rows updated');
END IF;

END; / ```

SQL Cursor Attributes
Attribute	Description
SQL%FOUND	TRUE if DML affected rows
SQL%NOTFOUND	TRUE if no rows affected
SQL%ROWCOUNT	Number of rows affected

5.2 Explicit Cursor Lifecycle
```sql DECLARE CURSOR c_employees IS SELECT employee_id, first_name, last_name, salary FROM employees WHERE department_id = 60;

v_emp c_employees%ROWTYPE;
BEGIN OPEN c_employees;

LOOP
    FETCH c_employees INTO v_emp;
    EXIT WHEN c_employees%NOTFOUND;
    DBMS_OUTPUT.PUT_LINE(v_emp.first_name || ' ' || v_emp.last_name || ': $' || v_emp.salary);
END LOOP;

CLOSE c_employees;
END; / ```

5.3 Cursor FOR Loop
```sql -- Using declared cursor DECLARE CURSOR c_depts IS SELECT department_id, department_name FROM departments; BEGIN FOR dept IN c_depts LOOP DBMS_OUTPUT.PUT_LINE(dept.department_name); END LOOP; END; /

-- Inline cursor (no declaration needed) BEGIN FOR emp IN (SELECT first_name, salary FROM employees WHERE department_id = 60) LOOP DBMS_OUTPUT.PUT_LINE(emp.first_name || ': $' || emp.salary); END LOOP; END; / ```

5.4 Parameterized Cursors
```sql DECLARE CURSOR c_dept_emps(p_dept_id NUMBER, p_min_salary NUMBER DEFAULT 0) IS SELECT first_name, last_name, salary FROM employees WHERE department_id = p_dept_id AND salary >= p_min_salary; BEGIN DBMS_OUTPUT.PUT_LINE('IT Department, All:'); FOR emp IN c_dept_emps(60) LOOP DBMS_OUTPUT.PUT_LINE(' ' || emp.first_name || ' ' || emp.last_name); END LOOP;

DBMS_OUTPUT.PUT_LINE('IT Department, Salary >= 8000:');
FOR emp IN c_dept_emps(60, 8000) LOOP
    DBMS_OUTPUT.PUT_LINE('  ' || emp.first_name || ' ' || emp.last_name);
END LOOP;
END; / ```

5.5 REF CURSOR (Dynamic Cursors)
```sql DECLARE TYPE emp_cursor IS REF CURSOR; c_emps emp_cursor; v_name VARCHAR2(100); v_salary NUMBER; v_report_type VARCHAR2(20) := 'MANAGERS'; BEGIN CASE v_report_type WHEN 'MANAGERS' THEN OPEN c_emps FOR SELECT first_name || ' ' || last_name, salary FROM employees WHERE job_id LIKE '%MGR%'; ELSE OPEN c_emps FOR SELECT first_name || ' ' || last_name, salary FROM employees; END CASE;

LOOP
    FETCH c_emps INTO v_name, v_salary;
    EXIT WHEN c_emps%NOTFOUND;
    DBMS_OUTPUT.PUT_LINE(v_name || ': $' || v_salary);

CLOSE c_emps;
END; / ```

5.6 BULK COLLECT

```sql DECLARE CURSOR c_all IS SELECT * FROM employees; TYPE emp_tab IS TABLE OF employees%ROWTYPE; v_batch emp_tab; c_batch_size CONSTANT PLS_INTEGER := 100; BEGIN OPEN c_all; LOOP FETCH c_all BULK COLLECT INTO v_batch LIMIT c_batch_size; EXIT WHEN v_batch.COUNT = 0;

    DBMS_OUTPUT.PUT_LINE('Processing batch of ' || v_batch.COUNT || ' rows');
    -- Process batch here

END LOOP;

END; / ```

8. Bulk Operations
8.1 FORALL Statement
```sql DECLARE TYPE t_id_tab IS TABLE OF NUMBER; TYPE t_sal_tab IS TABLE OF NUMBER; v_ids t_id_tab; v_salaries t_sal_tab; BEGIN SELECT employee_id, salary * 1.05 BULK COLLECT INTO v_ids, v_salaries FROM employees WHERE department_id = 60;

END; / ```

8.2 FORALL with SAVE EXCEPTIONS
```sql DECLARE TYPE t_id_tab IS TABLE OF NUMBER; v_ids t_id_tab := t_id_tab(1, 2, 9999, 4); e_bulk_errors EXCEPTION; PRAGMA EXCEPTION_INIT(e_bulk_errors, -24381); BEGIN FORALL i IN 1..v_ids.COUNT SAVE EXCEPTIONS DELETE FROM employees WHERE employee_id = v_ids(i); EXCEPTION WHEN e_bulk_errors THEN FOR j IN 1..SQL%BULK_EXCEPTIONS.COUNT LOOP DBMS_OUTPUT.PUT_LINE('Error at ' || SQL%BULK_EXCEPTIONS(j).ERROR_INDEX || ': ' || SQLERRM(-SQL%BULK_EXCEPTIONS(j).ERROR_CODE)); END LOOP; END; / ```

8.3 FORALL with INDICES OF

FORALL i IN INDICES OF v_emp_ids

9. Stored Procedures
9.1 Creating Procedures
```sql CREATE OR REPLACE PROCEDURE hire_employee( p_first_name IN VARCHAR2, p_last_name IN VARCHAR2, p_email IN VARCHAR2, p_job_id IN VARCHAR2, p_salary IN NUMBER, p_department_id IN NUMBER, p_employee_id OUT NUMBER ) IS v_min_salary NUMBER; v_max_salary NUMBER; BEGIN -- Validate salary range SELECT min_salary, max_salary INTO v_min_salary, v_max_salary FROM jobs WHERE job_id = p_job_id;

IF p_salary < v_min_salary OR p_salary > v_max_salary THEN
    RAISE_APPLICATION_ERROR(-20001, 'Salary out of range for job');
END IF;

-- Generate ID and insert
SELECT employees_seq.NEXTVAL INTO p_employee_id FROM dual;

INSERT INTO employees (
    employee_id, first_name, last_name, email,
    hire_date, job_id, salary, department_id
) VALUES (
    p_employee_id, p_first_name, p_last_name, UPPER(p_email),
    SYSDATE, p_job_id, p_salary, p_department_id
);

COMMIT;
EXCEPTION WHEN NO_DATA_FOUND THEN RAISE_APPLICATION_ERROR(-20002, 'Invalid job_id'); WHEN DUP_VAL_ON_INDEX THEN RAISE_APPLICATION_ERROR(-20003, 'Email already exists'); END hire_employee; / ```

11. Oracle Packages
11.1 Package Structure
``` ┌─────────────────────────────────────────────────────────────────┐ │ ORACLE PACKAGE │ ├─────────────────────────────────────────────────────────────────┤ │ PACKAGE SPECIFICATION (Public Interface) │ │ • Public types, constants, exceptions │ │ • Public procedure/function headers │ ├─────────────────────────────────────────────────────────────────┤ │ PACKAGE BODY (Implementation) │ │ • Private types, variables │ │ • Private procedures/functions │ │ • Implementation of public items │ └─────────────────────────────────────────────────────────────────┘ ```

11.2 Package Specification
```sql CREATE OR REPLACE PACKAGE emp_mgmt AS -- Types TYPE t_emp_rec IS RECORD (employee_id NUMBER, name VARCHAR2(100), salary NUMBER); TYPE t_emp_tab IS TABLE OF t_emp_rec INDEX BY PLS_INTEGER;

-- Constants
c_max_salary CONSTANT NUMBER := 100000;

-- Exceptions
e_salary_exceeded EXCEPTION;

-- Procedures
PROCEDURE hire_employee(p_name VARCHAR2, p_salary NUMBER, p_emp_id OUT NUMBER);
PROCEDURE terminate_employee(p_emp_id NUMBER);

-- Functions
FUNCTION get_employee_count(p_dept_id NUMBER) RETURN NUMBER;
END emp_mgmt; / ```

11.3 Package Body
```sql CREATE OR REPLACE PACKAGE BODY emp_mgmt AS -- Private variable g_last_emp_id NUMBER;

-- Private procedure
PROCEDURE log_activity(p_emp_id NUMBER, p_action VARCHAR2) IS
    PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
    INSERT INTO activity_log VALUES (p_emp_id, p_action, SYSDATE, USER);
    COMMIT;
END;

-- Public implementations
PROCEDURE hire_employee(p_name VARCHAR2, p_salary NUMBER, p_emp_id OUT NUMBER) IS
BEGIN
    IF p_salary > c_max_salary THEN
        RAISE e_salary_exceeded;
    END IF;
    
    SELECT emp_seq.NEXTVAL INTO p_emp_id FROM dual;
    INSERT INTO employees (employee_id, employee_name, salary)
    VALUES (p_emp_id, p_name, p_salary);
    
    g_last_emp_id := p_emp_id;
    log_activity(p_emp_id, 'HIRE');
    COMMIT;
END;

PROCEDURE terminate_employee(p_emp_id NUMBER) IS
BEGIN
    UPDATE employees SET status = 'TERMINATED' WHERE employee_id = p_emp_id;
    log_activity(p_emp_id, 'TERMINATE');
    COMMIT;
END;

FUNCTION get_employee_count(p_dept_id NUMBER) RETURN NUMBER IS
    v_count NUMBER;
BEGIN
    SELECT COUNT(*) INTO v_count FROM employees
    WHERE department_id = p_dept_id AND status = 'ACTIVE';
    RETURN v_count;
END;
END emp_mgmt; / ```

12. Database Triggers
12.1 Trigger Types
Type	Timing	Use Case
BEFORE	Before DML	Validation, auto-fill
AFTER	After DML	Auditing, logging
INSTEAD OF	On views	Make views updatable
12.2 Row-Level Trigger
```sql CREATE OR REPLACE TRIGGER trg_salary_audit AFTER UPDATE OF salary ON employees FOR EACH ROW BEGIN INSERT INTO salary_audit ( employee_id, old_salary, new_salary, change_type, changed_by, changed_date ) VALUES ( :NEW.employee_id, :OLD.salary, :NEW.salary, CASE WHEN :NEW.salary > :OLD.salary THEN 'INCREASE' ELSE 'DECREASE' END, USER, SYSDATE ); END; / ```

12.3 BEFORE Trigger (Validation)
```sql CREATE OR REPLACE TRIGGER trg_employee_validation BEFORE INSERT OR UPDATE ON employees FOR EACH ROW DECLARE v_min_salary NUMBER; v_max_salary NUMBER; BEGIN SELECT min_salary, max_salary INTO v_min_salary, v_max_salary FROM jobs WHERE job_id = :NEW.job_id;

IF :NEW.salary < v_min_salary OR :NEW.salary > v_max_salary THEN
    RAISE_APPLICATION_ERROR(-20001, 'Salary out of range for job');
END IF;

:NEW.email := UPPER(:NEW.email);
:NEW.last_modified := SYSDATE;
END; / ```

12.4 Auto-Generate Primary Key
```sql CREATE OR REPLACE TRIGGER trg_employee_pk BEFORE INSERT ON employees FOR EACH ROW BEGIN IF :NEW.employee_id IS NULL THEN :NEW.employee_id := employees_seq.NEXTVAL; END IF; END; / ```

12.5 Compound Trigger
```sql CREATE OR REPLACE TRIGGER trg_salary_compound FOR UPDATE OF salary ON employees COMPOUND TRIGGER TYPE t_audit_tab IS TABLE OF salary_audit%ROWTYPE INDEX BY PLS_INTEGER; g_audits t_audit_tab; g_idx PLS_INTEGER := 0;

AFTER EACH ROW IS
BEGIN
    g_idx := g_idx + 1;
    g_audits(g_idx).employee_id := :NEW.employee_id;
    g_audits(g_idx).old_salary := :OLD.salary;
    g_audits(g_idx).new_salary := :NEW.salary;
END AFTER EACH ROW;

AFTER STATEMENT IS
BEGIN
    FORALL i IN 1..g_audits.COUNT
        INSERT INTO salary_audit VALUES g_audits(i);
END AFTER STATEMENT;
END; / ```

12.6 Trigger Management
```sql ALTER TRIGGER trg_salary_audit DISABLE; ALTER TRIGGER trg_salary_audit ENABLE; ALTER TABLE employees DISABLE ALL TRIGGERS; ALTER TABLE employees ENABLE ALL TRIGGERS; DROP TRIGGER trg_salary_audit; ```

13. Locking and Concurrency
13.1 SELECT FOR UPDATE
```sql DECLARE CURSOR c_employees IS SELECT employee_id, salary FROM employees WHERE department_id = 60 FOR UPDATE; BEGIN FOR emp IN c_employees LOOP UPDATE employees SET salary = emp.salary * 1.10 WHERE CURRENT OF c_employees; END LOOP; COMMIT; END; / ```

13.2 FOR UPDATE Options
```sql -- Don't wait if locked SELECT * FROM employees WHERE employee_id = 100 FOR UPDATE NOWAIT;

-- Wait up to 5 seconds SELECT * FROM employees WHERE employee_id = 100 FOR UPDATE WAIT 5;

-- Skip locked rows SELECT * FROM employees WHERE department_id = 60 FOR UPDATE SKIP LOCKED; ```

13.3 Deadlock Prevention
```sql CREATE OR REPLACE PROCEDURE transfer_funds( p_from_acct NUMBER, p_to_acct NUMBER, p_amount NUMBER ) IS v_balance NUMBER; BEGIN -- Always lock in consistent order (lower ID first) IF p_from_acct < p_to_acct THEN SELECT balance INTO v_balance FROM accounts WHERE account_id = p_from_acct FOR UPDATE NOWAIT; SELECT balance INTO v_balance FROM accounts WHERE account_id = p_to_acct FOR UPDATE NOWAIT; ELSE SELECT balance INTO v_balance FROM accounts WHERE account_id = p_to_acct FOR UPDATE NOWAIT; SELECT balance INTO v_balance FROM accounts WHERE account_id = p_from_acct FOR UPDATE NOWAIT; END IF;

UPDATE accounts SET balance = balance - p_amount WHERE account_id = p_from_acct;
UPDATE accounts SET balance = balance + p_amount WHERE account_id = p_to_acct;
COMMIT;
END; / ```

14. Transaction Management
14.1 Transaction Control
```sql BEGIN INSERT INTO orders VALUES (...); SAVEPOINT after_order;

INSERT INTO order_items VALUES (...);
SAVEPOINT after_items;

-- On error, can rollback to savepoint
ROLLBACK TO after_order;

COMMIT;  -- Make permanent
-- or ROLLBACK;  -- Undo all
END; / ```

14.2 Autonomous Transactions
```sql CREATE OR REPLACE PROCEDURE log_error(p_error_msg VARCHAR2) IS PRAGMA AUTONOMOUS_TRANSACTION; BEGIN INSERT INTO error_log VALUES (SYSDATE, p_error_msg, USER); COMMIT; -- Only commits this insert END; /

-- Usage - log persists even if main transaction rolls back BEGIN INSERT INTO orders VALUES (...); log_error('Order created'); -- Commits independently RAISE_APPLICATION_ERROR(-20001, 'Test error'); EXCEPTION WHEN OTHERS THEN log_error(SQLERRM); -- This log persists! ROLLBACK; -- Main transaction rolled back RAISE; END; / ```

15. PL/SQL Optimization Techniques
15.1 Use PLS_INTEGER
```sql -- Faster than NUMBER for integer operations DECLARE v_counter PLS_INTEGER := 0; BEGIN FOR i IN 1..1000000 LOOP v_counter := v_counter + 1; END LOOP; END; / ```

15.2 Use BULK Operations
```sql -- Slow: Row-by-row FOR emp IN (SELECT * FROM employees) LOOP UPDATE salary_history SET archived = 'Y' WHERE employee_id = emp.employee_id; END LOOP;

-- Fast: Bulk DECLARE TYPE t_ids IS TABLE OF NUMBER; v_ids t_ids; BEGIN SELECT employee_id BULK COLLECT INTO v_ids FROM employees; FORALL i IN 1..v_ids.COUNT UPDATE salary_history SET archived = 'Y' WHERE employee_id = v_ids(i); END; / ```

15.3 Use NOCOPY for Large Parameters
```sql -- Pass by reference, not value PROCEDURE process_data(p_large_collection IN OUT NOCOPY collection_type) ```

15.4 Use Result Cache
```sql CREATE OR REPLACE FUNCTION get_config(p_key VARCHAR2) RETURN VARCHAR2 RESULT_CACHE RELIES_ON (configuration) IS v_value VARCHAR2(4000); BEGIN SELECT config_value INTO v_value FROM configuration WHERE config_key = p_key; RETURN v_value; END; / ```

e_inventory_low EXCEPTION;

CREATE OR REPLACE PACKAGE BODY order_pkg AS

PROCEDURE log_order(p_order_id NUMBER, p_action VARCHAR2) IS
    PRAGMA AUTONOMOUS_TRANSACTION;
BEGIN
    INSERT INTO order_log VALUES (order_log_seq.NEXTVAL, p_order_id, p_action, SYSDATE, USER);
    COMMIT;
END;

PROCEDURE create_order(p_customer_id NUMBER, p_items t_items, p_order_id OUT NUMBER) IS
    v_total NUMBER := 0;
    v_available NUMBER;
BEGIN
    -- Check inventory
    FOR i IN 1..p_items.COUNT LOOP
        SELECT quantity_on_hand INTO v_available FROM products
        WHERE product_id = p_items(i).product_id;
        IF v_available < p_items(i).quantity THEN
            RAISE e_inventory_low;
        END IF;
    END LOOP;
    
    -- Create order
    SELECT order_seq.NEXTVAL INTO p_order_id FROM dual;
    INSERT INTO orders (order_id, customer_id, order_date, status)
    VALUES (p_order_id, p_customer_id, SYSDATE, 'PENDING');
    
    -- Add items
    FOR i IN 1..p_items.COUNT LOOP
        INSERT INTO order_items VALUES (
            item_seq.NEXTVAL, p_order_id, p_items(i).product_id,
            p_items(i).quantity, p_items(i).price
        );
        UPDATE products SET quantity_on_hand = quantity_on_hand - p_items(i).quantity
        WHERE product_id = p_items(i).product_id;
        v_total := v_total + (p_items(i).quantity * p_items(i).price);
    END LOOP;
    
    UPDATE orders SET total_amount = v_total WHERE order_id = p_order_id;
    log_order(p_order_id, 'CREATED');
    COMMIT;
END;

PROCEDURE cancel_order(p_order_id NUMBER, p_reason VARCHAR2) IS
BEGIN
    -- Restore inventory
    FOR item IN (SELECT product_id, quantity FROM order_items WHERE order_id = p_order_id)
    LOOP
        UPDATE products SET quantity_on_hand = quantity_on_hand + item.quantity
        WHERE product_id = item.product_id;
    END LOOP;
    
    UPDATE orders SET status = 'CANCELLED' WHERE order_id = p_order_id;
    log_order(p_order_id, 'CANCELLED: ' || p_reason);
    COMMIT;
END;

FUNCTION get_order_total(p_order_id NUMBER) RETURN NUMBER IS
    v_total NUMBER;
BEGIN
    SELECT NVL(SUM(quantity * unit_price), 0) INTO v_total
    FROM order_items WHERE order_id = p_order_id;
    RETURN v_total;
END;
END order_pkg; / ```

1.1 What Are Stored Procedures?
A stored procedure is a named PL/SQL block compiled and stored in the database that:

Performs a specific business operation
Accepts input parameters and can return output values
Is compiled once and executed many times
Provides security through controlled access to data

    -- Executable section

    -- Exception handlers]

1.3 Parameter Modes
IN Parameters (Default)
/*
 * IN parameters: Pass values INTO the procedure
 * - Read-only within procedure
 * - Can have default values
 */
CREATE OR REPLACE PROCEDURE display_employee(
    p_employee_id IN NUMBER,
    p_format      IN VARCHAR2 DEFAULT 'FULL'
)
IS
    v_emp employees%ROWTYPE;
BEGIN
    SELECT * INTO v_emp FROM employees WHERE employee_id = p_employee_id;
    
    CASE p_format
        WHEN 'FULL' THEN
            DBMS_OUTPUT.PUT_LINE('ID: ' || v_emp.employee_id);
            DBMS_OUTPUT.PUT_LINE('Name: ' || v_emp.first_name || ' ' || v_emp.last_name);
            DBMS_OUTPUT.PUT_LINE('Salary: $' || v_emp.salary);
        WHEN 'BRIEF' THEN
            DBMS_OUTPUT.PUT_LINE(v_emp.first_name || ' ' || v_emp.last_name);
    END CASE;
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        DBMS_OUTPUT.PUT_LINE('Employee ' || p_employee_id || ' not found');
END display_employee;
/
OUT Parameters
/*
 * OUT parameters: Return values FROM the procedure
 * - Write-only (initial value ignored)
 * - Must be assigned before procedure ends
 */
CREATE OR REPLACE PROCEDURE get_employee_stats(
    p_department_id IN  NUMBER,
    p_emp_count     OUT NUMBER,
    p_total_salary  OUT NUMBER,
    p_avg_salary    OUT NUMBER
)
IS
BEGIN
    SELECT COUNT(*), NVL(SUM(salary), 0), NVL(AVG(salary), 0)
    INTO p_emp_count, p_total_salary, p_avg_salary
    FROM employees
    WHERE department_id = p_department_id;
END get_employee_stats;

 * IN OUT parameters: Pass value in, modify, return
 */
CREATE OR REPLACE PROCEDURE format_phone_number(
    p_phone IN OUT VARCHAR2
)
IS
    v_digits VARCHAR2(20);
BEGIN
    v_digits := REGEXP_REPLACE(p_phone, '[^0-9]', '');
    
    CASE LENGTH(v_digits)
        WHEN 10 THEN
            p_phone := '(' || SUBSTR(v_digits, 1, 3) || ') ' ||
                       SUBSTR(v_digits, 4, 3) || '-' ||
                       SUBSTR(v_digits, 7, 4);
        WHEN 11 THEN
            p_phone := '+' || SUBSTR(v_digits, 1, 1) || ' (' ||
                       SUBSTR(v_digits, 2, 3) || ') ' ||
                       SUBSTR(v_digits, 5, 3) || '-' ||
                       SUBSTR(v_digits, 8, 4);
        ELSE
            p_phone := v_digits;
    END CASE;
END format_phone_number;

1.7 Real-World Example: Employee Transfer
CREATE OR REPLACE PROCEDURE transfer_employee(
    p_employee_id       IN  NUMBER,
    p_new_department_id IN  NUMBER,
    p_new_manager_id    IN  NUMBER   DEFAULT NULL,
    p_effective_date    IN  DATE     DEFAULT SYSDATE,
    p_old_department_id OUT NUMBER,
    p_success           OUT BOOLEAN,
    p_message           OUT VARCHAR2
)
IS
    e_employee_not_found   EXCEPTION;
    e_department_not_found EXCEPTION;
BEGIN
    p_success := FALSE;
    
    -- Get current department
    SELECT department_id INTO p_old_department_id
    FROM employees WHERE employee_id = p_employee_id;
    
    -- Validate new department
    DECLARE
        v_count NUMBER;
    BEGIN
        SELECT COUNT(*) INTO v_count FROM departments
        WHERE department_id = p_new_department_id;
        IF v_count = 0 THEN RAISE e_department_not_found; END IF;
    END;
    
    -- Perform transfer
    UPDATE employees
    SET department_id = p_new_department_id,
        manager_id = NVL(p_new_manager_id, manager_id)
    WHERE employee_id = p_employee_id;
    
    -- Log transfer
    INSERT INTO employee_transfer_history VALUES (
        transfer_seq.NEXTVAL, p_employee_id, p_old_department_id,
        p_new_department_id, p_effective_date, USER
    );
    
    COMMIT;
    p_success := TRUE;
    p_message := 'Transfer completed successfully';
    
EXCEPTION
    WHEN NO_DATA_FOUND THEN
        p_message := 'Employee not found';
    WHEN e_department_not_found THEN
        p_message := 'Department not found';
    WHEN OTHERS THEN
        p_message := 'Error: ' || SQLERRM;
        ROLLBACK;
END transfer_employee;
/

)
RETURN NUMBER
IS

CREATE OR REPLACE FUNCTION get_employee_bonus(p_employee_id IN NUMBER)
RETURN NUMBER
IS
    v_salary        NUMBER;
    v_years_service NUMBER;
    v_bonus         NUMBER;
BEGIN
    SELECT salary, TRUNC(MONTHS_BETWEEN(SYSDATE, hire_date) / 12)
    INTO v_salary, v_years_service
    FROM employees WHERE employee_id = p_employee_id;
    
    v_bonus := v_salary * 0.05 * (1 + LEAST(v_years_service, 10) * 0.02);
    RETURN ROUND(v_bonus, 2);
EXCEPTION
    WHEN NO_DATA_FOUND THEN RETURN NULL;
END get_employee_bonus;

2.4 Function Purity Levels

 * - Oracle can cache results
 * - Required for function-based indexes

CREATE OR REPLACE FUNCTION format_currency(
    p_amount   IN NUMBER,
    p_currency IN VARCHAR2 DEFAULT 'USD'
)
RETURN VARCHAR2
DETERMINISTIC
IS
BEGIN
    RETURN CASE p_currency
        WHEN 'USD' THEN '$'
        WHEN 'EUR' THEN '€'
        WHEN 'GBP' THEN '£'
        ELSE p_currency || ' '
    END || TO_CHAR(p_amount, '999,999,999.00');
END format_currency;

2.6 Pipelined Table Functions
CREATE OR REPLACE TYPE emp_summary_rec AS OBJECT (
    department_name VARCHAR2(50),
    employee_count  NUMBER,
    total_salary    NUMBER
);
/
CREATE OR REPLACE TYPE emp_summary_tab AS TABLE OF emp_summary_rec;
/

CREATE OR REPLACE FUNCTION get_department_summaries(p_min_employees IN NUMBER DEFAULT 1)
RETURN emp_summary_tab
PIPELINED
IS
BEGIN
    FOR dept IN (
        SELECT d.department_name, COUNT(e.employee_id) AS emp_count, NVL(SUM(e.salary), 0) AS total_sal
        FROM departments d LEFT JOIN employees e ON d.department_id = e.department_id
        GROUP BY d.department_name
        HAVING COUNT(e.employee_id) >= p_min_employees
    )
    LOOP
        PIPE ROW (emp_summary_rec(dept.department_name, dept.emp_count, dept.total_sal));
    END LOOP;
    RETURN;
END;

CREATE OR REPLACE PACKAGE customer_mgmt AS

    TYPE customer_rec IS RECORD (

    TYPE customer_tab IS TABLE OF customer_rec INDEX BY PLS_INTEGER;
    
    -- Constants
    c_status_active   CONSTANT VARCHAR2(20) := 'ACTIVE';
    c_status_inactive CONSTANT VARCHAR2(20) := 'INACTIVE';
    c_max_credit      CONSTANT NUMBER := 100000;
    
    -- Exceptions
    e_customer_not_found   EXCEPTION;
    e_duplicate_customer   EXCEPTION;
    e_invalid_credit_limit EXCEPTION;
    
    -- Procedures
    PROCEDURE create_customer(

        p_email       IN  VARCHAR2,
        p_credit_limit IN NUMBER DEFAULT 1000,
        p_customer_id OUT NUMBER
    );
    
    PROCEDURE update_customer(
        p_customer_id IN NUMBER,
        p_name        IN VARCHAR2 DEFAULT NULL,
        p_email       IN VARCHAR2 DEFAULT NULL
    );
    
    -- Functions
    FUNCTION get_customer(p_customer_id IN NUMBER) RETURN customer_rec;

    FUNCTION search_customers(p_name_pattern IN VARCHAR2) RETURN customer_tab;
    
END customer_mgmt;
/
3.3 Package Body
CREATE OR REPLACE PACKAGE BODY customer_mgmt AS
    -- Private variables
    g_last_customer_id NUMBER;
    
    -- Private procedure
    PROCEDURE log_activity(p_customer_id NUMBER, p_action VARCHAR2) IS
        PRAGMA AUTONOMOUS_TRANSACTION;
    BEGIN
        INSERT INTO customer_activity_log VALUES (
            activity_seq.NEXTVAL, p_customer_id, p_action, SYSTIMESTAMP, USER
        );
        COMMIT;
    END;
    
    -- Private function
    FUNCTION is_valid_email(p_email VARCHAR2) RETURN BOOLEAN IS
    BEGIN
        RETURN REGEXP_LIKE(p_email, '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$');
    END;
    
    -- Public implementations
    PROCEDURE create_customer(
        p_name        IN  VARCHAR2,
        p_email       IN  VARCHAR2,
        p_credit_limit IN NUMBER DEFAULT 1000,
        p_customer_id OUT NUMBER
    ) IS
    BEGIN
        IF NOT is_valid_email(p_email) THEN
            RAISE_APPLICATION_ERROR(-20001, 'Invalid email format');
        END IF;
        
        IF p_credit_limit > c_max_credit THEN
            RAISE e_invalid_credit_limit;
        END IF;
        
        SELECT customer_seq.NEXTVAL INTO p_customer_id FROM dual;
        
        INSERT INTO customers VALUES (
            p_customer_id, p_name, LOWER(p_email), p_credit_limit, c_status_active, SYSDATE, USER
        );
        
        g_last_customer_id := p_customer_id;
        log_activity(p_customer_id, 'CREATE');
        COMMIT;
    END;
    
    PROCEDURE update_customer(
        p_customer_id IN NUMBER,
        p_name        IN VARCHAR2 DEFAULT NULL,
        p_email       IN VARCHAR2 DEFAULT NULL
    ) IS
    BEGIN
        UPDATE customers
        SET customer_name = NVL(p_name, customer_name),
            email = NVL(LOWER(p_email), email)
        WHERE customer_id = p_customer_id;
        
        IF SQL%ROWCOUNT = 0 THEN RAISE e_customer_not_found; END IF;
        
        log_activity(p_customer_id, 'UPDATE');
        COMMIT;
    END;
    
    FUNCTION get_customer(p_customer_id IN NUMBER) RETURN customer_rec IS
        v_customer customer_rec;
    BEGIN
        SELECT customer_id, customer_name, email, credit_limit, status
        INTO v_customer
        FROM customers WHERE customer_id = p_customer_id;
        RETURN v_customer;
    EXCEPTION
        WHEN NO_DATA_FOUND THEN RAISE e_customer_not_found;
    END;
    
    FUNCTION is_customer_active(p_customer_id IN NUMBER) RETURN BOOLEAN IS
        v_status VARCHAR2(20);
    BEGIN
        SELECT status INTO v_status FROM customers WHERE customer_id = p_customer_id;
        RETURN v_status = c_status_active;
    EXCEPTION
        WHEN NO_DATA_FOUND THEN RETURN FALSE;
    END;
    
    FUNCTION search_customers(p_name_pattern IN VARCHAR2) RETURN customer_tab IS
        v_results customer_tab;
        v_idx PLS_INTEGER := 0;
    BEGIN
        FOR cust IN (
            SELECT customer_id, customer_name, email, credit_limit, status
            FROM customers
            WHERE UPPER(customer_name) LIKE UPPER('%' || p_name_pattern || '%')
        )
        LOOP
            v_idx := v_idx + 1;
            v_results(v_idx) := cust;
        END LOOP;
        RETURN v_results;
    END;
    
-- Package initialization
BEGIN
    g_last_customer_id := 0;
END customer_mgmt;
/

4.1 Trigger Types
Type	When	Use Case
BEFORE	Before DML	Validation, auto-fill
AFTER	After DML	Auditing, logging
INSTEAD OF	Instead of DML on view	Make views updatable
4.2 Row-Level vs Statement-Level

4.4 BEFORE Trigger for Validation
CREATE OR REPLACE TRIGGER trg_employee_validation
BEFORE INSERT OR UPDATE ON employees
FOR EACH ROW
DECLARE
    v_min_salary NUMBER;
    v_max_salary NUMBER;
BEGIN
    -- Auto-generate PK
    IF INSERTING AND :NEW.employee_id IS NULL THEN
        :NEW.employee_id := employee_seq.NEXTVAL;
    END IF;
    
    -- Set timestamps
    IF INSERTING THEN
        :NEW.created_date := SYSDATE;
        :NEW.created_by := USER;
    END IF;
    :NEW.modified_date := SYSDATE;
    :NEW.modified_by := USER;
    
    -- Validate salary
    SELECT min_salary, max_salary INTO v_min_salary, v_max_salary
    FROM jobs WHERE job_id = :NEW.job_id;
    
    IF :NEW.salary NOT BETWEEN v_min_salary AND v_max_salary THEN
        RAISE_APPLICATION_ERROR(-20001, 'Salary out of range for job');
    END IF;
    
    -- Standardize email
    :NEW.email := LOWER(TRIM(:NEW.email));
END;

    TYPE emp_id_tab IS TABLE OF NUMBER;

            );

/*
 * Use Compound Trigger to avoid mutating table error
 */
CREATE OR REPLACE TRIGGER trg_check_budget
FOR UPDATE OF salary ON employees
COMPOUND TRIGGER
    TYPE dept_tab IS TABLE OF NUMBER INDEX BY PLS_INTEGER;
    g_depts dept_tab;
    
    AFTER EACH ROW IS
    BEGIN
        g_depts(:NEW.department_id) := 1;
    END AFTER EACH ROW;
    
    AFTER STATEMENT IS
        v_dept_id NUMBER;
        v_total NUMBER;
        v_budget NUMBER;
    BEGIN
        v_dept_id := g_depts.FIRST;
        WHILE v_dept_id IS NOT NULL LOOP
            SELECT SUM(salary) INTO v_total FROM employees WHERE department_id = v_dept_id;
            SELECT budget INTO v_budget FROM departments WHERE department_id = v_dept_id;
            IF v_total > v_budget THEN
                RAISE_APPLICATION_ERROR(-20001, 'Department ' || v_dept_id || ' budget exceeded');
            END IF;
            v_dept_id := g_depts.NEXT(v_dept_id);
        END LOOP;
    END AFTER STATEMENT;
END;

5. Locking and Concurrency
5.1 Oracle's Implicit Locking
/*
 * Oracle automatically acquires locks for DML operations
 * - Row-level locks (TX): Protect individual rows
 * - Table-level locks (TM): Protect table structure
 */

-- Session 1: Update creates row lock
UPDATE employees SET salary = 50000 WHERE employee_id = 100;
-- Row 100 is locked until COMMIT/ROLLBACK

-- Session 2: Reading is never blocked
SELECT salary FROM employees WHERE employee_id = 100;  -- Returns OLD value

-- Session 2: Trying to update same row blocks
UPDATE employees SET salary = 55000 WHERE employee_id = 100;  -- WAITS
5.2 SELECT FOR UPDATE
DECLARE
    CURSOR c_employees IS
        SELECT employee_id, salary FROM employees
        WHERE department_id = 60
        FOR UPDATE;  -- Lock all selected rows
BEGIN
    FOR emp IN c_employees LOOP
        UPDATE employees SET salary = emp.salary * 1.10
        WHERE CURRENT OF c_employees;
    END LOOP;
    COMMIT;
END;
/

-- Lock specific columns
SELECT * FROM employees WHERE employee_id = 100 FOR UPDATE OF salary;
5.3 NOWAIT and WAIT Options
-- NOWAIT: Fail immediately if locked
DECLARE
    e_resource_busy EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_resource_busy, -54);
BEGIN
    SELECT * FROM employees WHERE employee_id = 100 FOR UPDATE NOWAIT;
EXCEPTION
    WHEN e_resource_busy THEN
        DBMS_OUTPUT.PUT_LINE('Row is locked');
END;
/

-- WAIT n: Wait up to n seconds
SELECT * FROM employees WHERE employee_id = 100 FOR UPDATE WAIT 5;
5.4 SKIP LOCKED for Queue Processing
/*
 * SKIP LOCKED: Process only unlocked rows
 * Perfect for multi-consumer queue processing
 */
CREATE OR REPLACE PROCEDURE process_next_job
IS
    CURSOR c_pending IS
        SELECT job_id, job_type, job_data
        FROM job_queue
        WHERE status = 'PENDING'
        ORDER BY priority
        FOR UPDATE SKIP LOCKED;
    
    v_job c_pending%ROWTYPE;
BEGIN
    OPEN c_pending;
    FETCH c_pending INTO v_job;
    
    IF c_pending%FOUND THEN
        UPDATE job_queue SET status = 'PROCESSING'
        WHERE CURRENT OF c_pending;
        COMMIT;
        
        -- Process job...
        
        UPDATE job_queue SET status = 'COMPLETED'
        WHERE job_id = v_job.job_id;
        COMMIT;
    END IF;
    
    CLOSE c_pending;
END;
/
5.5 Deadlock Detection and Prevention
/*
 * DEADLOCK occurs when:
 * Session 1: Locks row A, wants row B
 * Session 2: Locks row B, wants row A
 * Oracle automatically detects and rolls back one session
 */

/*
 * PREVENTION STRATEGY 1: Lock resources in consistent order
 */
CREATE OR REPLACE PROCEDURE transfer_funds(
    p_from_account IN NUMBER,
    p_to_account   IN NUMBER,
    p_amount       IN NUMBER
)
IS
    v_from_balance NUMBER;
    v_to_balance   NUMBER;
    v_first_acct   NUMBER;
    v_second_acct  NUMBER;
    
    e_insufficient_funds EXCEPTION;
BEGIN
    -- Always lock in account_id order to prevent deadlocks
    IF p_from_account < p_to_account THEN
        v_first_acct := p_from_account;
        v_second_acct := p_to_account;
    ELSE
        v_first_acct := p_to_account;
        v_second_acct := p_from_account;
    END IF;
    
    -- Lock first account
    SELECT balance INTO v_from_balance
    FROM accounts WHERE account_id = v_first_acct
    FOR UPDATE;
    
    -- Lock second account
    SELECT balance INTO v_to_balance
    FROM accounts WHERE account_id = v_second_acct
    FOR UPDATE;
    
    -- Now get actual balances in correct order
    IF v_first_acct = p_from_account THEN
        -- v_from_balance already has from account
        NULL;
    ELSE
        -- Swap values
        v_to_balance := v_from_balance;
        SELECT balance INTO v_from_balance
        FROM accounts WHERE account_id = p_from_account;
    END IF;
    
    -- Check sufficient funds
    IF v_from_balance < p_amount THEN
        RAISE e_insufficient_funds;
    END IF;
    
    -- Perform transfer
    UPDATE accounts SET balance = balance - p_amount
    WHERE account_id = p_from_account;
    
    UPDATE accounts SET balance = balance + p_amount
    WHERE account_id = p_to_account;
    
    -- Log transaction
    INSERT INTO transfer_log (from_account, to_account, amount, transfer_date)
    VALUES (p_from_account, p_to_account, p_amount, SYSDATE);
    
    COMMIT;
    
EXCEPTION
    WHEN e_insufficient_funds THEN
        ROLLBACK;
        RAISE_APPLICATION_ERROR(-20001, 'Insufficient funds in account ' || p_from_account);
END transfer_funds;
/

/*
 * PREVENTION STRATEGY 2: Use NOWAIT with retry logic
 */
CREATE OR REPLACE PROCEDURE update_with_retry(
    p_employee_id IN NUMBER,
    p_new_salary  IN NUMBER,
    p_max_retries IN NUMBER DEFAULT 3
)
IS
    v_retries NUMBER := 0;
    v_locked  BOOLEAN := TRUE;
    e_resource_busy EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_resource_busy, -54);
BEGIN
    WHILE v_locked AND v_retries < p_max_retries LOOP
        BEGIN
            UPDATE employees
            SET salary = p_new_salary
            WHERE employee_id = p_employee_id;
            
            v_locked := FALSE;
            COMMIT;
            
        EXCEPTION
            WHEN e_resource_busy THEN
                v_retries := v_retries + 1;
                DBMS_OUTPUT.PUT_LINE('Retry ' || v_retries || ' - row locked');
                DBMS_LOCK.SLEEP(POWER(2, v_retries));  -- Exponential backoff
        END;
    END LOOP;
    
    IF v_locked THEN
        RAISE_APPLICATION_ERROR(-20002, 'Failed to acquire lock after ' || p_max_retries || ' retries');
    END IF;
END update_with_retry;
/
5.6 Transaction Isolation Levels
/*
 * Oracle supports two isolation levels:
 * 1. READ COMMITTED (default) - sees committed data as of statement start
 * 2. SERIALIZABLE - sees committed data as of transaction start
 */

-- Set isolation level for session
ALTER SESSION SET ISOLATION_LEVEL = SERIALIZABLE;

-- Set isolation level for transaction
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

/*
 * SERIALIZABLE example: Report generation
 */
CREATE OR REPLACE PROCEDURE generate_consistent_report
IS
BEGIN
    -- Start serializable transaction
    SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    
    -- All queries see data as of this point
    INSERT INTO report_data
    SELECT 'SALES', SUM(amount) FROM sales;
    
    INSERT INTO report_data
    SELECT 'EXPENSES', SUM(amount) FROM expenses;
    
    -- Even if other sessions modify data, we see consistent snapshot
    INSERT INTO report_data
    SELECT 'PROFIT', 
           (SELECT SUM(amount) FROM sales) - 
           (SELECT SUM(amount) FROM expenses)
    FROM dual;
    
    COMMIT;
    
EXCEPTION
    WHEN OTHERS THEN
        ROLLBACK;
        RAISE;
END generate_consistent_report;
/

/*
 * Handle serialization failure
 */
DECLARE
    e_serialization_failure EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_serialization_failure, -8177);  -- ORA-08177
BEGIN
    SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    
    -- Perform operations...
    UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 100;
    
    COMMIT;
    
EXCEPTION
    WHEN e_serialization_failure THEN
        ROLLBACK;
        -- Retry the transaction
        DBMS_OUTPUT.PUT_LINE('Serialization failure - retry needed');
END;

6. Dynamic SQL
6.1 Why Use Dynamic SQL?
Dynamic SQL is needed when:

Table or column names are not known until runtime
DDL statements need to be executed from PL/SQL
SQL statements are built based on user input
Performance requires dynamically optimized queries
6.2 Native Dynamic SQL with EXECUTE IMMEDIATE
/*
 * Basic EXECUTE IMMEDIATE
 */

    v_table_name VARCHAR2(30) := 'EMPLOYEES';
    v_count NUMBER;

    DBMS_OUTPUT.PUT_LINE('Count: ' || v_count);

/

/*
 * DDL execution
 */
CREATE OR REPLACE PROCEDURE create_archive_table(
    p_source_table IN VARCHAR2,
    p_archive_suffix IN VARCHAR2 DEFAULT '_ARCHIVE'
)
IS
    v_archive_table VARCHAR2(61);
    v_sql VARCHAR2(4000);
BEGIN
    v_archive_table := p_source_table || p_archive_suffix;
    
    -- Drop if exists
    BEGIN
        EXECUTE IMMEDIATE 'DROP TABLE ' || v_archive_table || ' PURGE';
    EXCEPTION
        WHEN OTHERS THEN
            IF SQLCODE != -942 THEN  -- Table doesn't exist
                RAISE;
            END IF;
    END;
    
    -- Create archive table
    v_sql := 'CREATE TABLE ' || v_archive_table || ' AS ' ||
             'SELECT t.*, SYSDATE AS archived_date FROM ' || p_source_table || ' t WHERE 1=0';
    EXECUTE IMMEDIATE v_sql;
    
    DBMS_OUTPUT.PUT_LINE('Created table: ' || v_archive_table);
END create_archive_table;
/

/*
 * DML with RETURNING clause
 */
DECLARE
    v_sql VARCHAR2(200);
    v_new_id NUMBER;
    v_new_name VARCHAR2(100);
BEGIN
    v_sql := 'INSERT INTO employees (employee_id, first_name, last_name, email, hire_date, job_id) ' ||
             'VALUES (employee_seq.NEXTVAL, :1, :2, :3, SYSDATE, :4) ' ||
             'RETURNING employee_id, first_name || '' '' || last_name INTO :5, :6';
    
    EXECUTE IMMEDIATE v_sql
    USING 'John', 'Smith', 'jsmith@email.com', 'IT_PROG'
    RETURNING INTO v_new_id, v_new_name;
    
    DBMS_OUTPUT.PUT_LINE('Created: ' || v_new_id || ' - ' || v_new_name);
    COMMIT;
END;

6.3 Bind Variables and SQL Injection Prevention
/*
 * DANGEROUS: String concatenation allows SQL injection
 */
CREATE OR REPLACE PROCEDURE search_employees_UNSAFE(
    p_name IN VARCHAR2
)
IS
    v_sql VARCHAR2(4000);
    v_count NUMBER;
BEGIN
    -- NEVER DO THIS - vulnerable to SQL injection!
    v_sql := 'SELECT COUNT(*) FROM employees WHERE last_name = ''' || p_name || '''';
    EXECUTE IMMEDIATE v_sql INTO v_count;
    -- Attacker could pass: Smith' OR '1'='1
END;
/

/*
 * SAFE: Use bind variables
 */
CREATE OR REPLACE PROCEDURE search_employees_SAFE(
    p_name IN VARCHAR2,
    p_results OUT SYS_REFCURSOR
)
IS
    v_sql VARCHAR2(4000);
BEGIN
    v_sql := 'SELECT employee_id, first_name, last_name, salary ' ||
             'FROM employees WHERE last_name = :name';
    
    OPEN p_results FOR v_sql USING p_name;  -- Bind variable - SAFE
END search_employees_SAFE;

/*
 * Dynamic WHERE clause with bind variables
 */
CREATE OR REPLACE PROCEDURE dynamic_search(
    p_department_id IN NUMBER   DEFAULT NULL,
    p_min_salary    IN NUMBER   DEFAULT NULL,
    p_job_id        IN VARCHAR2 DEFAULT NULL,
    p_results       OUT SYS_REFCURSOR
)
IS
    v_sql VARCHAR2(4000);
    v_where VARCHAR2(2000) := ' WHERE 1=1';
    
    TYPE bind_tab IS TABLE OF VARCHAR2(100) INDEX BY PLS_INTEGER;
    v_binds bind_tab;
    v_bind_idx PLS_INTEGER := 0;
BEGIN
    v_sql := 'SELECT employee_id, first_name, last_name, salary, department_id, job_id FROM employees';
    
    IF p_department_id IS NOT NULL THEN
        v_bind_idx := v_bind_idx + 1;
        v_where := v_where || ' AND department_id = :b' || v_bind_idx;
        v_binds(v_bind_idx) := p_department_id;
    END IF;
    
    IF p_min_salary IS NOT NULL THEN
        v_bind_idx := v_bind_idx + 1;
        v_where := v_where || ' AND salary >= :b' || v_bind_idx;
        v_binds(v_bind_idx) := p_min_salary;
    END IF;
    
    IF p_job_id IS NOT NULL THEN
        v_bind_idx := v_bind_idx + 1;
        v_where := v_where || ' AND job_id = :b' || v_bind_idx;
        v_binds(v_bind_idx) := p_job_id;
    END IF;
    
    v_sql := v_sql || v_where || ' ORDER BY last_name, first_name';
    
    -- Open cursor with dynamic binds
    CASE v_bind_idx
        WHEN 0 THEN OPEN p_results FOR v_sql;
        WHEN 1 THEN OPEN p_results FOR v_sql USING v_binds(1);
        WHEN 2 THEN OPEN p_results FOR v_sql USING v_binds(1), v_binds(2);
        WHEN 3 THEN OPEN p_results FOR v_sql USING v_binds(1), v_binds(2), v_binds(3);
    END CASE;
END dynamic_search;

/*
 * Dynamic cursor with OPEN FOR

CREATE OR REPLACE PROCEDURE generate_dynamic_report(
    p_table_name  IN VARCHAR2,
    p_column_list IN VARCHAR2,
    p_where_clause IN VARCHAR2 DEFAULT NULL,
    p_order_by    IN VARCHAR2 DEFAULT NULL
)
IS
    v_sql VARCHAR2(4000);
    v_cursor SYS_REFCURSOR;
    v_col_value VARCHAR2(4000);
    
    -- For describing columns
    v_cursor_id INTEGER;
    v_col_cnt INTEGER;
    v_desc_tab DBMS_SQL.DESC_TAB;
BEGIN
    -- Build SQL
    v_sql := 'SELECT ' || p_column_list || ' FROM ' || p_table_name;
    
    IF p_where_clause IS NOT NULL THEN
        v_sql := v_sql || ' WHERE ' || p_where_clause;
    END IF;
    
    IF p_order_by IS NOT NULL THEN
        v_sql := v_sql || ' ORDER BY ' || p_order_by;
    END IF;
    
    DBMS_OUTPUT.PUT_LINE('Executing: ' || v_sql);
    DBMS_OUTPUT.PUT_LINE(RPAD('-', 60, '-'));
    
    -- Use DBMS_SQL to handle unknown columns
    v_cursor_id := DBMS_SQL.OPEN_CURSOR;
    DBMS_SQL.PARSE(v_cursor_id, v_sql, DBMS_SQL.NATIVE);
    DBMS_SQL.DESCRIBE_COLUMNS(v_cursor_id, v_col_cnt, v_desc_tab);
    
    -- Define columns
    FOR i IN 1..v_col_cnt LOOP
        DBMS_SQL.DEFINE_COLUMN(v_cursor_id, i, v_col_value, 4000);
    END LOOP;
    
    -- Execute and fetch
    IF DBMS_SQL.EXECUTE(v_cursor_id) >= 0 THEN
        WHILE DBMS_SQL.FETCH_ROWS(v_cursor_id) > 0 LOOP
            FOR i IN 1..v_col_cnt LOOP
                DBMS_SQL.COLUMN_VALUE(v_cursor_id, i, v_col_value);
                DBMS_OUTPUT.PUT(RPAD(NVL(v_col_value, 'NULL'), 20));
            END LOOP;
            DBMS_OUTPUT.NEW_LINE;
        END LOOP;
    END IF;
    
    DBMS_SQL.CLOSE_CURSOR(v_cursor_id);
    
EXCEPTION
    WHEN OTHERS THEN
        IF DBMS_SQL.IS_OPEN(v_cursor_id) THEN
            DBMS_SQL.CLOSE_CURSOR(v_cursor_id);
        END IF;
        RAISE;
END generate_dynamic_report;
/

        p_table_name  => 'EMPLOYEES',
        p_column_list => 'employee_id, first_name, last_name, salary',
        p_where_clause => 'department_id = 60',
        p_order_by    => 'salary DESC'
    );
END;

/*
 * Dynamic pivot table generator
 */
CREATE OR REPLACE PROCEDURE generate_pivot_report(
    p_base_table    IN VARCHAR2,
    p_pivot_column  IN VARCHAR2,
    p_value_column  IN VARCHAR2,
    p_group_column  IN VARCHAR2
)
IS
    v_cursor_id     INTEGER;
    v_sql           VARCHAR2(32767);
    v_pivot_values  VARCHAR2(4000);
    v_dummy         INTEGER;
BEGIN
    -- Get distinct pivot values
    v_cursor_id := DBMS_SQL.OPEN_CURSOR;
    DBMS_SQL.PARSE(v_cursor_id, 
        'SELECT DISTINCT ' || p_pivot_column || ' FROM ' || p_base_table || ' ORDER BY 1',
        DBMS_SQL.NATIVE);
    DBMS_SQL.DEFINE_COLUMN(v_cursor_id, 1, v_pivot_values, 100);
    v_dummy := DBMS_SQL.EXECUTE(v_cursor_id);
    
    v_pivot_values := '';
    WHILE DBMS_SQL.FETCH_ROWS(v_cursor_id) > 0 LOOP
        DECLARE
            v_val VARCHAR2(100);
        BEGIN
            DBMS_SQL.COLUMN_VALUE(v_cursor_id, 1, v_val);
            IF v_pivot_values IS NOT NULL THEN
                v_pivot_values := v_pivot_values || ', ';
            END IF;
            v_pivot_values := v_pivot_values || '''' || v_val || '''';
        END;
    END LOOP;
    DBMS_SQL.CLOSE_CURSOR(v_cursor_id);
    
    -- Build pivot query
    v_sql := 'SELECT * FROM (' ||
             '  SELECT ' || p_group_column || ', ' || p_pivot_column || ', ' || p_value_column ||
             '  FROM ' || p_base_table ||
             ') PIVOT (' ||
             '  SUM(' || p_value_column || ')' ||
             '  FOR ' || p_pivot_column || ' IN (' || v_pivot_values || ')' ||
             ')';
    
    DBMS_OUTPUT.PUT_LINE('Generated SQL:');
    DBMS_OUTPUT.PUT_LINE(v_sql);
    
EXCEPTION
    WHEN OTHERS THEN
        IF DBMS_SQL.IS_OPEN(v_cursor_id) THEN
            DBMS_SQL.CLOSE_CURSOR(v_cursor_id);
        END IF;
        RAISE;
END generate_pivot_report;

/*
 * Bulk insert with dynamic SQL
 */
CREATE OR REPLACE PROCEDURE bulk_insert_dynamic(
    p_target_table IN VARCHAR2,
    p_source_query IN VARCHAR2,
    p_batch_size   IN NUMBER DEFAULT 1000
)
IS
    v_cursor_id   INTEGER;
    v_insert_sql  VARCHAR2(4000);
    v_desc_tab    DBMS_SQL.DESC_TAB;
    v_col_cnt     INTEGER;
    v_col_list    VARCHAR2(4000);
    v_bind_list   VARCHAR2(4000);
    v_rows        INTEGER;
    v_total_rows  INTEGER := 0;
    
    TYPE varchar_tab IS TABLE OF VARCHAR2(4000) INDEX BY PLS_INTEGER;
    v_values varchar_tab;
BEGIN
    -- Parse source query to get columns
    v_cursor_id := DBMS_SQL.OPEN_CURSOR;
    DBMS_SQL.PARSE(v_cursor_id, p_source_query, DBMS_SQL.NATIVE);
    DBMS_SQL.DESCRIBE_COLUMNS(v_cursor_id, v_col_cnt, v_desc_tab);
    
    -- Build column and bind lists
    FOR i IN 1..v_col_cnt LOOP
        IF i > 1 THEN
            v_col_list := v_col_list || ', ';
            v_bind_list := v_bind_list || ', ';
        END IF;
        v_col_list := v_col_list || v_desc_tab(i).col_name;
        v_bind_list := v_bind_list || ':b' || i;
    END LOOP;
    
    DBMS_SQL.CLOSE_CURSOR(v_cursor_id);
    
    -- Build insert statement
    v_insert_sql := 'INSERT INTO ' || p_target_table || 
                    ' (' || v_col_list || ') VALUES (' || v_bind_list || ')';
    
    DBMS_OUTPUT.PUT_LINE('Insert SQL: ' || v_insert_sql);
    DBMS_OUTPUT.PUT_LINE('Processing...');
    
    -- Execute with bulk binding would go here
    -- (Simplified for demonstration)
    
    EXECUTE IMMEDIATE 'INSERT INTO ' || p_target_table || ' ' || p_source_query;
    v_total_rows := SQL%ROWCOUNT;
    
    COMMIT;
    DBMS_OUTPUT.PUT_LINE('Inserted ' || v_total_rows || ' rows');
    
EXCEPTION
    WHEN OTHERS THEN
        IF DBMS_SQL.IS_OPEN(v_cursor_id) THEN
            DBMS_SQL.CLOSE_CURSOR(v_cursor_id);
        END IF;
        ROLLBACK;
        RAISE;
END bulk_insert_dynamic;

6.6 Performance Considerations for Dynamic SQL
/*
 * BEST PRACTICES for Dynamic SQL Performance
 */

-- 1. Use bind variables to enable cursor sharing
-- BAD: Different SQL for each value
EXECUTE IMMEDIATE 'SELECT * FROM emp WHERE id = ' || v_id;

-- GOOD: Same SQL, different bind values
EXECUTE IMMEDIATE 'SELECT * FROM emp WHERE id = :id' USING v_id;

-- 2. Cache cursors for repeated execution
CREATE OR REPLACE PACKAGE dynamic_cache_pkg AS
    TYPE cursor_cache IS TABLE OF INTEGER INDEX BY VARCHAR2(100);
    g_cursors cursor_cache;
    
    FUNCTION get_cached_cursor(p_sql VARCHAR2) RETURN INTEGER;
    PROCEDURE close_all_cursors;
END;
/

CREATE OR REPLACE PACKAGE BODY dynamic_cache_pkg AS
    FUNCTION get_cached_cursor(p_sql VARCHAR2) RETURN INTEGER IS
        v_hash VARCHAR2(100);
        v_cursor INTEGER;
    BEGIN
        v_hash := DBMS_CRYPTO.HASH(UTL_RAW.CAST_TO_RAW(p_sql), DBMS_CRYPTO.HASH_MD5);
        
        IF g_cursors.EXISTS(v_hash) THEN
            RETURN g_cursors(v_hash);
        ELSE
            v_cursor := DBMS_SQL.OPEN_CURSOR;
            DBMS_SQL.PARSE(v_cursor, p_sql, DBMS_SQL.NATIVE);
            g_cursors(v_hash) := v_cursor;
            RETURN v_cursor;
        END IF;
    END;
    
    PROCEDURE close_all_cursors IS
        v_key VARCHAR2(100);
    BEGIN
        v_key := g_cursors.FIRST;
        WHILE v_key IS NOT NULL LOOP
            IF DBMS_SQL.IS_OPEN(g_cursors(v_key)) THEN
                DBMS_SQL.CLOSE_CURSOR(g_cursors(v_key));
            END IF;
            v_key := g_cursors.NEXT(v_key);
        END LOOP;
        g_cursors.DELETE;
    END;
END;
/

-- 3. Prefer static SQL when possible
-- Use dynamic SQL only when truly needed

-- 4. Validate identifiers to prevent injection
CREATE OR REPLACE FUNCTION validate_identifier(p_name VARCHAR2) RETURN VARCHAR2 IS
BEGIN
    -- Check against data dictionary
    IF NOT REGEXP_LIKE(p_name, '^[A-Za-z][A-Za-z0-9_$#]*$') THEN
        RAISE_APPLICATION_ERROR(-20001, 'Invalid identifier: ' || p_name);
    END IF;
    
    -- Use DBMS_ASSERT for additional safety
    RETURN DBMS_ASSERT.SIMPLE_SQL_NAME(p_name);
END;

CREATE OR REPLACE PACKAGE BODY banking_pkg AS

     * PRIVATE CONSTANTS

    c_daily_transfer_limit   CONSTANT NUMBER := 50000;

    -- Generate unique account number
    FUNCTION generate_account_number RETURN VARCHAR2 IS
        v_number VARCHAR2(20);
    BEGIN
        SELECT TO_CHAR(SYSDATE, 'YYMM') || 
               LPAD(account_seq.NEXTVAL, 10, '0')
        INTO v_number FROM dual;
        RETURN v_number;
    END;
    
    -- Log audit record
    PROCEDURE log_audit(
        p_table_name    IN VARCHAR2,
        p_operation     IN VARCHAR2,
        p_record_id     IN NUMBER,
        p_old_values    IN CLOB DEFAULT NULL,
        p_new_values    IN CLOB DEFAULT NULL
    ) IS
        PRAGMA AUTONOMOUS_TRANSACTION;
    BEGIN
        INSERT INTO bank_audit_log (
            audit_id, table_name, operation, record_id,
            old_values, new_values, changed_by, changed_date
        ) VALUES (
            audit_seq.NEXTVAL, p_table_name, p_operation, p_record_id,
            p_old_values, p_new_values, USER, SYSTIMESTAMP
        );
        COMMIT;
    END log_audit;
    
    -- Validate account status
    PROCEDURE validate_account(
        p_account_id    IN NUMBER,
        p_for_update    IN BOOLEAN DEFAULT FALSE
    ) IS
        v_status VARCHAR2(20);
        v_sql VARCHAR2(200);
    BEGIN
        IF p_for_update THEN
            SELECT status INTO v_status
            FROM bank_accounts
            WHERE account_id = p_account_id
            FOR UPDATE NOWAIT;
        ELSE
            SELECT status INTO v_status
            FROM bank_accounts
            WHERE account_id = p_account_id;
        END IF;
        
        IF v_status != c_status_active THEN
            RAISE e_account_inactive;
        END IF;
        
    EXCEPTION
        WHEN NO_DATA_FOUND THEN
            RAISE e_account_not_found;
    END validate_account;
    
    -- Record transaction
    FUNCTION record_transaction(
        p_account_id    IN NUMBER,
        p_txn_type      IN VARCHAR2,
        p_amount        IN NUMBER,
        p_balance_before IN NUMBER,
        p_balance_after IN NUMBER,
        p_reference_id  IN NUMBER DEFAULT NULL,
        p_description   IN VARCHAR2 DEFAULT NULL
    ) RETURN NUMBER IS
        v_txn_id NUMBER;
    BEGIN
        SELECT transaction_seq.NEXTVAL INTO v_txn_id FROM dual;
        
        INSERT INTO bank_transactions (
            transaction_id, account_id, transaction_type, amount,
            balance_before, balance_after, reference_id, description,
            transaction_date, processed_by
        ) VALUES (
            v_txn_id, p_account_id, p_txn_type, p_amount,
            p_balance_before, p_balance_after, p_reference_id, p_description,
            SYSTIMESTAMP, USER
        );
        
        RETURN v_txn_id;
    END record_transaction;
    
    /*******************************************
     * PUBLIC PROCEDURE IMPLEMENTATIONS
     *******************************************/
    
    PROCEDURE open_account(
        p_customer_id   IN  NUMBER,
        p_account_type  IN  VARCHAR2,
        p_initial_deposit IN NUMBER DEFAULT 0,
        p_account_id    OUT NUMBER,
        p_account_number OUT VARCHAR2
    ) IS
        v_interest_rate NUMBER;
    BEGIN
        -- Validate initial deposit
        IF p_initial_deposit < 0 THEN
            RAISE e_invalid_amount;
        END IF;
        
        -- Determine interest rate
        v_interest_rate := CASE p_account_type
            WHEN 'SAVINGS' THEN 0.025
            WHEN 'CHECKING' THEN 0.001
            WHEN 'MONEY_MARKET' THEN 0.035
            ELSE 0
        END;
        
        -- Generate account number
        p_account_number := generate_account_number();
        SELECT account_seq.CURRVAL INTO p_account_id FROM dual;
        
        -- Create account
        INSERT INTO bank_accounts (
            account_id, customer_id, account_number, account_type,
            balance, interest_rate, status, opened_date, last_activity
        ) VALUES (
            p_account_id, p_customer_id, p_account_number, p_account_type,
            p_initial_deposit, v_interest_rate, c_status_active, SYSDATE, SYSDATE
        );
        
        -- Record initial deposit if any
        IF p_initial_deposit > 0 THEN
            INSERT INTO bank_transactions (
                transaction_id, account_id, transaction_type, amount,
                balance_before, balance_after, description, processed_by
            ) VALUES (
                transaction_seq.NEXTVAL, p_account_id, c_txn_deposit, p_initial_deposit,
                0, p_initial_deposit, 'Initial deposit', USER
            );
        END IF;
        
        log_audit('BANK_ACCOUNTS', 'INSERT', p_account_id, NULL,
                 '{"account_number":"' || p_account_number || '","type":"' || p_account_type || '"}');
        
        COMMIT;
    END open_account;
    
    PROCEDURE close_account(
        p_account_id    IN NUMBER,
        p_reason        IN VARCHAR2 DEFAULT NULL
    ) IS
        v_balance NUMBER;
    BEGIN
        SELECT balance INTO v_balance
        FROM bank_accounts
        WHERE account_id = p_account_id
        FOR UPDATE;
        
        IF v_balance != 0 THEN
            RAISE_APPLICATION_ERROR(-20001, 
                'Account must have zero balance to close. Current balance: ' || v_balance);
        END IF;
        
        UPDATE bank_accounts
        SET status = c_status_closed,
            closed_date = SYSDATE,
            modified_date = SYSDATE,
            modified_by = USER
        WHERE account_id = p_account_id;
        
        log_audit('BANK_ACCOUNTS', 'CLOSE', p_account_id, NULL,
                 '{"reason":"' || NVL(p_reason, 'Customer request') || '"}');
        
        COMMIT;
    END close_account;
    
    FUNCTION get_balance(p_account_id IN NUMBER) RETURN NUMBER IS
        v_balance NUMBER;
    BEGIN
        SELECT balance INTO v_balance
        FROM bank_accounts
        WHERE account_id = p_account_id;
        
        RETURN v_balance;
    EXCEPTION
        WHEN NO_DATA_FOUND THEN
            RAISE e_account_not_found;
    END get_balance;
    
    FUNCTION get_account_info(p_account_id IN NUMBER) RETURN account_rec IS
        v_account account_rec;
    BEGIN
        SELECT account_id, account_number, account_type, balance, status
        INTO v_account
        FROM bank_accounts
        WHERE account_id = p_account_id;
        
        RETURN v_account;
    EXCEPTION
        WHEN NO_DATA_FOUND THEN
            RAISE e_account_not_found;
    END get_account_info;
    
    PROCEDURE deposit(
        p_account_id    IN  NUMBER,
        p_amount        IN  NUMBER,
        p_description   IN  VARCHAR2 DEFAULT NULL,
        p_transaction_id OUT NUMBER
    ) IS
        v_balance_before NUMBER;
        v_balance_after NUMBER;
    BEGIN
        -- Validate amount
        IF p_amount <= 0 THEN
            RAISE e_invalid_amount;
        END IF;
        
        -- Validate and lock account
        validate_account(p_account_id, TRUE);
        
        -- Get current balance
        SELECT balance INTO v_balance_before
        FROM bank_accounts
        WHERE account_id = p_account_id;
        
        v_balance_after := v_balance_before + p_amount;
        
        -- Update balance
        UPDATE bank_accounts
        SET balance = v_balance_after,
            last_activity = SYSDATE
        WHERE account_id = p_account_id;
        
        -- Record transaction
        p_transaction_id := record_transaction(
            p_account_id, c_txn_deposit, p_amount,
            v_balance_before, v_balance_after, NULL, p_description
        );
        
        COMMIT;
    END deposit;
    
    PROCEDURE withdraw(
        p_account_id    IN  NUMBER,
        p_amount        IN  NUMBER,
        p_description   IN  VARCHAR2 DEFAULT NULL,
        p_transaction_id OUT NUMBER
    ) IS
        v_balance_before NUMBER;
        v_balance_after NUMBER;
        v_daily_total NUMBER;
    BEGIN
        -- Validate amount
        IF p_amount <= 0 THEN
            RAISE e_invalid_amount;
        END IF;
        
        -- Check daily limit
        v_daily_total := get_daily_total(p_account_id, c_txn_withdrawal);
        IF v_daily_total + p_amount > c_daily_withdrawal_limit THEN
            RAISE e_daily_limit_exceeded;
        END IF;
        
        -- Validate and lock account
        validate_account(p_account_id, TRUE);
        
        -- Get current balance
        SELECT balance INTO v_balance_before
        FROM bank_accounts
        WHERE account_id = p_account_id;
        
        -- Check sufficient funds
        IF v_balance_before < p_amount THEN
            RAISE e_insufficient_funds;
        END IF;
        
        v_balance_after := v_balance_before - p_amount;
        
        -- Update balance
        UPDATE bank_accounts
        SET balance = v_balance_after,
            last_activity = SYSDATE
        WHERE account_id = p_account_id;
        
        -- Record transaction
        p_transaction_id := record_transaction(
            p_account_id, c_txn_withdrawal, p_amount,
            v_balance_before, v_balance_after, NULL, p_description
        );
        
        COMMIT;
    END withdraw;
    
    PROCEDURE transfer(
        p_from_account_id IN  NUMBER,
        p_to_account_id   IN  NUMBER,
        p_amount          IN  NUMBER,
        p_description     IN  VARCHAR2 DEFAULT NULL,
        p_transfer_id     OUT NUMBER
    ) IS
        v_from_balance   NUMBER;
        v_to_balance     NUMBER;
        v_daily_total    NUMBER;
        v_from_txn_id    NUMBER;
        v_to_txn_id      NUMBER;
        v_first_acct     NUMBER;
        v_second_acct    NUMBER;
    BEGIN
        -- Validate amount
        IF p_amount <= 0 THEN
            RAISE e_invalid_amount;
        END IF;
        
        IF p_from_account_id = p_to_account_id THEN
            RAISE_APPLICATION_ERROR(-20002, 'Cannot transfer to same account');
        END IF;
        
        -- Check daily limit
        v_daily_total := get_daily_total(p_from_account_id, c_txn_transfer_out);
        IF v_daily_total + p_amount > c_daily_transfer_limit THEN
            RAISE e_daily_limit_exceeded;
        END IF;
        
        -- Lock accounts in consistent order to prevent deadlocks
        IF p_from_account_id < p_to_account_id THEN
            v_first_acct := p_from_account_id;
            v_second_acct := p_to_account_id;
        ELSE
            v_first_acct := p_to_account_id;
            v_second_acct := p_from_account_id;
        END IF;
        
        -- Validate and lock first account
        validate_account(v_first_acct, TRUE);
        -- Validate and lock second account
        validate_account(v_second_acct, TRUE);
        
        -- Get balances
        SELECT balance INTO v_from_balance
        FROM bank_accounts WHERE account_id = p_from_account_id;
        
        SELECT balance INTO v_to_balance
        FROM bank_accounts WHERE account_id = p_to_account_id;
        
        -- Check sufficient funds
        IF v_from_balance < p_amount THEN
            RAISE e_insufficient_funds;
        END IF;
        
        -- Create transfer record
        SELECT transfer_seq.NEXTVAL INTO p_transfer_id FROM dual;
        
        INSERT INTO bank_transfers (
            transfer_id, from_account_id, to_account_id, amount,
            transfer_type, status, initiated_by,
            reference_number
        ) VALUES (
            p_transfer_id, p_from_account_id, p_to_account_id, p_amount,
            'INTERNAL', 'COMPLETED', USER,
            'TRF' || TO_CHAR(SYSDATE, 'YYYYMMDD') || LPAD(p_transfer_id, 10, '0')
        );
        
        -- Update from account
        UPDATE bank_accounts
        SET balance = balance - p_amount,
            last_activity = SYSDATE
        WHERE account_id = p_from_account_id;
        
        v_from_txn_id := record_transaction(
            p_from_account_id, c_txn_transfer_out, p_amount,
            v_from_balance, v_from_balance - p_amount, p_transfer_id, p_description
        );
        
        -- Update to account
        UPDATE bank_accounts
        SET balance = balance + p_amount,
            last_activity = SYSDATE
        WHERE account_id = p_to_account_id;
        
        v_to_txn_id := record_transaction(
            p_to_account_id, c_txn_transfer_in, p_amount,
            v_to_balance, v_to_balance + p_amount, p_transfer_id, p_description
        );
        
        -- Update transfer record
        UPDATE bank_transfers
        SET completed_date = SYSTIMESTAMP
        WHERE transfer_id = p_transfer_id;
        
        COMMIT;
        
    EXCEPTION
        WHEN e_insufficient_funds OR e_account_not_found OR e_account_inactive THEN
            ROLLBACK;
            RAISE;
        WHEN OTHERS THEN
            ROLLBACK;
            RAISE e_transfer_failed;
    END transfer;
    
    FUNCTION get_transaction_history(
        p_account_id    IN NUMBER,
        p_start_date    IN DATE DEFAULT NULL,
        p_end_date      IN DATE DEFAULT NULL,
        p_limit         IN NUMBER DEFAULT 100
    ) RETURN transaction_tab IS
        v_transactions transaction_tab;
        v_idx PLS_INTEGER := 0;
    BEGIN
        FOR txn IN (
            SELECT transaction_id, transaction_type, amount, 
                   balance_after, transaction_date
            FROM bank_transactions
            WHERE account_id = p_account_id
              AND (p_start_date IS NULL OR transaction_date >= p_start_date)
              AND (p_end_date IS NULL OR transaction_date <= p_end_date + 1)
            ORDER BY transaction_date DESC
            FETCH FIRST p_limit ROWS ONLY
        )
        LOOP
            v_idx := v_idx + 1;
            v_transactions(v_idx).transaction_id := txn.transaction_id;
            v_transactions(v_idx).transaction_type := txn.transaction_type;
            v_transactions(v_idx).amount := txn.amount;
            v_transactions(v_idx).balance_after := txn.balance_after;
            v_transactions(v_idx).transaction_date := txn.transaction_date;
        END LOOP;
        
        RETURN v_transactions;
    END get_transaction_history;
    
    FUNCTION get_daily_total(
        p_account_id    IN NUMBER,
        p_txn_type      IN VARCHAR2
    ) RETURN NUMBER IS
        v_total NUMBER;
    BEGIN
        SELECT NVL(SUM(amount), 0) INTO v_total
        FROM bank_transactions
        WHERE account_id = p_account_id
          AND transaction_type = p_txn_type
          AND TRUNC(transaction_date) = TRUNC(SYSDATE);
        
        RETURN v_total;
    END get_daily_total;
    
END banking_pkg;

1. Introduction to Concurrency Control
1.1 Why Concurrency Matters
In a multi-user database environment, multiple sessions may attempt to:

Read the same data simultaneously
Modify the same rows concurrently
Access shared resources at the same time
Without proper concurrency control, we face:

Problem	Description	Example
Lost Updates	One transaction overwrites another's changes	Two users update same account balance
Dirty Reads	Reading uncommitted data from another transaction	Seeing a transfer before it's committed
Non-Repeatable Reads	Same query returns different results within a transaction	Balance changes between two SELECTs
Phantom Reads	New rows appear in repeated queries	New orders appear during report generation
1.2 Oracle's Concurrency Philosophy
┌─────────────────────────────────────────────────────────────────┐
│              ORACLE'S CONCURRENCY PRINCIPLES                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  1. READERS NEVER BLOCK WRITERS                                  │
│     • SELECT statements never wait for DML                       │
│     • Achieved through multi-version read consistency            │
│                                                                  │
│  2. WRITERS NEVER BLOCK READERS                                  │
│     • DML never blocks SELECT statements                         │
│     • Readers see data as of their query start time              │
│                                                                  │
│  3. WRITERS ONLY BLOCK OTHER WRITERS                             │
│     • Only when modifying the SAME rows                          │
│     • Row-level locking minimizes contention                     │
│                                                                  │
│  4. LOCKS ARE HELD UNTIL COMMIT/ROLLBACK                         │
│     • No automatic lock escalation                               │
│     • Predictable behavior for developers                        │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘

2. Locks vs Latches
2.1 Conceptual Differences
Aspect	Locks	Latches
Purpose	Protect user data (rows, tables)	Protect internal memory structures
Duration	Transaction duration	Very brief (microseconds)
Scope	Logical (business data)	Physical (SGA structures)
Visibility	Application-level	Internal to Oracle
Queueing	FIFO queue for waiters	No guaranteed ordering
Deadlock Detection	Oracle detects and resolves	Latches use timeouts
User Control	Can be explicitly requested	No user control
2.2 Locks (Enqueues)
/*
 * LOCKS protect database objects and user data
 * - Also called "enqueues"
 * - Managed through enqueue mechanism
 * - Have modes (Share, Exclusive, etc.)

-- View current locks in the database
SELECT 
    s.sid,
    s.serial#,
    s.username,

3. Oracle Lock Types and Modes
3.1 Row-Level Locks (TX)
/*
 * Row-level locks are the most granular
 * - Acquired automatically during DML
 * - Lock only the affected rows
 * - Released on COMMIT/ROLLBACK
 */

-- Session 1: Lock a specific row
UPDATE employees 
SET salary = 50000 
WHERE employee_id = 100;
-- Row 100 is now locked

-- Session 2: Can update OTHER rows freely
UPDATE employees 
SET salary = 60000 
WHERE employee_id = 101;  -- Succeeds immediately

-- Session 2: Updating SAME row waits
UPDATE employees 
SET salary = 55000 
WHERE employee_id = 100;  -- Waits for Session 1
3.2 Table-Level Locks (TM)
Mode	Name	Allows	Conflicts With
2	Row Share (RS/SS)	Concurrent DML	Exclusive
3	Row Exclusive (RX/SX)	Concurrent DML	Share, Exclusive
4	Share (S)	Read, Share locks	Row Exclusive, Exclusive
5	Share Row Exclusive (SRX/SSX)	Read only	All except Row Share
6	Exclusive (X)	Nothing	All modes
/*
 * Table locks are acquired implicitly with DML
 * - DML acquires Row-X (RX) mode on table
 * - DDL acquires Exclusive (X) mode
 */

    s.username,

        2, 'Row-S',

JOIN v$session s ON l.sid = s.sid
JOIN dba_objects o ON l.id1 = o.object_id
WHERE l.type = 'TM'
  AND s.username IS NOT NULL;

3.4 Explicit Table Locking
/*
 * LOCK TABLE statement for explicit locking
 * Use when you need predictable locking behavior
 */

-- Lock table in share mode (allows reads, blocks writes)
LOCK TABLE employees IN SHARE MODE;

-- Lock table in exclusive mode (blocks everything)
LOCK TABLE employees IN EXCLUSIVE MODE;

-- Lock with NOWAIT (fail immediately if can't lock)
LOCK TABLE employees IN EXCLUSIVE MODE NOWAIT;

-- Lock with timeout
LOCK TABLE employees IN EXCLUSIVE MODE WAIT 10;  -- Wait up to 10 seconds

/*
 * REAL-WORLD: Batch update requiring exclusive access
 */
DECLARE
    e_lock_failed EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_lock_failed, -54);
BEGIN
    -- Try to get exclusive lock
    EXECUTE IMMEDIATE 'LOCK TABLE salary_adjustments IN EXCLUSIVE MODE NOWAIT';
    
    -- Perform batch update
    UPDATE employees e
    SET salary = salary * (1 + (
        SELECT adjustment_pct FROM salary_adjustments sa
        WHERE sa.department_id = e.department_id
    ))
    WHERE department_id IN (SELECT department_id FROM salary_adjustments);
    
    COMMIT;
    
EXCEPTION
    WHEN e_lock_failed THEN
        DBMS_OUTPUT.PUT_LINE('Table is locked by another session');
END;

4. Deadlocks
4.1 What is a Deadlock?
A deadlock occurs when two or more sessions are waiting for resources held by each other, creating a circular wait condition that cannot be resolved without intervention.

┌─────────────────────────────────────────────────────────────────┐
│                    DEADLOCK SCENARIO                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Time    Session 1                    Session 2                  │
│  ────    ─────────                    ─────────                  │
│                                                                  │
│  T1      UPDATE accounts              UPDATE accounts            │
│          SET balance = 1000           SET balance = 2000         │
│          WHERE id = 100;              WHERE id = 200;            │
│          [Locks row 100]              [Locks row 200]            │
│                                                                  │
│  T2      UPDATE accounts              UPDATE accounts            │

4.4 Preventing Deadlocks
Strategy 1: Consistent Lock Ordering
/*
 * ALWAYS access resources in the same order
 * Example: Always lock by account_id ascending
 */
CREATE OR REPLACE PROCEDURE transfer_funds_safe(
    p_from_account  IN NUMBER,
    p_to_account    IN NUMBER,
    p_amount        IN NUMBER
)
IS
    v_first_account  NUMBER;
    v_second_account NUMBER;
    v_balance        NUMBER;
BEGIN
    -- Determine lock order (always lock lower ID first)
    IF p_from_account < p_to_account THEN
        v_first_account := p_from_account;
        v_second_account := p_to_account;
    ELSE
        v_first_account := p_to_account;
        v_second_account := p_from_account;
    END IF;
    
    -- Lock in consistent order
    SELECT balance INTO v_balance
    FROM accounts WHERE account_id = v_first_account
    FOR UPDATE;
    
    SELECT balance INTO v_balance
    FROM accounts WHERE account_id = v_second_account
    FOR UPDATE;
    
    -- Now perform the transfer
    UPDATE accounts SET balance = balance - p_amount
    WHERE account_id = p_from_account;
    
    UPDATE accounts SET balance = balance + p_amount
    WHERE account_id = p_to_account;
    
    COMMIT;
END;
/
Strategy 2: Lock All Resources Upfront
/*
 * Lock all required rows at the beginning of transaction
 */
CREATE OR REPLACE PROCEDURE batch_update_safe(
    p_employee_ids  IN SYS.ODCINUMBERLIST
)
IS
    CURSOR c_employees IS
        SELECT employee_id, salary
        FROM employees
        WHERE employee_id IN (SELECT column_value FROM TABLE(p_employee_ids))
        ORDER BY employee_id  -- Consistent order!
        FOR UPDATE;
BEGIN
    -- Lock all rows first
    FOR emp IN c_employees LOOP
        NULL;  -- Just acquiring locks
    END LOOP;
    
    -- Now safe to update
    FOR emp IN c_employees LOOP
        UPDATE employees
        SET salary = emp.salary * 1.10
        WHERE employee_id = emp.employee_id;
    END LOOP;
    
    COMMIT;
END;
/
Strategy 3: Use NOWAIT with Retry
/*
 * Try to acquire locks, retry if busy
 */
CREATE OR REPLACE PROCEDURE update_with_retry(
    p_employee_id  IN NUMBER,
    p_new_salary   IN NUMBER,
    p_max_retries  IN NUMBER DEFAULT 3
)
IS
    v_retries NUMBER := 0;
    v_done    BOOLEAN := FALSE;
    
    e_resource_busy EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_resource_busy, -54);
    
    e_deadlock EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_deadlock, -60);
BEGIN
    WHILE NOT v_done AND v_retries < p_max_retries LOOP
        BEGIN
            -- Try to lock with NOWAIT
            UPDATE employees
            SET salary = p_new_salary
            WHERE employee_id = p_employee_id;
            
            COMMIT;
            v_done := TRUE;
            
        EXCEPTION
            WHEN e_resource_busy OR e_deadlock THEN
                ROLLBACK;
                v_retries := v_retries + 1;
                -- Exponential backoff
                DBMS_LOCK.SLEEP(POWER(2, v_retries) * 0.1);
        END;
    END LOOP;
    
    IF NOT v_done THEN
        RAISE_APPLICATION_ERROR(-20001, 
            'Failed to update after ' || p_max_retries || ' retries');
    END IF;
END;
/
Strategy 4: Shorten Transaction Duration
/*
 * Keep transactions short to reduce deadlock window
 */

-- BAD: Long transaction holding locks
BEGIN
    UPDATE accounts SET status = 'PROCESSING' WHERE account_id = 100;
    
    -- Long-running external call
    send_notification_to_external_system(...);  -- Takes 30 seconds!
    
    UPDATE accounts SET status = 'COMPLETED' WHERE account_id = 100;
    COMMIT;
END;

-- GOOD: Minimize lock duration
BEGIN
    -- Quick status update
    UPDATE accounts SET status = 'PROCESSING' WHERE account_id = 100;
    COMMIT;
    
    -- External call (no locks held)
    send_notification_to_external_system(...);
    
    -- Quick final update
    UPDATE accounts SET status = 'COMPLETED' WHERE account_id = 100;
    COMMIT;
END;
4.5 Handling Deadlocks in Application Code
/*
 * Robust deadlock handling pattern
 */
CREATE OR REPLACE PROCEDURE process_order(p_order_id IN NUMBER)
IS
    e_deadlock EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_deadlock, -60);
    
    c_max_retries CONSTANT PLS_INTEGER := 3;
    v_retry_count PLS_INTEGER := 0;
    v_success BOOLEAN := FALSE;
BEGIN
    WHILE NOT v_success AND v_retry_count < c_max_retries LOOP
        BEGIN
            -- Start fresh transaction
            SAVEPOINT before_processing;
            
            -- Lock order and items
            UPDATE orders SET status = 'PROCESSING'
            WHERE order_id = p_order_id;
            
            UPDATE order_items SET reserved = 'Y'
            WHERE order_id = p_order_id;
            
            -- Update inventory (potential deadlock point)
            UPDATE inventory i
            SET quantity = quantity - (
                SELECT quantity FROM order_items oi
                WHERE oi.order_id = p_order_id
                  AND oi.product_id = i.product_id
            )
            WHERE product_id IN (
                SELECT product_id FROM order_items
                WHERE order_id = p_order_id
            );
            
            -- Finalize
            UPDATE orders SET status = 'COMPLETED'
            WHERE order_id = p_order_id;
            
            COMMIT;
            v_success := TRUE;
            
        EXCEPTION
            WHEN e_deadlock THEN
                ROLLBACK TO before_processing;
                v_retry_count := v_retry_count + 1;
                
                -- Log the deadlock
                log_error('Deadlock on order ' || p_order_id || 
                         ', retry ' || v_retry_count);
                
                -- Wait before retry (with jitter)
                DBMS_LOCK.SLEEP(DBMS_RANDOM.VALUE(0.1, 0.5) * v_retry_count);
        END;
    END LOOP;
    
    IF NOT v_success THEN
        RAISE_APPLICATION_ERROR(-20001, 
            'Order processing failed after ' || c_max_retries || ' retries');
    END IF;
END;
/
5. SELECT FOR UPDATE
5.1 Basic Syntax and Usage
/*
 * SELECT FOR UPDATE locks selected rows for subsequent modification
 * - Prevents other sessions from modifying the rows
 * - Rows remain locked until COMMIT/ROLLBACK
 */

-- Basic SELECT FOR UPDATE
SELECT employee_id, salary
FROM employees
WHERE department_id = 60
FOR UPDATE;

-- Lock specific columns only
SELECT employee_id, salary, commission_pct
FROM employees
WHERE department_id = 60
FOR UPDATE OF salary;  -- Only salary column is relevant for lock

-- Multiple tables
SELECT e.employee_id, e.salary, d.department_name
FROM employees e
JOIN departments d ON e.department_id = d.department_id
WHERE e.department_id = 60
FOR UPDATE OF e.salary;  -- Lock only employees table

SKIP LOCKED
/*
 * SKIP LOCKED: Skip rows that are locked by other sessions
 * Perfect for queue processing with multiple workers
 */

-- Job queue table
CREATE TABLE job_queue (
    job_id      NUMBER PRIMARY KEY,
    job_type    VARCHAR2(50),
    payload     CLOB,
    status      VARCHAR2(20) DEFAULT 'PENDING',
    priority    NUMBER DEFAULT 5,
    created_dt  TIMESTAMP DEFAULT SYSTIMESTAMP,
    processed_dt TIMESTAMP,
    worker_id   VARCHAR2(50)
);

-- Worker process that claims and processes jobs
CREATE OR REPLACE PROCEDURE process_jobs(
    p_worker_id  IN VARCHAR2,
    p_batch_size IN NUMBER DEFAULT 10
)
IS
    CURSOR c_jobs IS
        SELECT job_id, job_type, payload
        FROM job_queue
        WHERE status = 'PENDING'
        ORDER BY priority, created_dt
        FOR UPDATE SKIP LOCKED  -- Skip jobs being processed by others
        FETCH FIRST p_batch_size ROWS ONLY;
    
    TYPE job_tab IS TABLE OF c_jobs%ROWTYPE;
    v_jobs job_tab;
BEGIN
    OPEN c_jobs;
    FETCH c_jobs BULK COLLECT INTO v_jobs;
    CLOSE c_jobs;
    
    IF v_jobs.COUNT = 0 THEN
        DBMS_OUTPUT.PUT_LINE('No jobs available');
        RETURN;
    END IF;
    
    -- Mark jobs as processing
    FORALL i IN 1..v_jobs.COUNT
        UPDATE job_queue
        SET status = 'PROCESSING',
            worker_id = p_worker_id
        WHERE job_id = v_jobs(i).job_id;
    COMMIT;
    
    -- Process each job
    FOR i IN 1..v_jobs.COUNT LOOP
        BEGIN
            -- Actual job processing
            process_single_job(v_jobs(i).job_id, v_jobs(i).payload);
            
            UPDATE job_queue
            SET status = 'COMPLETED',
                processed_dt = SYSTIMESTAMP
            WHERE job_id = v_jobs(i).job_id;
            
        EXCEPTION
            WHEN OTHERS THEN
                UPDATE job_queue
                SET status = 'FAILED',
                    processed_dt = SYSTIMESTAMP
                WHERE job_id = v_jobs(i).job_id;
        END;
        COMMIT;
    END LOOP;
END;
/

/*
 * Multiple workers can run simultaneously:
 * Worker 1: Gets jobs 1, 2, 3
 * Worker 2: Gets jobs 4, 5, 6 (skips 1, 2, 3)
 * Worker 3: Gets jobs 7, 8, 9 (skips 1-6)
 */
5.3 WHERE CURRENT OF
/*
 * WHERE CURRENT OF updates/deletes the current cursor row
 * - More efficient than re-querying by primary key
 * - Only works with FOR UPDATE cursors
 */
DECLARE
    CURSOR c_employees IS
        SELECT employee_id, salary, commission_pct
        FROM employees
        WHERE department_id = 80
        FOR UPDATE OF salary;
BEGIN
    FOR emp IN c_employees LOOP
        IF emp.commission_pct IS NOT NULL THEN
            UPDATE employees
            SET salary = emp.salary * (1 + emp.commission_pct)
            WHERE CURRENT OF c_employees;  -- Update this exact row
        END IF;
    END LOOP;
    COMMIT;
END;

5.4 Real-World Patterns
Pattern 1: Pessimistic Locking for Critical Updates
/*
 * SCENARIO: Bank account balance update
 * Must ensure no race conditions
 */
CREATE OR REPLACE FUNCTION withdraw_funds(
    p_account_id IN NUMBER,
    p_amount     IN NUMBER
) RETURN BOOLEAN
IS
    v_current_balance NUMBER;
    e_insufficient EXCEPTION;
BEGIN
    -- Lock the account row
    SELECT balance INTO v_current_balance
    FROM accounts
    WHERE account_id = p_account_id
    FOR UPDATE;
    
    -- Check balance
    IF v_current_balance < p_amount THEN
        RAISE e_insufficient;
    END IF;
    
    -- Deduct amount
    UPDATE accounts
    SET balance = balance - p_amount,
        last_transaction = SYSTIMESTAMP
    WHERE account_id = p_account_id;
    
    -- Record transaction
    INSERT INTO transactions (account_id, amount, txn_type, txn_date)
    VALUES (p_account_id, -p_amount, 'WITHDRAWAL', SYSTIMESTAMP);
    
    COMMIT;
    RETURN TRUE;
    
EXCEPTION
    WHEN e_insufficient THEN
        ROLLBACK;
        RETURN FALSE;
END;
/
Pattern 2: Inventory Reservation
/*
 * SCENARIO: E-commerce inventory reservation
 * Multiple users trying to purchase limited stock
 */
CREATE OR REPLACE PROCEDURE reserve_inventory(
    p_product_id IN NUMBER,
    p_quantity   IN NUMBER,
    p_order_id   IN NUMBER,
    p_success    OUT BOOLEAN,
    p_message    OUT VARCHAR2
)
IS
    v_available NUMBER;
    e_timeout EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_timeout, -30006);
BEGIN
    p_success := FALSE;
    
    -- Try to lock with short timeout
    BEGIN
        SELECT quantity_available INTO v_available
        FROM inventory
        WHERE product_id = p_product_id
        FOR UPDATE WAIT 3;
    EXCEPTION
        WHEN e_timeout THEN
            p_message := 'Product is being updated by another user. Please retry.';
            RETURN;
    END;
    
    -- Check availability
    IF v_available < p_quantity THEN
        p_message := 'Insufficient inventory. Available: ' || v_available;
        ROLLBACK;
        RETURN;
    END IF;
    
    -- Reserve inventory
    UPDATE inventory
    SET quantity_available = quantity_available - p_quantity,
        quantity_reserved = quantity_reserved + p_quantity
    WHERE product_id = p_product_id;
    
    -- Create reservation record
    INSERT INTO inventory_reservations 
    (reservation_id, product_id, order_id, quantity, reserved_at, expires_at)
    VALUES 
    (reservation_seq.NEXTVAL, p_product_id, p_order_id, p_quantity, 
     SYSTIMESTAMP, SYSTIMESTAMP + INTERVAL '30' MINUTE);
    
    COMMIT;
    p_success := TRUE;
    p_message := 'Inventory reserved successfully';
END;

6. Isolation Levels and Read Consistency
6.1 Oracle's Default: Read Committed
/*
 * READ COMMITTED (Default):
 * - Each query sees only committed data as of query start
 * - Different queries in same transaction may see different data
 * - No dirty reads, but non-repeatable reads possible
 */

-- Session 1: Start transaction
SELECT balance FROM accounts WHERE account_id = 100;  -- Returns 1000

-- Session 2: Update and commit
UPDATE accounts SET balance = 1500 WHERE account_id = 100;
COMMIT;

-- Session 1: Same query, different result
SELECT balance FROM accounts WHERE account_id = 100;  -- Returns 1500!
6.2 Serializable Isolation
/*
 * SERIALIZABLE:
 * - Transaction sees snapshot of database as of transaction start
 * - All queries see consistent data throughout transaction
 * - May receive ORA-08177 if concurrent changes conflict
 */

-- Set isolation level
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Or in PL/SQL
BEGIN
    SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    
    -- All queries now see data as of this point
    SELECT balance FROM accounts WHERE account_id = 100;  -- Returns 1000
    
    -- Even if another session updates and commits...
    
    SELECT balance FROM accounts WHERE account_id = 100;  -- Still returns 1000!
    
    COMMIT;
END;
/

/*
 * Serialization failure example
 */
DECLARE
    e_serialization EXCEPTION;
    PRAGMA EXCEPTION_INIT(e_serialization, -8177);
BEGIN
    SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    
    -- Read some data
    SELECT ... FROM some_table;
    
    -- Try to update (another session modified this row since we started)
    UPDATE some_table SET ...;  -- ORA-08177!
    
    COMMIT;
EXCEPTION
    WHEN e_serialization THEN
        ROLLBACK;
        -- Retry the entire transaction
END;

6.4 ORA-01555: Snapshot Too Old
/*
 * ORA-01555 occurs when:
 * - Long-running query needs old data from undo
 * - But undo has been overwritten
 * 
 * Prevention strategies:
 */

-- 1. Increase undo retention
ALTER SYSTEM SET undo_retention = 3600;  -- 1 hour

-- 2. Use RETENTION GUARANTEE
ALTER TABLESPACE undotbs1 RETENTION GUARANTEE;

-- 3. For long reports, use flashback query
SELECT * FROM large_table AS OF TIMESTAMP (SYSTIMESTAMP - INTERVAL '1' HOUR);

-- 4. Break up long-running queries
DECLARE
    v_start_scn NUMBER;
BEGIN
    v_start_scn := DBMS_FLASHBACK.GET_SYSTEM_CHANGE_NUMBER;
    
    -- Process in chunks, all seeing same SCN
    FOR chunk IN (
        SELECT ROWID rid FROM large_table 
        WHERE MOD(ORA_HASH(id), 10) = 0  -- First chunk
    )
    LOOP
        -- Process using AS OF SCN for consistency
        SELECT * FROM large_table AS OF SCN v_start_scn
        WHERE ROWID = chunk.rid;
    END LOOP;
END;
/
6.5 When to Use Each Isolation Level
Use Case	Isolation Level	Reason
General OLTP	READ COMMITTED	Best concurrency, default behavior
Financial reports	SERIALIZABLE	Consistent point-in-time view
Audit queries	SERIALIZABLE	Must see consistent data
High-volume inserts	READ COMMITTED	Avoid serialization failures
Balance calculations	SERIALIZABLE	Prevent phantom reads
7. Blocking and Waiting Sessions
7.1 Understanding Blocking
┌─────────────────────────────────────────────────────────────────┐
│                    BLOCKING CHAIN                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Session 100 (BLOCKER)                                           │
│       │                                                          │
│       │ Holds lock on row 1                                      │

/*
 * Query to find blocking sessions
 */

    'Session ' || s1.sid || ' (' || s1.username || ')' AS blocked_session,
    'is blocked by Session ' || s2.sid || ' (' || s2.username || ')' AS blocker,

8. Real-World Case Studies
8.1 Case Study: E-Commerce Flash Sale
Scenario: Thousands of users trying to purchase limited inventory simultaneously.

/*
 * Problem: Traditional approach causes massive blocking
 */
-- BAD: Everyone blocks on the same row
UPDATE products 
SET quantity = quantity - 1 
WHERE product_id = 100 AND quantity > 0;

/*
 * Solution: Use optimistic locking with version control
 */
CREATE TABLE products (
    product_id    NUMBER PRIMARY KEY,
    product_name  VARCHAR2(100),
    quantity      NUMBER,
    version       NUMBER DEFAULT 1,
    last_updated  TIMESTAMP
);

CREATE OR REPLACE FUNCTION purchase_product(
    p_product_id IN NUMBER,
    p_quantity   IN NUMBER,
    p_user_id    IN NUMBER
) RETURN VARCHAR2
IS
    v_current_qty     NUMBER;
    v_current_version NUMBER;
    v_rows_updated    NUMBER;
    c_max_retries     CONSTANT NUMBER := 3;
    v_retry           NUMBER := 0;
BEGIN
    WHILE v_retry < c_max_retries LOOP
        -- Read current state (no lock)
        SELECT quantity, version
        INTO v_current_qty, v_current_version
        FROM products
        WHERE product_id = p_product_id;
        
        -- Check availability
        IF v_current_qty < p_quantity THEN
            RETURN 'INSUFFICIENT_STOCK';
        END IF;
        
        -- Optimistic update with version check
        UPDATE products
        SET quantity = quantity - p_quantity,
            version = version + 1,
            last_updated = SYSTIMESTAMP
        WHERE product_id = p_product_id
          AND version = v_current_version  -- Only if unchanged
          AND quantity >= p_quantity;
        
        v_rows_updated := SQL%ROWCOUNT;
        
        IF v_rows_updated = 1 THEN
            -- Success! Create order
            INSERT INTO orders (order_id, user_id, product_id, quantity, order_date)
            VALUES (order_seq.NEXTVAL, p_user_id, p_product_id, p_quantity, SYSTIMESTAMP);
            
            COMMIT;
            RETURN 'SUCCESS';
        END IF;
        
        -- Version changed, retry
        v_retry := v_retry + 1;
        DBMS_LOCK.SLEEP(0.01 * v_retry);  -- Small backoff
    END LOOP;
    
    RETURN 'RETRY_EXHAUSTED';
END;
/
8.2 Case Study: Banking Batch Processing
Scenario: Nightly interest calculation affecting millions of accounts while online banking is still active.

/*
 * Solution: Process in small batches with minimal locking
 */
CREATE OR REPLACE PROCEDURE apply_daily_interest
IS
    c_batch_size CONSTANT NUMBER := 1000;
    v_processed  NUMBER := 0;
    
    CURSOR c_accounts IS
        SELECT account_id, balance, interest_rate
        FROM accounts
        WHERE account_type = 'SAVINGS'
          AND status = 'ACTIVE'
          AND last_interest_date < TRUNC(SYSDATE)
        ORDER BY account_id;  -- Consistent ordering prevents deadlocks
    
    TYPE account_tab IS TABLE OF c_accounts%ROWTYPE;
    v_accounts account_tab;
BEGIN
    OPEN c_accounts;
    
    LOOP
        FETCH c_accounts BULK COLLECT INTO v_accounts LIMIT c_batch_size;
        EXIT WHEN v_accounts.COUNT = 0;
        
        -- Process batch
        FOR i IN 1..v_accounts.COUNT LOOP
            BEGIN
                -- Short transaction per account
                UPDATE accounts
                SET balance = balance + (balance * interest_rate / 365),
                    last_interest_date = TRUNC(SYSDATE)
                WHERE account_id = v_accounts(i).account_id
                  AND last_interest_date < TRUNC(SYSDATE);  -- Idempotent
                
                IF SQL%ROWCOUNT = 1 THEN
                    INSERT INTO interest_log 
                    VALUES (v_accounts(i).account_id, 
                            v_accounts(i).balance * v_accounts(i).interest_rate / 365,
                            SYSDATE);
                END IF;
                
            EXCEPTION
                WHEN OTHERS THEN
                    -- Log error but continue with other accounts
                    log_error('Interest failed for account ' || v_accounts(i).account_id);
            END;
        END LOOP;
        
        COMMIT;  -- Commit each batch
        v_processed := v_processed + v_accounts.COUNT;
        
        -- Brief pause to allow online transactions
        DBMS_LOCK.SLEEP(0.1);
    END LOOP;
    
    CLOSE c_accounts;
    
    DBMS_OUTPUT.PUT_LINE('Processed ' || v_processed || ' accounts');
END;

        SELECT 
            s1.sid AS blocked,

        JOIN v$session s ON l.sid = s.sid

            'Locks: ' || r.locks_held || ' ' ||
            'Longest: ' || r.longest_lock_sec || 's'

11.1 Key Concepts
Concept	Description
Locks	Protect user data; transaction duration; user-visible
Latches	Protect memory structures; microseconds; internal
Deadlock	Circular wait; Oracle auto-detects and resolves
FOR UPDATE	Explicit row locking for subsequent modification
NOWAIT/WAIT	Control lock acquisition timeout
SKIP LOCKED	Process only unlocked rows (queue pattern)
READ COMMITTED	Statement-level consistency (default)
SERIALIZABLE	Transaction-level consistency
Blocking	One session waiting for another's locks
11.2 Quick Reference
-- Explicit locking
SELECT ... FOR UPDATE [NOWAIT | WAIT n | SKIP LOCKED];
LOCK TABLE table IN {SHARE | EXCLUSIVE} MODE [NOWAIT];

-- Isolation levels
SET TRANSACTION ISOLATION LEVEL {READ COMMITTED | SERIALIZABLE};

-- Find blockers
SELECT * FROM v$session WHERE blocking_session IS NOT NULL;

-- Kill session
ALTER SYSTEM KILL SESSION 'sid,serial#' [IMMEDIATE];

-- Key views
v$lock       -- Current locks
v$session    -- Session info including blocking_session
v$transaction -- Active transactions
v$locked_object -- Locked objects
11.3 Best Practices
Practice	Description
Lock in consistent order	Prevents deadlocks
Keep transactions short	Reduces blocking duration
Use NOWAIT/WAIT	Avoid indefinite waits
Use SKIP LOCKED for queues	Enables parallel processing
Monitor blocking regularly	Catch issues early
Use optimistic locking	For high-concurrency scenarios
Commit frequently	Release locks promptly
Avoid long-running transactions	Reduces ORA-01555 risk

SELECT 'IN_SOURCE_ONLY' AS status, s.*
FROM source_orders s
WHERE NOT EXISTS (SELECT 1 FROM target_orders t WHERE t.order_id = s.order_id);

-- Find records in TARGET but not SOURCE
SELECT 'IN_TARGET_ONLY' AS status, t.*
FROM target_orders t
WHERE NOT EXISTS (SELECT 1 FROM source_orders s WHERE s.order_id = t.order_id);

-- Combined with FULL OUTER JOIN
SELECT 
    COALESCE(s.order_id, t.order_id) AS order_id,
    CASE 
        WHEN s.order_id IS NULL THEN 'TARGET_ONLY'
        WHEN t.order_id IS NULL THEN 'SOURCE_ONLY'
        WHEN s.order_total != t.order_total THEN 'AMOUNT_MISMATCH'
        ELSE 'MATCH'
    END AS status,
    s.order_total AS source_amount,
    t.order_total AS target_amount
FROM source_orders s
FULL OUTER JOIN target_orders t ON s.order_id = t.order_id
WHERE s.order_id IS NULL OR t.order_id IS NULL OR s.order_total != t.order_total;
3.4 Field-Level Comparison
-- Detailed field comparison using UNPIVOT
WITH source_data AS (
    SELECT order_id,
           TO_CHAR(customer_id) AS customer_id,
           TO_CHAR(order_total) AS order_total,
           status
    FROM source_orders
),
target_data AS (
    SELECT order_id,
           TO_CHAR(customer_id) AS customer_id,
           TO_CHAR(order_total) AS order_total,
           status
    FROM target_orders
)
SELECT s.order_id, s.field_name,
       s.field_value AS source_value,
       t.field_value AS target_value
FROM (
    SELECT order_id, field_name, field_value
    FROM source_data
    UNPIVOT (field_value FOR field_name IN (customer_id, order_total, status))
) s
JOIN (
    SELECT order_id, field_name, field_value
    FROM target_data
    UNPIVOT (field_value FOR field_name IN (customer_id, order_total, status))
) t ON s.order_id = t.order_id AND s.field_name = t.field_name
WHERE NVL(s.field_value, 'NULL') != NVL(t.field_value, 'NULL');
4. Count and Checksum Comparisons
4.1 Theory of Checksums
┌─────────────────────────────────────────────────────────────────┐
│                 CHECKSUM COMPARISON BENEFITS                     │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  SPEED: O(1) vs O(N) for full comparison                        │
│  For 1 billion records: checksum = ms, full = hours             │
│                                                                  │
│  TYPES:                                                          │
│  • Count checksum: Record counts                                 │
│  • Additive checksum: SUM of numeric fields                     │
│  • Hash checksum: Cryptographic hash of data                    │
│                                                                  │
│  LIMITATION: May miss offsetting errors                         │
│  (+$100 and -$100 errors cancel out)                            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
4.2 Count-Based Validation
-- Multi-level count comparison
SELECT 'TOTAL' AS level, NULL AS group_value,
       (SELECT COUNT(*) FROM source_orders) AS source_count,
       (SELECT COUNT(*) FROM target_orders) AS target_count
UNION ALL
SELECT 'BY_STATUS', status,
       s.cnt, t.cnt
FROM (SELECT status, COUNT(*) cnt FROM source_orders GROUP BY status) s
FULL JOIN (SELECT status, COUNT(*) cnt FROM target_orders GROUP BY status) t
USING (status)
WHERE NVL(s.cnt, 0) != NVL(t.cnt, 0);
4.3 Additive Checksums
-- Sum-based checksum
SELECT 
    'ORDERS' AS table_name,
    COUNT(*) AS record_count,
    SUM(order_total) AS amount_checksum,
    SUM(order_id) AS id_checksum  -- Catches missing/duplicate IDs
FROM orders;
4.4 Hash-Based Checksums
-- Row-level hash
SELECT 
    order_id,
    ORA_HASH(order_id || '|' || customer_id || '|' || order_total || '|' || status) AS row_hash
FROM orders;

-- Compare row hashes between systems
SELECT 
    COALESCE(s.order_id, t.order_id) AS order_id,
    CASE 
        WHEN s.row_hash IS NULL THEN 'MISSING_IN_SOURCE'
        WHEN t.row_hash IS NULL THEN 'MISSING_IN_TARGET'
        WHEN s.row_hash != t.row_hash THEN 'DATA_DIFFERS'
        ELSE 'MATCH'
    END AS status
FROM (SELECT order_id, ORA_HASH(order_id||customer_id||order_total) AS row_hash FROM source_orders) s
FULL JOIN (SELECT order_id, ORA_HASH(order_id||customer_id||order_total) AS row_hash FROM target_orders) t
ON s.order_id = t.order_id
WHERE s.row_hash IS NULL OR t.row_hash IS NULL OR s.row_hash != t.row_hash;
5. Null Detection and Analysis
5.1 Theory of Null Values
┌─────────────────────────────────────────────────────────────────┐
│                  THREE-VALUED LOGIC                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  SQL uses: TRUE, FALSE, UNKNOWN                                  │
│                                                                  │
│  NULL = NULL  → UNKNOWN (not TRUE!)                             │
│  NULL != NULL → UNKNOWN (not FALSE!)                            │
│  NULL > 5     → UNKNOWN                                         │
│                                                                  │
│  Testing implications:                                           │
│  • Use IS NULL / IS NOT NULL for comparisons                    │
│  • COUNT(*) vs COUNT(column) behave differently                 │
│  • Use NVL/COALESCE when comparing nullable values              │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
5.2 Comprehensive Null Analysis
-- Null count per column
SELECT 
    'email' AS column_name,
    COUNT(*) AS total_rows,
    COUNT(*) - COUNT(email) AS null_count,
    ROUND((COUNT(*) - COUNT(email)) * 100.0 / COUNT(*), 2) AS null_pct
FROM customers
UNION ALL
SELECT 'phone', COUNT(*), COUNT(*) - COUNT(phone),
       ROUND((COUNT(*) - COUNT(phone)) * 100.0 / COUNT(*), 2)
FROM customers;
5.3 Dynamic Null Analysis
CREATE OR REPLACE PROCEDURE analyze_nulls(p_table_name IN VARCHAR2)
IS
    v_sql VARCHAR2(4000);
    v_null_count NUMBER;
    v_total NUMBER;
BEGIN
    EXECUTE IMMEDIATE 'SELECT COUNT(*) FROM ' || p_table_name INTO v_total;
    
    DBMS_OUTPUT.PUT_LINE('NULL Analysis for ' || p_table_name);
    DBMS_OUTPUT.PUT_LINE(RPAD('Column', 30) || RPAD('Nulls', 10) || 'Pct');
    
    FOR col IN (SELECT column_name FROM user_tab_columns WHERE table_name = UPPER(p_table_name))
    LOOP
        v_sql := 'SELECT COUNT(*) - COUNT(' || col.column_name || ') FROM ' || p_table_name;
        EXECUTE IMMEDIATE v_sql INTO v_null_count;
        DBMS_OUTPUT.PUT_LINE(
            RPAD(col.column_name, 30) || 
            RPAD(v_null_count, 10) ||
            ROUND(v_null_count * 100.0 / NULLIF(v_total, 0), 2) || '%'
        );
    END LOOP;
END;

5.4 Null Pattern Analysis
-- Find combinations of nulls
SELECT 
    CASE WHEN email IS NULL THEN 'N' ELSE 'Y' END ||
    CASE WHEN phone IS NULL THEN 'N' ELSE 'Y' END ||
    CASE WHEN address IS NULL THEN 'N' ELSE 'Y' END AS null_pattern,
    COUNT(*) AS record_count,
    ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (), 2) AS percentage
FROM customers
GROUP BY 
    CASE WHEN email IS NULL THEN 'N' ELSE 'Y' END ||
    CASE WHEN phone IS NULL THEN 'N' ELSE 'Y' END ||
    CASE WHEN address IS NULL THEN 'N' ELSE 'Y' END
ORDER BY record_count DESC;
6. Duplicate Detection
6.1 Types of Duplicates
Type	Description	Detection Method
Exact	All fields identical	GROUP BY all columns
Partial	Key matches, some fields differ	GROUP BY business key
Fuzzy	Similar but not exact ("Jon" vs "John")	SOUNDEX, UTL_MATCH
6.2 Exact Duplicate Detection
-- Find completely duplicate rows
SELECT customer_id, first_name, last_name, email, COUNT(*) AS occurrences
FROM customers
GROUP BY customer_id, first_name, last_name, email
HAVING COUNT(*) > 1;

-- Using ROW_NUMBER to identify duplicates
SELECT *
FROM (
    SELECT c.*,
           ROW_NUMBER() OVER (PARTITION BY email ORDER BY customer_id) AS rn
    FROM customers c
)
WHERE rn > 1;  -- All duplicates except first
6.3 Key-Based Duplicates
-- Duplicate emails
SELECT email, COUNT(*) AS occurrences,
       LISTAGG(customer_id, ', ') WITHIN GROUP (ORDER BY customer_id) AS customer_ids
FROM customers
WHERE email IS NOT NULL
GROUP BY email
HAVING COUNT(*) > 1;
6.4 Fuzzy Duplicate Detection
-- Using SOUNDEX (phonetic matching)
SELECT c1.customer_id, c1.last_name,
       c2.customer_id AS match_id, c2.last_name AS match_name
FROM customers c1
JOIN customers c2 ON SOUNDEX(c1.last_name) = SOUNDEX(c2.last_name)
WHERE c1.customer_id < c2.customer_id
  AND c1.last_name != c2.last_name;

-- Using UTL_MATCH (edit distance similarity)
SELECT c1.customer_id, c1.last_name,
       c2.customer_id AS match_id, c2.last_name AS match_name,
       UTL_MATCH.JARO_WINKLER_SIMILARITY(c1.last_name, c2.last_name) AS similarity
FROM customers c1
JOIN customers c2 ON c1.customer_id < c2.customer_id
WHERE UTL_MATCH.JARO_WINKLER_SIMILARITY(c1.last_name, c2.last_name) > 85
ORDER BY similarity DESC;
6.5 Duplicate Resolution
-- Keep record with most complete data
WITH ranked_duplicates AS (
    SELECT customer_id, email,
           (CASE WHEN phone IS NOT NULL THEN 1 ELSE 0 END +
            CASE WHEN address IS NOT NULL THEN 1 ELSE 0 END +
            CASE WHEN last_order_date IS NOT NULL THEN 2 ELSE 0 END) AS completeness_score,
           ROW_NUMBER() OVER (
               PARTITION BY email 
               ORDER BY last_order_date DESC NULLS LAST, created_date
           ) AS keep_rank
    FROM customers
    WHERE email IN (SELECT email FROM customers GROUP BY email HAVING COUNT(*) > 1)
)
SELECT * FROM ranked_duplicates WHERE keep_rank = 1;  -- Records to keep
7. Referential Integrity Validation
7.1 Theory of Referential Integrity
┌─────────────────────────────────────────────────────────────────┐
│              REFERENTIAL INTEGRITY                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  ORPHAN RECORDS: Child exists without parent                     │
│  Example: Order with deleted customer                            │
│                                                                  │
│  WHY CONSTRAINTS MAY BE MISSING:                                 │
│  • Performance: FKs slow bulk loads                              │
│  • Legacy systems: Old designs                                   │
│  • Data warehouse: Disabled for ETL                              │
│  • Cross-database: Can't enforce across DBs                      │
│                                                                  │
│  SOLUTION: SQL-based integrity checks                            │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
7.2 Orphan Record Detection
-- Orders without customers
SELECT 'Orphan Orders' AS issue, COUNT(*) AS count
FROM orders o
WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id);

-- Comprehensive orphan check
WITH orphan_checks AS (
    SELECT 'orders.customer_id -> customers' AS relationship, o.order_id AS record_id
    FROM orders o WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id)
    UNION ALL
    SELECT 'order_items.order_id -> orders', oi.item_id
    FROM order_items oi WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.order_id = oi.order_id)
    UNION ALL
    SELECT 'employees.department_id -> departments', e.employee_id
    FROM employees e WHERE department_id IS NOT NULL
      AND NOT EXISTS (SELECT 1 FROM departments d WHERE d.department_id = e.department_id)
)
SELECT relationship, COUNT(*) AS orphan_count
FROM orphan_checks
GROUP BY relationship;
7.3 Self-Referencing Integrity
-- Check employee manager hierarchy
SELECT employee_id, manager_id, 'Invalid manager' AS issue
FROM employees e
WHERE manager_id IS NOT NULL
  AND NOT EXISTS (SELECT 1 FROM employees m WHERE m.employee_id = e.manager_id);

-- Detect circular references
WITH RECURSIVE emp_hierarchy AS (
    SELECT employee_id, manager_id, CAST(employee_id AS VARCHAR2(4000)) AS path
    FROM employees WHERE manager_id IS NULL
    UNION ALL
    SELECT e.employee_id, e.manager_id, h.path || '->' || e.employee_id
    FROM employees e JOIN emp_hierarchy h ON e.manager_id = h.employee_id
    WHERE h.path NOT LIKE '%' || e.employee_id || '%'  -- Prevent cycles
)
SELECT * FROM employees WHERE employee_id NOT IN (SELECT employee_id FROM emp_hierarchy);
8. Business Rule Validation
8.1 Types of Business Rules
Type	Description	Example
Attribute	Single field	Order total > 0
Intra-record	Multiple fields, same record	Ship date > order date
Inter-record	Multiple records	Sum of items = order total
Temporal	Time-based	Cancel within 24 hours
8.2 Attribute Rules
-- Salary within job grade range
SELECT e.employee_id, e.salary, j.min_salary, j.max_salary,
       CASE 
           WHEN e.salary < j.min_salary THEN 'Below minimum'
           WHEN e.salary > j.max_salary THEN 'Above maximum'
           ELSE 'Within range'
       END AS status
FROM employees e JOIN jobs j ON e.job_id = j.job_id
WHERE e.salary < j.min_salary OR e.salary > j.max_salary;
8.3 Intra-Record Rules
-- Date sequence validation
SELECT order_id, order_date, ship_date, delivery_date,
       CASE 
           WHEN ship_date < order_date THEN 'Ship before order'
           WHEN delivery_date < ship_date THEN 'Delivery before ship'
           ELSE 'VALID'
       END AS date_check
FROM orders
WHERE ship_date < order_date OR delivery_date < ship_date;

-- Conditional requirements
SELECT order_id, status, tracking_number,
       CASE 
           WHEN status = 'SHIPPED' AND tracking_number IS NULL THEN 'Missing tracking'
           ELSE 'OK'
       END AS check_result
FROM orders
WHERE status = 'SHIPPED' AND tracking_number IS NULL;
8.4 Inter-Record Rules
-- Order total must equal sum of line items
SELECT o.order_id, o.order_total AS stored_total,
       SUM(oi.quantity * oi.unit_price) AS calculated_total,
       ABS(o.order_total - SUM(oi.quantity * oi.unit_price)) AS difference
FROM orders o JOIN order_items oi ON o.order_id = oi.order_id
GROUP BY o.order_id, o.order_total
HAVING ABS(o.order_total - SUM(oi.quantity * oi.unit_price)) > 0.01;

-- Credit limit check
SELECT c.customer_id, c.credit_limit, SUM(o.order_total) AS outstanding
FROM customers c JOIN orders o ON c.customer_id = o.customer_id
WHERE o.status NOT IN ('CANCELLED', 'DELIVERED')
GROUP BY c.customer_id, c.credit_limit
HAVING SUM(o.order_total) > c.credit_limit;

9.2 Snapshot-Based Testing
-- Create pre-release snapshot
CREATE TABLE snapshot_orders AS
SELECT order_id, customer_id, order_total, status,
       ORA_HASH(order_id || customer_id || order_total || status) AS row_hash,
       SYSDATE AS snapshot_date
FROM orders;

-- Post-release comparison
SELECT COALESCE(s.order_id, o.order_id) AS order_id,
       CASE 
           WHEN s.order_id IS NULL THEN 'NEW'
           WHEN o.order_id IS NULL THEN 'DELETED'
           WHEN s.row_hash != ORA_HASH(o.order_id||o.customer_id||o.order_total||o.status) THEN 'MODIFIED'
           ELSE 'UNCHANGED'
       END AS change_type
FROM snapshot_orders s FULL JOIN orders o ON s.order_id = o.order_id
WHERE s.order_id IS NULL OR o.order_id IS NULL 
   OR s.row_hash != ORA_HASH(o.order_id||o.customer_id||o.order_total||o.status);
9.3 Expected Value Tests
-- Test cases with expected values
CREATE TABLE regression_tests (
    test_id NUMBER PRIMARY KEY,
    test_name VARCHAR2(100),
    test_query CLOB,
    expected_value VARCHAR2(1000),
    comparison_type VARCHAR2(20)  -- EXACT, RANGE, NOT_NULL
);

INSERT INTO regression_tests VALUES (1, 'Total Active Customers', 
    'SELECT COUNT(*) FROM customers WHERE status = ''ACTIVE''', '10000', 'RANGE:9500:10500');
INSERT INTO regression_tests VALUES (2, 'Order #12345 Total',
    'SELECT order_total FROM orders WHERE order_id = 12345', '1250.00', 'EXACT');
COMMIT;

-- Execute tests
CREATE OR REPLACE PROCEDURE run_regression_tests
IS
    v_actual VARCHAR2(1000);
    v_status VARCHAR2(20);
BEGIN
    FOR test IN (SELECT * FROM regression_tests)
    LOOP
        EXECUTE IMMEDIATE test.test_query INTO v_actual;
        
        IF test.comparison_type = 'EXACT' THEN
            v_status := CASE WHEN v_actual = test.expected_value THEN 'PASS' ELSE 'FAIL' END;
        END IF;
        
        DBMS_OUTPUT.PUT_LINE('[' || v_status || '] ' || test.test_name || 
                            ' | Expected: ' || test.expected_value || 
                            ' | Actual: ' || v_actual);
    END LOOP;
END;

9.4 Aggregate Baseline Comparison
-- Capture baseline
CREATE TABLE aggregate_baseline AS
SELECT 'ORDERS' AS table_name, 'COUNT' AS metric, COUNT(*) AS value FROM orders
UNION ALL SELECT 'ORDERS', 'SUM', SUM(order_total) FROM orders
UNION ALL SELECT 'CUSTOMERS', 'COUNT', COUNT(*) FROM customers;

-- Compare to baseline
SELECT b.table_name, b.metric, b.value AS baseline,
       c.current_value,
       ROUND(ABS(c.current_value - b.value) / NULLIF(b.value, 0) * 100, 2) AS variance_pct
FROM aggregate_baseline b
JOIN (
    SELECT 'ORDERS' AS table_name, 'COUNT' AS metric, COUNT(*) AS current_value FROM orders
    UNION ALL SELECT 'ORDERS', 'SUM', SUM(order_total) FROM orders
    UNION ALL SELECT 'CUSTOMERS', 'COUNT', COUNT(*) FROM customers
) c ON b.table_name = c.table_name AND b.metric = c.metric
WHERE ABS(c.current_value - b.value) / NULLIF(b.value, 0) > 0.01;  -- >1% variance

    run_id          NUMBER,
    test_name       VARCHAR2(100),
    test_category   VARCHAR2(50),
    status          VARCHAR2(20),
    message         VARCHAR2(4000),
    row_count       NUMBER,

10.2 Testing Package
CREATE OR REPLACE PACKAGE data_test_framework AS
    PROCEDURE run_all_tests(p_category VARCHAR2 DEFAULT NULL);
    PROCEDURE run_null_checks(p_table_name VARCHAR2);
    PROCEDURE run_duplicate_checks(p_table_name VARCHAR2, p_key_columns VARCHAR2);
    PROCEDURE run_referential_checks;
    PROCEDURE generate_report(p_run_id NUMBER);
END;
/

CREATE OR REPLACE PACKAGE BODY data_test_framework AS
    g_run_id NUMBER;
    
    PROCEDURE log_result(p_name VARCHAR2, p_category VARCHAR2, p_status VARCHAR2, 
                        p_message VARCHAR2, p_count NUMBER, p_ms NUMBER) IS
        PRAGMA AUTONOMOUS_TRANSACTION;
    BEGIN
        INSERT INTO data_test_results (run_id, test_name, test_category, status, message, row_count, execution_ms)
        VALUES (g_run_id, p_name, p_category, p_status, p_message, p_count, p_ms);
        COMMIT;
    END;
    
    PROCEDURE run_all_tests(p_category VARCHAR2 DEFAULT NULL) IS
    BEGIN
        SELECT NVL(MAX(run_id), 0) + 1 INTO g_run_id FROM data_test_results;
        DBMS_OUTPUT.PUT_LINE('Starting Test Run #' || g_run_id);
        
        IF p_category IS NULL OR p_category = 'NULL_CHECKS' THEN
            run_null_checks('CUSTOMERS');
            run_null_checks('ORDERS');
        END IF;
        
        IF p_category IS NULL OR p_category = 'DUPLICATES' THEN
            run_duplicate_checks('CUSTOMERS', 'email');
        END IF;
        
        IF p_category IS NULL OR p_category = 'REFERENTIAL' THEN
            run_referential_checks;
        END IF;
        
        generate_report(g_run_id);
    END;
    
    PROCEDURE run_null_checks(p_table_name VARCHAR2) IS
        v_start TIMESTAMP; v_count NUMBER; v_sql VARCHAR2(4000);
    BEGIN
        FOR col IN (SELECT column_name FROM user_tab_columns WHERE table_name = UPPER(p_table_name))
        LOOP
            v_start := SYSTIMESTAMP;
            v_sql := 'SELECT COUNT(*) FROM ' || p_table_name || ' WHERE ' || col.column_name || ' IS NULL';
            EXECUTE IMMEDIATE v_sql INTO v_count;
            log_result(p_table_name || '.' || col.column_name || ' NULL', 'NULL_CHECKS', 'INFO',
                      v_count || ' nulls', v_count, EXTRACT(SECOND FROM (SYSTIMESTAMP - v_start)) * 1000);
        END LOOP;
    END;
    
    PROCEDURE run_duplicate_checks(p_table_name VARCHAR2, p_key_columns VARCHAR2) IS
        v_start TIMESTAMP; v_count NUMBER;
    BEGIN
        v_start := SYSTIMESTAMP;
        EXECUTE IMMEDIATE 'SELECT COUNT(*) FROM (SELECT ' || p_key_columns || 
                         ' FROM ' || p_table_name || ' GROUP BY ' || p_key_columns || ' HAVING COUNT(*) > 1)'
            INTO v_count;
        log_result(p_table_name || ' duplicates on ' || p_key_columns, 'DUPLICATES',
                  CASE WHEN v_count = 0 THEN 'PASS' ELSE 'FAIL' END,
                  v_count || ' duplicates', v_count, EXTRACT(SECOND FROM (SYSTIMESTAMP - v_start)) * 1000);
    END;
    
    PROCEDURE run_referential_checks IS
        v_start TIMESTAMP; v_count NUMBER;
    BEGIN
        v_start := SYSTIMESTAMP;
        SELECT COUNT(*) INTO v_count FROM orders o
        WHERE NOT EXISTS (SELECT 1 FROM customers c WHERE c.customer_id = o.customer_id);
        log_result('Orders->Customers FK', 'REFERENTIAL',
                  CASE WHEN v_count = 0 THEN 'PASS' ELSE 'FAIL' END,
                  v_count || ' orphans', v_count, EXTRACT(SECOND FROM (SYSTIMESTAMP - v_start)) * 1000);
    END;
    
    PROCEDURE generate_report(p_run_id NUMBER) IS
        v_total NUMBER; v_passed NUMBER; v_failed NUMBER;
    BEGIN
        SELECT COUNT(*), SUM(CASE WHEN status = 'PASS' THEN 1 ELSE 0 END),
               SUM(CASE WHEN status = 'FAIL' THEN 1 ELSE 0 END)
        INTO v_total, v_passed, v_failed FROM data_test_results WHERE run_id = p_run_id;
        
        DBMS_OUTPUT.PUT_LINE('=== TEST SUMMARY ===');
        DBMS_OUTPUT.PUT_LINE('Total: ' || v_total || ' | Passed: ' || v_passed || ' | Failed: ' || v_failed);
    END;
END;
